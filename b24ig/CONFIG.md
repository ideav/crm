# Конфиг коннектора: источники (Битрикс24, 1С) → Интеграм

Один JSON-файл описывает один проект: какой Битрикс, какая база Интеграма, какие сущности, куда и как их загружать.
Код коннектора общий для всех проектов, всё проектное лежит в конфиге.

Пример: [`config/sportzania-spz.json`](config/sportzania-spz.json). Проверка конфига по живой базе: [`tools/validate_config.py`](tools/validate_config.py).

---

## Верхний уровень

| Ключ | Назначение |
|---|---|
| `version` | Версия формата конфига (сейчас `1`) |
| `project` | Имя проекта: по нему называются папки состояния и логов |
| `sources` | Подключения к источникам по именам: `bitrix24`, `odata1c` |
| `target` | Подключение к Интеграму |
| `runtime` | Часовой пояс (`timezone`), папки состояния и логов, блокировка, срок хранения логов в днях (`log_keep_days`), пробный запуск (`dry_run`). При запуске для базы относительные пути считаются от `templates/custom/<база>/connector/` |
| `safety` | Защиты от порчи данных |
| `notify` | Уведомления (Telegram) |
| `dictionaries` | Перевод кодов Битрикса в названия |
| `order` | Порядок загрузки сущностей. Сущность, на которую ссылаются, идёт раньше |
| `entities` | Описание сущностей |

### Секреты
Секреты **не пишутся в конфиг**, только ссылкой: `"${B24_WEBHOOK}"`, `"${INTEGRAM_TOKEN}"`. Значение берётся из переменной
окружения, а если её нет — из `secrets.json` в папке базы (`templates/custom/<база>/connector/secrets.json`, при запуске `--db`
или по URL: у cron по URL своего окружения нет). Валидатор отклоняет конфиг, в котором вместо ссылки стоит значение.

### `sources` — подключения
Словарь «имя подключения → настройки». Сущность выбирает подключение через `source.connection`, справочник — через `connection`.
Если подключение одно, `connection` можно не указывать. Старый формат с одним ключом `source` тоже читается.

```json
"sources": {
  "b24": { "type": "bitrix24", "webhook": "${B24_WEBHOOK}", "timezone": "Europe/Moscow" }
}
```

Ядро работает с источником через интерфейс `SourceAdapter` (`src/Source.php`): обход страниц по независимым от
источника условиям (период, курсор ID, «изменено после»), описание полей, справочники. Новый тип источника —
это новый адаптер, без изменений ядра.

Настройки подключения `type: bitrix24` (в тестах `transport: mock` + `fixtures_dir` — имитация по JSON-файлам):
| Ключ | По умолчанию | Что делает |
|---|---|---|
| `webhook` | — | URL входящего вебхука (из окружения) |
| `page_size` | 50 | Размер порции (лимит API Битрикса — 50) |
| `requests_per_sec` | 2 | Ограничение частоты запросов |
| `timeout_sec`, `retries` | 30, 3 | Таймаут и число повторов при сетевой ошибке |
| `timezone` | — | Часовой пояс портала для фильтров по датам |

### `target` (Интеграм)
| Ключ | Что делает |
|---|---|
| `base_url`, `db`, `token` | Адрес, база, токен (из окружения) |
| `max_file_bytes` | Размер одного файла импорта. Лимит ядра 8 МБ, берём с запасом 7 МБ |
| `max_rows_per_file` | Строк в одном файле импорта |
| `request_time_sec` | Параметр `TIME` для долгих запросов (по умолчанию 30 с, максимум 600) |

### `safety`
| Ключ | Что делает |
|---|---|
| `on_schema_drift: stop` | Если в Битриксе или Интеграме пропало поле или колонка, либо сменился тип, сущность не загружается, приходит уведомление |
| `never_send_empty_name` | Не отправлять строку с пустой первой колонкой: при ключе уникальности ядро **удалит** запись |
| `require_key` | Не отправлять строку без внешнего ключа |
| `verify_counts` | После загрузки сверить число записей с источником |
| `max_new_ratio_on_full_load` | Если полная загрузка создаёт больше этой доли новых записей, остановиться: вероятна ошибка ключа |
| `advance_state_only_after_upload` | Отметка «докуда загружено» сдвигается только после успешного импорта |

## `dictionaries` — перевод кодов в названия

| `source` | Откуда берётся (для нестатичных — через подключение `connection`) |
|---|---|
| `crm.status.list` | Справочники CRM. `entity_prefix` задаёт тип: `DEAL_STAGE` (включая `DEAL_STAGE_<воронка>`), `SOURCE`, `STATUS` |
| `crm.lead.fields` / `crm.deal.fields` | Списочные пользовательские поля: `field`, варианты в `items` |
| `static` | Фиксированная карта `map` |

Справочники загружаются **при каждом запуске**, поэтому новая стадия или источник появятся без правки кода. `fallback_file` используется, только если Битрикс недоступен.
Неизвестный код передаётся как есть и попадает в отчёт.

## `entities` — сущности

```json
"leads": {
  "enabled": true,
  "source":  { ... },
  "load":    { ... },
  "target":  { ... },
  "hierarchy": { "parent_field": "PARENT" },
  "fields":  { "<поле Битрикса>": { ... } },
  "on_source_delete": "keep"
}
```

### `source`
| Ключ | Значения |
|---|---|
| `connection` | Имя подключения из `sources` (можно не указывать, если подключение одно) |
| `method` | Метод REST: `crm.lead.list`, `crm.deal.list`, `tasks.task.list`, `user.get`, `department.get` |
| `pagination` | `id_cursor` (фильтр `>ID`, для больших таблиц) · `start` (параметр `start`/`next`) |
| `result_path` | Где лежат записи в ответе: `result`, `result.tasks` |
| `response_keys` | `camelCase`, если API отдаёт ключи не так, как принимает `select` (задачи: `RESPONSIBLE_ID` → `responsibleId`) |
| `filters` | Список фильтров, выполняемых по очереди, с дедупликацией по ID (пользователи: активные и уволенные) |
| `from_entity` | Не ходить в Битрикс, взять записи уже скачанной сущности (Табельный из пользователей) |

### `load`
| `mode` | Поведение |
|---|---|
| `full` | Каждый запуск забирает всё (справочные сущности: отделы, пользователи) |
| `incremental` | Фаза `new`: записи с ID больше курсора. Фаза `updated`: записи с `field` новее прошлого успешного запуска. Период задаётся `period.from` / `period.to` (`null` — без границы), **год в коде не зашит** |

### `target`
| Ключ | Значения |
|---|---|
| `table` / `table_id` | Имя и ID таблицы. Валидатор сверяет, что это одна и та же таблица |
| `key` | Колонка **внешнего ключа**. `@name` — первая колонка (таблица должна быть уникальной). Иначе имя колонки с флагом `key` **в неуникальной таблице**: если первая колонка уникальна, импорт ищет запись по ключу и названию, и переименование в источнике даёт дубль (проверено). Важно при создании таблиц: `_d_new` делает таблицу уникальной при **любом** значении параметра `unique`, даже `unique=0` — для неуникальной таблицы параметр не передавать |
| `mode` | `upsert` — создать или обновить · `insert_only` — только новые ключи, существующие записи не трогать (кадровые таблицы) |
| `bind_existing` | Привязка старых записей без ключа: `by: "@name"`, нормализация `trim`/`lower`/`yo`. Однозначное совпадение — проставить ключ, неоднозначное — в отчёт на ручную привязку |

### `fields`
Ключ — поле Битрикса. Если одно поле нужно в двух колонках, ключ пишется с суффиксом `@…`, а исходное поле указывается в `from`:
```json
"UF_DEPARTMENT":     { "column": "Департаменты (ID)", "transform": "join" },
"UF_DEPARTMENT@ref": { "column": "Департамент", "from": "UF_DEPARTMENT", "ref": { "entity": "departments", "by": "key", "multi": true } }
```

| Ключ | Что делает |
|---|---|
| `column` | Колонка Интеграма (имя или псевдоним). `@name` — первая колонка |
| `transform` | см. ниже |
| `ref` | Колонка-ссылка, см. ниже |
| `optional` | Поле может отсутствовать в Битриксе: предупреждение вместо остановки |

**Преобразования `transform`:**
| Значение | Что делает |
|---|---|
| *(нет)* | Строка как есть. Переносы и табуляции заменяются пробелом, `\` и `;` экранируются |
| `number` | Целое. Пусто остаётся пустым |
| `money` | Десятичное с точкой |
| `datetime` | ISO-дата Битрикса `2026-05-12T10:17:25+03:00` передаётся как есть (ядро разбирает её с учётом пояса, проверено) |
| `yn` | `Y`/`N`, булевы `true`/`false` переводятся в `Y`/`N` |
| `join` | Массив склеивается через `,` без пробелов |
| `multifield` | Мультиполе CRM (`PHONE`, `EMAIL`, `WEB`, `IM`): значения `VALUE` через `, ` |
| `dict:<имя>` | Перевод кода через `dictionaries.<имя>`, для массива поэлементно |
| `template` | Сборка строки: `"template": "{LAST_NAME} {NAME} {SECOND_NAME}"`, лишние пробелы убираются |

**Ссылки `ref`:**
| Ключ | Значения |
|---|---|
| `entity` | Сущность этого же конфига, на которую ссылаемся |
| `by` | `key` — ищем цель по её внешнему ключу · `name` — по названию в таблице-справочнике |
| `missing` | `skip` — нет цели, поле остаётся пустым (**заглушка не создаётся**) · `create` — создать запись в справочнике · `error` — остановить |
| `multi` | Мультиссылка |

Как ставится ссылка, коннектор решает сам:
- цель ищется по уникальной первой колонке и найдена в снимке → ссылка отправляется в импорте (быстро);
- цель ищется по ключевой колонке (отделы) или имя неоднозначно → ссылка ставится **вторым проходом** через `_m_set` по id записи. Иначе импорт возьмёт первую запись с этим именем.

### `hierarchy`
`parent_field` — поле-родитель. Записи загружаются сверху вниз, ссылка на родителя ставится вторым проходом.

### `on_source_delete`
`keep` — не трогать запись, которая пропала из источника (по умолчанию). Мягкая пометка «неактивна» — в следующей версии формата.

## Порядок работы коннектора (для справки)

1. Загрузить конфиг, подставить секреты из окружения, проверить схему: `metadata` Интеграма и `*.fields` Битрикса.
2. Загрузить справочники.
3. По сущностям в порядке `order`:
   - скачать данные;
   - построить снимок ключей в Интеграме;
   - привязать старые записи (`bind_existing`);
   - собрать файлы импорта в порядке колонок из `metadata` с `;` в конце строки;
   - загрузить;
   - вторым проходом проставить ссылки;
   - сверить число записей;
   - сохранить состояние.
4. Записать итоговый отчёт и отправить уведомление.

## Источник 1С (OData)

Стандартный интерфейс OData 1С:Предприятия: администратор 1С публикует базу с галочкой «Публиковать стандартный интерфейс OData»
и заводит пользователя только на чтение (инструкция — `docs/connector-1c.md` в `ideav/crm`).

```json
"sources": {
  "1c": { "type": "odata1c", "url": "https://сервер/база/odata/standard.odata/", "user": "${ONEC_USER}", "password": "${ONEC_PASSWORD}",
          "timezone": "Europe/Moscow", "page_size": 500, "timeout_sec": 60, "retries": 3 }
}
```

| Где | Ключ | Что делает |
|---|---|---|
| `source` | `entity` | Набор OData: `Catalog_Контрагенты`, `Document_РеализацияТоваровУслуг` |
| `source` | `filter` | Дополнительный `$filter`, например `DeletionMark eq false` |
| `source` | `order`, `page_size` | Сортировка для `$top/$skip` (по умолчанию `Ref_Key`) и размер страницы |
| `load` | `period` | Документы за период: `$filter` по полю даты (`Date ge datetime'…'`) |
| `load` | `detect_changes: {field: DataVersion}` | Отправлять только записи, у которых версия изменилась с прошлой успешной загрузки (версии — в `state/<сущность>.versions.json`). Работает для любого источника в режиме `full` |
| `dictionaries` | `source: odata.entity` | Справочник «GUID → название» из любой сущности 1С (`entity`, `code`, `name`) |

**Что адаптер делает с данными.**
- Нулевой GUID `00000000-…` (пустая ссылка) превращается в пусто.
- Пустая дата `0001-01-01T00:00:00` превращается в пусто (иначе Интеграм запишет 01.01.2001 — проверено).
- К дате без пояса дописывается пояс подключения.
- Поля сверяются с `$metadata`; неизвестные поля в `$select` не попадают.

Курсоров `>ID` и «изменено после» у 1С нет, поэтому `load.mode: incremental` для 1С не используется.

### Табличные части документов → подчинённые таблицы
```json
"sale_items": {
  "source": { "from_entity": "sales", "collection": "Товары" },
  "load":   { "mode": "full" },
  "target": { "table": "Строка реализации", "table_id": 123, "mode": "replace_children", "parent": { "entity": "sales" } },
  "fields": {
    "LineNumber":       { "column": "@name", "transform": "number" },
    "Номенклатура_Key": { "column": "Номенклатура", "ref": { "entity": "products", "by": "key", "missing": "skip" } },
    "Количество":       { "column": "Количество", "transform": "money" }
  }
}
```
- Строки берутся из коллекции родительского документа (без отдельных запросов).
- У строк нет своего ключа, поэтому у **изменённых** родителей (по `detect_changes`) старые строки удаляются и загружаются заново одним файлом.
  Файл грузится с `autoParent`, первая колонка файла — id записи родителя. Строки неизменённых документов не трогаются.
- Колонка подчинённой таблицы у родителя при импорте родителя остаётся пустой: число строк ядро считает само.
- Если строки не сошлись, версии этих родителей сбрасываются: следующий запуск перечитает их.

## Что сознательно не входит в v1
- Воронки сделок (`CATEGORY_ID`) и контакты/компании: колонок нет, при необходимости добавятся одной строкой в `fields`.
- Удаление и пометка записей, пропавших из источника.
- Регистры 1С (остатки, обороты): у записей нет ключа, нужен составной ключ — следующий шаг.
