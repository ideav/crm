# Матрица разрешений и приоритетов (#4734)

Одна страница на вопрос «что произойдёт, когда нажали вот это»: какие типовые операции запускает
каждое действие, что этому действию разрешено трогать и чем разрешаются конфликты правил.

Правила по существу живут в ТЗ [`atex_planning_tz.md`](atex_planning_tz.md) §15 и в исполняемом
реестре `download/atex/js/production-planning/05-invariants.js`; конвейер описан в
[`atex_production_planning_algorithm.md`](atex_production_planning_algorithm.md). Здесь — сводка со
ссылками `file:line`, по которой видно, кому что можно.

---

## На пальцах

Планировщик получает команды из **четырёх входов**, и разрешения у них разные.

| вход | признак | действия |
|---|---|---|
| **Ручное адресное** | оператор назвал КОНКРЕТНОЕ задание | перенос 🗓, ↑↓, перетаскивание, удаление |
| **Ручное по отклонениям** | адреса нет, права ручные | «Урегулировать» |
| **Автоматика по набору** | раскидывает всё подряд | «Сгенерировать», «Упорядочить» |
| **Пересчёт чисел** | порядок и дни остаются, меняются минуты и старты | «↻ Пересчитать наладку», «⏩ Пересчитать отсюда» |

Отсюда главное свойство матрицы: **ранг правил — функция трёх аргументов (правило A, правило B,
вход)**. Одна и та же пара разрешается в разные стороны в зависимости от того, кто спрашивает
(#4728, решение заказчика 12.08.2026; таблица — §4.2). Плоская лестница «что важнее чего» конфликты
этого рабочего места не выражает.

Два сквозных правила, которые матрица не переопределяет нигде:

- **ручное действие не получает отказа** (решение заказчика 02.08 и 05.08.2026). Ни окно `[С; По]`,
  ни потолок дня, ни заморозка отказом не оборачиваются. Единственное исключение — §4.3;
- **отработанный станко-день планированием не судится** (#4740): начатое и выполненное — факт, его
  не двигают, за перебор смены не судят и в набивку не тянут.

## 1. Что запускает нажатие

Типовые операции из тикета:

| № | операция | где живёт |
|---|---|---|
| 1 | поиск места для задания при оптимизации | слой размещения `15-slot-placement.js` (`computeSlotPlacement`) |
| 2 | поиск места для задания при генерации | тот же слой: «Сгенерировать» и «Упорядочить» — один конвейер (#4001) |
| 3 | сдвиг паровозом после встраивания задания | `splitMachineQueue` при `preserveOrder`, `10-planning-engine.js` |
| 4 | сдвиг паровозом после удаления задания | `autoSequenceQueue(SETUP, preserveOrder=true)`, `20-controller.js:10896` |
| 5 | сдвиг паровозом после переноса задания | 3 + 4 одним расчётом |
| 6 | пересчёт тайминга заданий | `computeCutSetupUpdates:8150` + `recalcStartUpdates:11553` / `reconcilePlanStarts:11416` |
| 7 | проверка наполненности дня | `overfilledDaysOf` + `plannerUnderfilledDays` → `levelDayLoad:12312` |
| 8 | контроль валидности картины | детектор `recalcMismatchRows:11673` (экран) + страж `guardPlanOps` (запись) |

Кто из них участвует в каждом действии (номера — из таблицы выше):

| действие | точка входа | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| **Сгенерировать** | `generateCuts:6929` → `runGenerateCuts:7232` | — | ✓ | ✓ | — | — | ✓ | ✓ | ✓ |
| **Упорядочить** (Станок/Все) | `optimizeQueue:2835` → `runOptimizeQueue:3469` | ✓ | — | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **Урегулировать** | `settleDeviations:4824` | — | — | ✓ | — | ✓ | ✓ | ✓ | ✓ |
| **Перенос 🗓** (и drag между днями) | `moveCutToDay:4324` | ✓ | — | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **↑↓ внутри дня** | `moveCutInDay:8518` | — | — | — | — | — | ✓ | ✓ | ✓ |
| **Перетаскивание внутри дня** | `reorderCutInDay:11155` | — | — | ✓ | — | — | ✓ | ✓ | ✓ |
| **Удаление задания** | `deleteCutTask:5391` → `runDeleteCutTask:5447` | — | — | — | ✓ | — | ✓ | ✓ | ✓ |
| **↻ Пересчитать наладку** | `recalcSetupTiming:11716` | — | — | — | — | — | ✓ | ✓ | ✓ |

Строки без «✓» в 1–5 план не перепланируют: они меняют минуты, старты и разбиение по дням, а место
и порядок берут как есть.

**Вход в рабочее место ничего не пишет.** `reload` только читает (`loadCutStrips` → `loadPlanning`
→ `loadSleeveBatches` → `loadShiftEvents`), лечение «Вида сырья» и «Партии сырья» идёт **в памяти**
(`healContinuationMaterials`, `healCutBatches:2147`) и уходит в базу при ближайшей записи плана.
Оператору при входе показываются: кнопка «↻ Пересчитать наладку (заданий: N)» и бейджи расхождений
одним расчётом (`recalcMismatchRows`, #4479), бейдж дня «(N мин)» и просрочка.

## 2. Что каждому действию разрешено

«✓» — вправе; «—» — не делает; «⛔» — получает отказ.

| действие | порядок в дне | день задания | 🔒 сосед | замороженный день | начатое / выполненное | станок |
|---|---|---|---|---|---|---|
| **Сгенерировать** | пересобирает | двигает свободные, 🔒 держит свой день | ⛔ `FIXED_CUT_DAY` (drop) | ⛔ `FROZEN_DAY` (drop) | не трогает (#4572, #4381) | вправе сменить |
| **Упорядочить · Все** | пересобирает | двигает свободные | ⛔ (#4728: адреса нет — прав нет) | ⛔ | не трогает | вправе сменить |
| **Упорядочить · Станок** | пересобирает | двигает свободные | ⛔ | ⛔ | не трогает | заперт `withinSlitterIds` |
| **Урегулировать** | сохраняет (`trainOnly`) | двигает вперёд паровозом | ✓ двигает (`manualShift`, #4736) | ✓ пишет и выбирает его (#4569, PR#4571) | оставляет на месте, делит по факту (#4564) | заперт `machineLockByCut` |
| **Перенос 🗓** | пересобирает по срокам (`preserveOrder=false`, #4074) | ставит в выбранный оператором (`pinCutIds` / `weightPositionCutIds`) | ✓ двигает хвост (#4736) | ✓ кладёт, лишнее рвёт по потолку (#4494) | ⛔ «Начатое задание нельзя перенести» (`:4328`, `:4357`) | по диалогу; отпуск целевого станка — ⛔ (`:4387`) |
| **↑↓ внутри дня** | меняет | сохраняет | ✓ переставляет: замок держит ДЕНЬ (#4392) | ручной пересчёт заморозку не соблюдает (#4582) | ⛔ начатое — «стена» (#4381) | — |
| **Перетаскивание внутри дня** | меняет | сохраняет | ✓ переставляет + двигает хвост (`manualShift`, `:11187`) | то же | ⛔ начатое — «стена» | — |
| **Удаление задания** | сохраняет (`preserveOrder=true`) | схлопывает дыру, хвост едет назад | ✓ двигает хвост; 🔒 **в самой цепочке** — ⛔ (`:5403`) | — | ⛔ начатое удалить нельзя (`:5410`) | — |
| **↻ Пересчитать наладку** | сохраняет | сохраняет (#4401) | не двигает | по кнопке оператора — не соблюдает (#4582); автоматический вызов — соблюдает | не трогает | заперт станком |
| **⏩ Пересчитать отсюда** | сохраняет (решение 01.08.2026) | сохраняет; прошлое закреплено `keepBeforeCutId` | не двигает | не соблюдает (#4588) | не трогает | заперт станком |
| **Вход в рабочее место** | — | — | — | — | — | — |

Три поля, которыми действие объявляет свои права, и одна точка, где они читаются:

| поле `moveScope` | что объявляет | читают |
|---|---|---|
| `wholeDayCutIds` / `pinCutIds` / `weightPositionCutIds` | «оператор несёт ЭТО задание сейчас» | страж → `isManualMoveCut:10602` |
| `manualShift` | «двигается весь хвост очереди, включая 🔒» | страж → `ctx.isFixedShiftedCut`; упаковщик → `manualShiftByCut` |
| `unfrozenDayKeys` / `dayKeys` | «эти дни для этого действия разморожены и видимы» | `manualUnfrozen`, `recalcScopeCutIds` |

Страж всегда зовётся с набором правил автоматики (`guardPlanOps`, `:10598`) — ручные права
выражаются предикатами контекста. Поэтому «действие ручное» надо **донести полем**: не донёс —
правило автоматики снимет операции цепочки целиком (#4536), и задание останется с прежним временем.

## 3. Реестр §15: кого ограничивает и как

`actor: 'auto'` — правило ограничивает автоматику, ручное действие проходит (и пишется в журнал).
`actor: 'any'` — запрет для всех. `mode: 'drop'` — страж выбрасывает нарушающую операцию;
`mode: 'audit'` — выбросить нечего, правило называет причину и ловит регрессию на всех путях
записи. `gate: 'ratchet'` — набор операций сравнивается с ХРАНИМЫМ планом, и созданное или
углублённое нарушение снимает операции всех затронутых цепочек целиком.

| правило | actor | mode | gate | о чём |
|---|---|---|---|---|
| `FROZEN_DAY` | auto | drop | — | автоматика не изменяет замороженный день: ни двигает, ни удаляет, ни кладёт новое |
| `FIXED_CUT_DAY` | auto | drop | — | автоматика не меняет ДЕНЬ 🔒 и не удаляет её |
| `FIXED_BLOCK` | auto | audit | — | 🔒 одного дня — монолит: порядок между собой не меняется, между ними ничего не встаёт |
| `FIXED_NO_PUSH` | auto | audit | — | перед 🔒 автоматика ничего не ставит |
| `FIXED_NO_OVERTAKE` | auto | audit | — | подвижное не обгоняет 🔒, за которой стояло |
| `DAY_CAPACITY` | auto | audit | — | станко-день не длиннее смены с нахлёстом |
| `DAY_FILL` | auto | audit | — | станко-день пакуется до потолка |
| `CHAIN_CONTIGUOUS` | any | audit | ratchet | части разорванного по дням задания идут непрерывно |
| `ORDER_PARTS_ADJACENT` | any | audit | — | части одной работы, оказавшиеся рядом в одном дне, — одно задание |
| `CUT_BATCH` | any | audit | — | задание в производство обязано иметь «Партию сырья» |
| `CHAIN_SETUP_ONCE` | any | audit | — | наладка разорванного по дням задания платится один раз на цепочку |
| `SUPPLY_CONSERVED` | any | audit | ratchet | выпуск позиции по всем заданиям не меньше заказанного количества |

Таблица держится тестом `experiments/atex-pp-4734-rule-matrix.test.js`: состав правил, `actor`,
`mode` и `gate` в этом документе сверяются с реестром, и расхождение роняет гейт.

## 4. Приоритеты

### 4.1. Внутри одного расчёта: объектив плана

Кандидаты «Упорядочить» и итоговый план судятся ОДНИМ выражением
(`combinedPlanObjective`, `20-controller.js:2906`) — лексикографический порядок сверху вниз:

| ранг | что | вес | тикет |
|---|---|---|---|
| 1 | задание в окне «Отпуска» станка (станок не работает) | `1e15` | #4413 |
| 2 | новое нарушение жёсткого правила §15 (`ops.ruleBreaks`) | `1e12` | #4471 |
| 3 | дни опоздания | `1e9` | #4064 |
| 4 | недоупакованные станко-дни | `1e6` | #4469 |
| 5 | минуты переналадки | 1 мин = 1 | — |

Нарушение, которое **уже есть в хранимом плане**, кандидату не вменяется (`capacityBreaksStored`,
`:12112`): иначе план, однажды попавший за потолок, запирался бы навсегда (#4622).

Штрафы размещения (срок 200, фольга не в конце дня 80, переналадка 30–35 и 15, соседство заказа 12)
живут отдельно — ТЗ §8.2/§11. Они вправе проигрывать друг другу, и в реестр §15 не входят.

### 4.2. Между правилами: ранг зависит от входа

| пара правил | автоматика по набору | ручное действие | пересчёт чисел |
|---|---|---|---|
| потолок дня × 🔒 | **🔒 сильнее**: день уходит за потолок вместе с 🔒, перебор законен (#4512) | **потолок сильнее**: 🔒 из хвоста уезжает и рвётся, оператору сказано (#4728, #4736) | потолок сильнее — выравнивание несёт `manualShift` (#4736) |
| заморозка × потолок дня | **заморозка сильнее**: в замороженный день ничего не кладётся (#4497) | **потолок сильнее**: задание берёт, сколько в дне есть, остаток уезжает продолжением (#4494) | ручной пересчёт дни своего действия размораживает (#4582) |
| заморозка × команда | заморозка сильнее (#4436) | **команда сильнее** (#4569); исключение — §4.3 | ручной вызов — сильнее (#4582/#4588), автоматический — слабее |
| просрочка × заморозка | **заморозка сильнее**: задание уезжает на ближайший доступный день и помечается просроченным (#4338 → #4347 → #4436) | то же | — |
| просрочка × 🔒 | **🔒 сильнее**: замок дня абсолютен, просроченная 🔒 остаётся на своём дне (#4434 п.1) | ручное действие двигает 🔒 само (#4736) | — |
| потолок × недобор дня | **одно правило**: перебор и недобор — один долг плана, выравнивание работает в обе стороны (#4743, #4751) | то же | то же |
| окно `[С; По]` × команда | окно — область размещения; за него переливают (#3974) | **команда сильнее**: не влезло — двигаем за окно (решение 05.08.2026) | то же |
| отработанный день × любое правило | **факт сильнее**: перебор от сделанной работы нарушением не считается, день не добивают (#4740) | то же | то же |
| обеспечение × запись | `SUPPLY_CONSERVED` с храповиком: недостача, созданная записью, снимает операции цепочек целиком (#4751) | то же (`actor: 'any'`) | то же |

Единственное, что снимает замок 🔒 у автоматики, — **физически нерабочий день**: окно смены целиком
накрыто выходным, праздником или «Отпуском» (`dayFullyBlocked`). Вердикт ставит упаковщик
(`ops.fixedDayLost`), страж его не пересчитывает (`isFixedReleasedCut`, `:10611`).

### 4.3. Единственный отказ ручному действию

Замороженный день **впереди** останавливает действие целиком: удаление, перетаскивание, перенос 🗓 и
«Урегулировать» двигают весь хвост очереди, а сдвиг, упершийся в замороженный день, встал бы на нём
— вышел бы половинчатый результат «тут сдвинули, а там не смогли». Проверка одна на четыре
обработчика и стои́т ДО первой записи: `manualShiftRefused` (`20-controller.js:10138`), зовётся через
`refuseManualShift`. Оператору называются дни (#4736).

Отказы по существу самого задания живут в обработчиках: начатое не переносится, не переставляется и
не удаляется (#4381); 🔒-звено цепочки не удаляется без снятия фиксации (`:5403`); перенос на станок,
у которого в целевой день отпуск, не выполняется (`:4387`).

## 5. Сколько расчётов плана даёт одно нажатие

Одно нажатие может дать **две** раскладки разными стратегиями — фаза записи и фаза выравнивания.
Это корень серии «опять задание не там» (#4770):

| действие | фаза 1 | фаза 2 |
|---|---|---|
| ⏩ `recalcFromCut` | планирования нет: колонки и старты встык | `levelOverfilledAfterWrite` — **единственная** раскладка |
| ↻ `recalcSetupTiming` | то же | `levelOverfilledAfterWrite` |
| «Урегулировать» | переносы + разделение + `reconcilePlanStarts` (детерминированно, #4726) | `levelOverfilledAfterWrite` |
| 🗓 перенос | `autoSequenceQueue(SETUP, preserveOrder=false)` — пересборка **по срокам** | `levelDayLoad` → `autoSequenceQueueAfterMerge(SETUP, preserveOrder=true, trainOnly)` — **паровоз** |
| удаление | `autoSequenceQueue(SETUP, preserveOrder=true)` — паровоз | то же выравнивание |
| «Сгенерировать» / «Упорядочить» | пересборка по стратегии | то же выравнивание |

Стратегии двух фаз разные: первая вправе менять порядок ради сроков, вторая объявляет порядок
авторитетным и возит работу паровозом. На одной очереди они дают разные ответы, поэтому контекст
между ними приходится передавать явно — полями из §2. Предел проходов выравнивания на одно нажатие —
`LEVEL_MAX_PASSES = 3` (`:10999`), и долг плана обязан строго убывать (#4751).

## 6. Как пополнять

1. Новое правило — сперва в ТЗ §15 и в реестр `05-invariants.js` с объявленным `mode`, затем строка
   в §3 этого документа (иначе `atex-pp-4734-rule-matrix.test.js` покраснеет).
2. Новое действие или новое поле прав — строка в §2 со ссылкой `file:line`.
3. Конфликт двух правил, разрешённый заказчиком, — строка в §4.2 с обеими сторонами и входом.
   Ранг записывается тройкой (правило A, правило B, вход): лестницей он не выражается (#4728).
4. Перед правкой поведения — сверяться с
   [`atex_production_planning_algorithm.md`](atex_production_planning_algorithm.md) и обновлять его
   в том же PR.

## 7. Расхождения, найденные при сборке матрицы (17.08.2026)

- **↑↓ и перетаскивание внутри дня получают разные права.** Перетаскивание
  (`reorderCutInDay:11155`) считает точку сдвига и несёт её в выравнивание — `manualShiftFrom`
  (`:11187`) и `recalcSetupTiming(sid, {auto: true, manualShift: dragShift})` (`:11204`). ↑↓
  (`moveCutInDay:8518`) зовёт тот же пересчёт без неё (`:8572`) и точку сдвига не считает вовсе.
  Обе перестановки
  меняют переналадку соседей, то есть длину дня; у ↑↓ выравнивание упрётся в 🔒 (#4736) и
  замороженный день впереди отказа не даст. Заведено отдельным тикетом.
