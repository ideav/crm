# Эталонная база `cm` — шаблон «Сопоставление каталогов»

## На пальцах

Шаблон базы в Интеграме — это **таблица MySQL**, из которой ядро клонирует базу пользователя.
Партнёр выбирает «Сопоставление каталогов» в Личном кабинете при создании базы, и за один шаг
получает схему, отчёты, роли, гранты, меню, настройки и файлы рабочих мест. В конструктор базы
заходить не нужно, установщик запускать не нужно.

Работает это так (`index.php`, `newDb()`):

```sql
CREATE TABLE <база> LIKE cm;
INSERT INTO <база> SELECT * FROM cm;
```
```
cp -r templates/custom/cm templates/custom/<база>
cp -r download/cm         download/<база>
```

После клонирования ядро заводит в новой базе одного пользователя — того, кто нажал «Создать», —
с ролью администратора. Всё остальное приезжает из `cm` как есть.

Имя `cm` занять нельзя: маска пользовательских баз требует 3–15 символов (`USER_DB_MASK`,
`index.php`), поэтому двухбуквенные имена остаются за шаблонами — как `ru`, `en`, `fu`.

## Что должно быть в `cm`

| Что | Почему |
|---|---|
| Типы и реквизиты всех таблиц шаблона | Схема сопоставления; без неё отчёты не собираются |
| Отчёты, их колонки, связи FROM, формулы, сортировки, лимиты | `mass_match`, `Сопоставление`, `matching_export`, запросы токенизации |
| Справочник «Функция» | Формулы колонок отчётов ссылаются на функции по id |
| Роли «Партнёр» и «Оператор каталогов» с грантами | Гранты выданы **только** на таблицы шаблона |
| Пункты меню обеих ролей | Рабочие места должны открываться сразу |
| Запись «Настройка сопоставления» со значениями по умолчанию | Стартовый конфиг: пресет, веса, обязательные атрибуты, серая зона |
| Запись «Настройка» (269), если шаблон читает из неё флаги | Иначе рабочие места стартуют с пустым конфигом |

## Чего в `cm` быть не должно

| Что | Что случится, если оставить |
|---|---|
| Записи «Пользователь» | Учётка вместе с **токеном, xsrf и хэшем пароля** уедет в базу каждого клиента, и токен будет в них действующим |
| Записи SKU, RFP, Токен, Бренд | Номенклатура и заявки чужого клиента в базе нового |
| Записи «Решение по паре», «Журнал развёртывания» | Чужая история решений подменяет собой обучение на данных клиента |
| Записи «Профиль загрузки» | Профили привязаны к колонкам чужих файлов |

Первая строка — не гигиена, а утечка доступа: `newDb()` копирует таблицу целиком, включая
реквизиты `Token` (125), `xsrf` (40), `Пароль` (20) и `Secret` (130).

## Операции

### 1. Собрать шаблон из рабочей базы

Копирование и вычистка — `docs/scripts/prepare_cm_template.sql`. Скрипт правится сверху: имя
базы-источника и список таблиц с данными. Порядок работы:

```bash
mysql -u <user> -p <schema> < docs/scripts/prepare_cm_template.sql
```

Прогнать скрипт вхолостую, не трогая боевую схему, можно на стенде: рядом лежит
`docs/scripts/prepare_cm_template.stand.sql` — синтетическая база с пользователями, токенами,
данными, ролями, меню, отчётом и поддеревом в три уровня.

Скрипт пересоздаёт таблицу `cm`, копирует в неё базу-источник, удаляет записи перечисленных
таблиц вместе с подчинёнными строками и всех пользователей, а в конце печатает две сводки:
сколько записей осталось по каждой таблице и сколько осталось строк с секретами. Вторая сводка
обязана быть нулевой.

### 2. Выложить файлы рабочих мест

У шаблона свой комплект файлов в репозитории — `templates/cm/` и `download/cm/{css,js}/`. Он едет
на сервер через `update.conf`:

```
templates/cm/*     → templates/custom/cm/
download/cm/css/*  → download/cm/css/
download/cm/js/*   → download/cm/js/
```

Каталоги `templates/custom/cm` и `download/cm` на сервере — источник для `cp -r` при создании
базы: их содержимое ложится в каталоги, одноимённые с новой базой. Пока их нет, база создастся,
но рабочие места откроются без JS и CSS.

Шаблон развивается сам по себе: `templates/xcom/` и `download/xcom/` — проект конкретного клиента,
и правка в нём не попадает в шаблон. Версия шаблона — `templates/cm/manifest.json`.

### 3. Включить шаблон на сервере

Список разрешённых шаблонов — `TEMPLATES` (`include/connection.php`), значение по умолчанию
`:en:ru:fu:cm:`. На сервере он перекрывается переменной окружения:

```
INTEGRAM_TEMPLATES=:en:ru:fu:cm:
```

Имя, которого нет в списке, ядро молча заменяет на `ru`.

### 4. Проверить

1. В ЛК создать базу с шаблоном «Сопоставление каталогов».
2. Открыть её: меню обеих ролей на месте, рабочие места открываются со стилями.
3. Открыть `report/<id отчёта>?JSON_KV` для `mass_match` — отчёт исполняется, а не отвечает
   «Невозможно связать колонки отчета».
4. `SELECT COUNT(*) FROM <новая база> WHERE t=18` — ровно один пользователь, тот, кто создал базу.

### 5. Выпустить новую версию шаблона

Шаблон — данные, а не код: правки в уже созданных базах клиентов не появляются. Новая версия
делается так же, с нуля: рабочая база приводится в порядок, `prepare_cm_template.sql` пересобирает
`cm`, версия отмечается в `templates/cm/manifest.json`. Базы, созданные раньше, остаются на
своей версии.

## Грабли

**Шаблон выбран, а база обычная русская.** Имя шаблона не прошло проверку `TEMPLATES` — ядро
подставляет `ru` без сообщения (`index.php`, `newDb()`). Проверить `INTEGRAM_TEMPLATES` на сервере;
в базе выбранный шаблон записан в реквизит «Шаблон» (283) карточки базы в ЛК.

**Рабочие места открываются без стилей и скриптов.** Нет каталогов `templates/custom/cm` или
`download/cm` — копировать было нечего. Проверяется запросом конечного URL:
`https://ideav.ru/download/<новая база>/js/xcom-match.js` должен отдавать 200, а не 302.

**«Шаблон «cm» не установлен на этом сервере».** Шаблон разрешён списком `TEMPLATES`, но таблицы
`cm` в схеме нет — эталонная база не собрана, см. шаг 1.
