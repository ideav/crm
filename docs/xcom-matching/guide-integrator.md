# Гайд внедренца: «Сопоставление каталогов»

## На пальцах

Шаблон превращает два Excel-каталога в воспроизводимый процесс: партнёр один раз устанавливает схему, проходит мастер, проверяет предложенные колонки и правила категории, затем отдаёт оператору рабочие места «Массовый подбор», «Ручное сопоставление» и «Выгрузка».

Целевой результат первого разворачивания: от двух файлов клиента до первого массового прогона не более 60 минут. Это стартовый норматив пилота; перед первым наблюдением его нужно подтвердить в протоколе. Время показывает сам мастер.

Партнёру не нужно редактировать SQL или запросы. Категорийная специфика хранится в строке `config` таблицы «Настройка сопоставления».

## Операции

### 1. Предварительная проверка

Сценарий подходит, если в обоих каталогах есть текстовое наименование и хотя бы один устойчивый идентификатор или атрибут: артикул, бренд, модель, тип, размер. Названия колонок могут различаться.

Сценарий не подходит как шаблонный, если:

- позиции описаны только кодами, чертежами или изображениями;
- одна строка файла означает комплект из нескольких независимых товаров;
- соответствие зависит от внешней инженерной модели, которой нет в файлах;
- требуется изменить бизнес-процесс клиента, а не только сопоставить позиции;
- результат нельзя объяснить через токены, обязательные атрибуты и зафиксированное ручное решение.

В этих случаях остановите разворачивание и оформите отдельный кастомный проект.

### 2. Установка

Из корня репозитория сначала выполните безопасную проверку плана:

```powershell
pwsh -File .\docs\create_xcom_matching.ps1 -DbName clientdb -DryRun
```

План должен закончиться строкой `Готово` и перечислить:

- таблицы `SKU`, `RFP`, `Токен`, `Токен SKU`, `Токен RFP`;
- `Настройка сопоставления`, `Решение по паре`, `Журнал развёртывания`;
- отчёты `mass_match`, `Сопоставление`, `matching_export`;
- роли `Партнёр`, `Оператор каталогов`;
- рабочие места `wizard`, `settings`, `matching`, `mass_match`, `export`.

После проверки запустите установку с токеном администратора базы:

```powershell
$env:INTEGRAM_TOKEN = '<токен>'
pwsh -File .\docs\create_xcom_matching.ps1 -DbName clientdb
```

Повторный запуск допустим: установщик ищет существующие таблицы, отчёты, роли, гранты, меню и сид конфига. Перед обновлением проверьте `templates/xcom/manifest.json`; версия меняется по Semantic Versioning. Обновление уже развёрнутой базы выполняется тем же идемпотентным установщиком.

### 3. Мастер первого разворачивания

Откройте `/{база}/wizard`.

1. Выберите каталог клиента RFP и собственный каталог SKU. Файлы разбираются в браузере. Проверьте лист, число строк, число колонок и строку заголовка.
2. Проверьте предложенные роли колонок. `Наименование` обязательно для обеих сторон. Артикул, бренд, модель, тип и размер можно исправить или отключить.
3. Укажите категорию. При необходимости выберите стартовый отраслевой пресет. Пресет является отправной точкой, а не готовым решением для любых данных.
4. Проверьте обязательные атрибуты и веса, подтвердите настройку, сохраните профиль.

Мастер сохраняет две строки:

- `config`: действующие правила сопоставления;
- `wizard_profile`: имена файлов, листы, объёмы, маппинг колонок и длительность настройки.

Дополнительно мастер создаёт две совместимые с системным рабочим местом загрузки настройки — «Сопоставление RFP — {категория}» и «Сопоставление SKU — {категория}» — и пишет проверяемую карту колонок в таблицу «Профиль загрузки». После сохранения эта карта открывается прямо в мастере через IntegramTable.

### 4. Что означает конфиг

| Ключ | Смысл | Как диагностировать |
|---|---|---|
| `schema_version` | Версия формата конфига | Не уменьшать вручную |
| `category` | Человекочитаемая категория клиента | Нужна для журнала и пилота |
| `preset` | Исходный отраслевой профиль | Пусто означает ручную настройку |
| `column_mapping` | Роли исходных Excel-колонок отдельно для RFP и SKU | Неверное наименование ломает токенизацию |
| `tma_weight` | Доля точного совпадения артикула в базовой оценке, от 0 до 1 | Слишком высокий вес переоценивает одинаковые коды |
| `required_attributes` | Жёсткий гейт: обе стороны заполнены и различаются, значит пара отбрасывается | Добавляйте только устойчивые атрибуты |
| `attribute_weights` | Мягкие бонусы совпавшим атрибутам | Вес не отбрасывает пару, только повышает оценку |
| `llm.enabled` | Разрешено ли доуточнение серой зоны ИИ | Без ИИ ручное место продолжает работать |
| `llm.gray_zone_min/max` | Диапазон оценки для отправки короткого списка ИИ | Слишком широкий диапазон увеличивает стоимость и шум |
| `decision_log` | Таблица решений, защищающая ручной выбор от повторного прогона | Не отключать на регулярных загрузках |

### 5. Как считается оценка

Базовая оценка состоит из двух частей:

1. текстовое покрытие: длина совпавших токенов относительно средней длины двух наименований;
2. точное совпадение артикула, его долю задаёт `tma_weight`.

После базовой оценки совпавшие мягкие атрибуты закрывают заданную долю оставшегося до 100 разрыва. Обязательный атрибут не является весом: явное несовпадение отбрасывает пару до скоринга.

Пример: базовая оценка 70, совпал атрибут с весом 0,2. Итог: `70 + (100 - 70) × 0,2 = 76`.

### 6. Первый прогон

1. Загрузите данные сохранённой настройкой.
2. Убедитесь, что обе стороны токенизированы в общий справочник.
3. Откройте «Массовый подбор», оставьте автоматическое число потоков и нажмите «Старт».
4. Проверьте статистику: обработано, с подбором, без подбора, ошибки, строк в минуту.
5. В «Ручном сопоставлении» примите или отклоните несколько спорных пар.
6. Повторите подбор на тех же строках. Принятые решения должны сохраниться, отклонённые кандидаты не должны предлагаться снова.
7. Откройте «Выгрузка результата» и скачайте Excel. Скопируйте JSON API из раскрывающегося блока.

### 7. Диагностика плохого качества

| Симптом | Вероятная причина | Действие |
|---|---|---|
| Почти нет кандидатов | Слишком жёсткий обязательный атрибут | Временно снимите обязательность и сравните выборку |
| Много товаров чужого типа | Тип не сопоставлен или задан только мягким весом | Проверьте маппинг и сделайте тип обязательным |
| Единицы измерения создают шум | `10 мм`, `10mm`, `10х1` токенизируются по-разному | Нормализуйте единицы при загрузке или выделите размер отдельной колонкой |
| Частые слова поднимают нерелевантные пары | Не хватает веса редких атрибутов | Добавьте бренд, модель, размер; не увеличивайте число потоков |
| Одинаковый артикул даёт ложное совпадение | `tma_weight` слишком велик или код не уникален | Уменьшите вес и добавьте обязательный атрибут |
| ИИ-кнопка недоступна | ИИ выключен или в серой зоне нет строк | Проверьте `llm.enabled` и пороги |
| ИИ вернул ошибку | Не настроен серверный агент или истекла оплата | Продолжайте ручную проверку; основной цикл не зависит от ИИ |
| После повторного прогона вернулся отклонённый SKU | Нет таблицы решений, гранта или RFP/SKU ID | Проверьте инсталлятор, metadata и права роли |
| Экспорт пуст | `matching_export` не имеет строк или нет гранта | Сверьте RFP напрямую и права на отчёт |

### 8. Поддержка и граница ответственности

Партнёр решает самостоятельно по этому гайду:

- выбор листов и колонок;
- настройку обязательных атрибутов, весов и порогов;
- нормализацию единиц и названий в исходном файле;
- повторный запуск установщика той же версии;
- объяснение оценки и ручных решений клиенту.

Эскалируйте как дефект шаблона, если воспроизводится одно из условий:

- DryRun проходит, а полный установщик падает на поддерживаемой чистой базе;
- валидный конфиг не применяется;
- ручное решение из журнала изменяется повторным прогоном;
- Excel и JSON расходятся на одной версии отчёта;
- основной экран ломается при отключённом ИИ.

Эскалируйте как кастомный проект, если нужна новая сущность данных, новый внешний источник, неописанная логика соответствия или изменение рабочего процесса клиента.

Общее правило границы: **решается данными — это шаблон; требует правки кода или схемы — это кастомный проект.** Развёрнутый чек-лист признаков — `docs/partner-template-4816-decisions.md`, Решение 4.

Эскалация принимается только как issue и только с полным набором:

- версия шаблона из `templates/xcom/manifest.json`;
- конфиг базы (таблица «Настройка сопоставления» или выгрузка JSON);
- какие шаги этого гайда уже пройдены, с результатом;
- обезличенный образец данных, на котором воспроизводится.

Без этого набора запрос возвращается на первую линию.

Экономика внедрения: партнёр назначает клиенту свою цену за внедрение и получает скидку 30% от публичной цены облачного тарифа — разница остаётся ему постоянной маржой на всё время подписки клиента. Условия фиксируются в соглашении до начала работ; шаблон не должен скрывать этот вопрос за техническим запуском. Модель описана в `docs/partner-template-4816-decisions.md`, Решение 1.

Обновление до новой версии шаблона — повторный прогон установщика новой версии на той же базе: он идемпотентен, конфиг базы не перетирается. Автообновления нет, следите за releases репозитория. Правила версий — там же, Решение 3.

## Грабли

- Не выдавайте роли оператора WRITE на файловый менеджер. Это право загрузки исполняемых фронтенд-ассетов.
- Не используйте реальные клиентские файлы в тестах и репозитории.
- Не включайте ИИ до проверки токенного шорт-листа: модель уточняет кандидатов, а не заменяет первичный поиск.
- Не превращайте стартовый пресет в обещание отраслевой точности. После каждого пилота фиксируйте, какие правила реально понадобились.
- Не редактируйте отчёты для каждой категории. Если без этого нельзя, шаблон недопараметризован или сценарий уже кастомный.
