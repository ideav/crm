Каждая задача — отдельная сессия агента со старта T2 (эталон T1 и два договора). В прогон попадает общая часть, текст одной задачи и раздел своей среды.

## Общая часть

Фонд ведёт два приложения: «Заявки на финансирование» и «Договоры». Описание данных — в разделе среды ниже. Выполни одну задачу из раздела «Задача». Вопросов не задавай: отвечать некому. Права ролей и правила, которые уже настроены, не ослабляй. Свой код вне базы (сервисы, прокси, обёртки) не пиши.

Закончив, напиши «ГОТОВО» и ответ на вопрос или что изменено.

## Среда B — ядро ideav.ru

Оба приложения — в одной базе ядра ideav.ru. Таблицы: «Компания» (ИНН, лимит финансирования), «Заявка», «Статус заявки», «Договор» (номер; «Заявка» — ссылка на заявку; «Сумма»; «Дата»; «Статус договора»: «Проект» или «Подписан»). Роли: «Админ фонда», «Эксперт», «Заявитель alpha», «Заявитель beta», «Юрист». Отчёт (запрос) «Остаток лимита»: компания, лимит, одобрено, законтрактовано, остаток.

## Среда A′ — PostgreSQL + PostgREST

Оба приложения — в одной базе `app` PostgreSQL 16, API — PostgREST v12 (схема `api`). Таблицы: `api.company(id, name, inn, funding_limit)`, `api.application` (компания — `company_id`), `api.status`, `api.app_user(login, fio, role, company_id)`, `api.contract(number, application_id, amount, signed_on, status)`. Отчёт — представление `api.limit_balance(company, funding_limit, approved, contracted, remaining)`.

Пользователь API определяется JWT `{"role": <роль PostgreSQL>, "login": <логин>}`, роль для JWT — `api.app_user.role`: `fund_admin` (`admin_f`), `expert` (`expert1`), `applicant` (`alpha_user`, `beta_user`), `lawyer` (`lawyer1`), `anon` (`delta_user`, без прав).

Инструменты:
- `sql` — SQL в базу `app` от суперпользователя;
- `api` — запрос к PostgREST от имени любого пользователя (`as_user`). Запросы помечаются заголовком `X-Client: ai`, если не указано `ai: false`;
- `WebFetch` — документация PostgreSQL (www.postgresql.org/docs/16) и PostgREST (docs.postgrest.org/en/v12).

## Среда A″ — две системы

- **S1 «Заявки»** — база `app` PostgreSQL 16, API — PostgREST v12 (схема `api`). Таблицы: `api.application` (компания — `company_inn`), `api.status`, `api.app_user(login, fio, role, company_inn)`, `api.contract(number, application_id, amount, signed_on, status)`. Отчёт — представление `api.limit_balance(company, funding_limit, approved, contracted, remaining)`. Компании S1 читает из S2 через `postgres_fdw`: сервер `registry`, внешняя таблица `reg.counterparty`, представление `api.company`.
- **S2 «Реестр контрагентов»** — отдельная PostgreSQL + PostgREST другого поставщика. Компании — `api.counterparty(inn, legal_name, funding_limit)`. Источник данных о компаниях — S2. Ключ связи S1 и S2 — ИНН.
- Из базы S1 база S2 доступна по сети логином только на чтение: `{CRM_READER_DSN}`.

Пользователь API S1 определяется JWT `{"role": <роль PostgreSQL>, "login": <логин>}`, роль для JWT — `api.app_user.role`: `fund_admin` (`admin_f`), `expert` (`expert1`), `applicant` (`alpha_user`, `beta_user`), `lawyer` (`lawyer1`), `anon` (`delta_user`, без прав).

Инструменты:
- `sql` — SQL в базу `app` S1 от суперпользователя;
- `api` — запрос к PostgREST S1 от имени любого пользователя (`as_user`). Запросы помечаются заголовком `X-Client: ai`, если не указано `ai: false`;
- `crm_api` — запрос к PostgREST S2 от имени администратора реестра;
- `WebFetch` — документация PostgreSQL (www.postgresql.org/docs/16) и PostgREST (docs.postgrest.org/en/v12).

## Среда A″ (a3) — разнородные системы

- **S1 «Заявки»** — база `app` PostgreSQL 16, API — PostgREST v12 (схема `api`). Таблицы: `api.company(id, name, inn, funding_limit, ext_id)` — копия справочника S2, `ext_id` — `Ref_Key` компании в S2; `api.application` (компания — `company_id`), `api.status`, `api.app_user(login, fio, role, company_id)`, `api.contract(number, application_id, amount, signed_on, status)`. Отчёт — представление `api.limit_balance(company, funding_limit, approved, contracted, remaining)`. Связи с S2 в S1 нет.
- **S2 «Реестр контрагентов»** — учётная система с API в стиле OData 1С: справочник `Catalog_Контрагенты` (`Ref_Key`, `Description` — наименование, `ИНН`, `ЛимитФинансирования`). SQL-доступа к S2 нет. Справочник API выдаёт инструмент `reg_doc`.
- **Источник истины по компаниям — S2.** Изменение данных компании (название, ИНН, лимит, новая компания) вносится в S2, и копия в S1 должна с ним совпасть. Для этого есть программа синхронизации `sync.py`: она переносит компании из S2 в S1, сопоставляя их по `Ref_Key`. Раннер запускает её перед проверкой. Её можно прочитать (`sync_read`), запустить (`sync_run`), поправить (`sync_write`) или привести S1 в соответствие вручную. Переменные окружения `sync.py`: `S1_DSN`, `REG_URL`, `REG_USER`, `REG_PASSWORD`.

Пользователь API S1 определяется JWT `{"role": <роль PostgreSQL>, "login": <логин>}`, роль для JWT — `api.app_user.role`: `fund_admin` (`admin_f`), `expert` (`expert1`), `applicant` (`alpha_user`, `beta_user`), `lawyer` (`lawyer1`), `anon` (`delta_user`, без прав).

Инструменты:
- `sql` — SQL в базу `app` S1 от суперпользователя;
- `api` — запрос к PostgREST S1 от имени любого пользователя (`as_user`). Запросы помечаются заголовком `X-Client: ai`, если не указано `ai: false`;
- `reg_api` — запрос к API S2 от имени его администратора;
- `reg_doc` — справочник API S2;
- `sync_read`, `sync_write`, `sync_run` — прочитать, записать и запустить `sync.py`;
- `WebFetch` — документация PostgreSQL (www.postgresql.org/docs/16) и PostgREST (docs.postgrest.org/en/v12).
