## Что уже есть

Фонд ведёт приложение «Заявки на финансирование»:

- 3 компании: «ООО «Альфа»», «ООО «Бета»», «АО «Гамма»». У каждой ИНН и лимит финансирования (5, 3 и 8 млн);
- 14 заявок. Поля заявки: номер, компания, статус, сумма, выручка, описание проекта, эксперт, заключение эксперта. Статусы по порядку процесса: Черновик → Подана → На экспертизе → Одобрена или Отклонена. Одобрены 4 заявки, 1 отклонена;
- пользователи: `admin_f` — админ фонда, владелец приложения; `expert1` — эксперт; `alpha_user` и `beta_user` — заявители «Альфы» и «Беты»; `lawyer1` и `delta_user` — пока без прав.

Права ролей и правила процесса для заявок уже настроены. Не ослабляй их.

## Задача

Построй второе приложение «Договоры» поверх заявок.

1. **Сущность «Договор»:** номер (уникальный), заявка (ссылка на одобренную заявку), сумма, дата, статус договора — «Проект» или «Подписан». Имена объектов — как в разделе своей среды: по ним приложение проверяют.
2. **Роль «Юрист»** для `lawyer1`: создаёт и правит договоры, читает заявки и компании.
3. **Заявитель** видит договоры только своей компании, только на чтение.
4. **Отчёт «Остаток лимита»:** по каждой компании, у которой есть одобренные заявки, — компания, лимит, одобрено (сумма одобренных заявок), законтрактовано (сумма договоров компании в любом статусе), остаток = лимит − законтрактовано.
5. **Данные компаний не копировать:** если в источнике поменяли лимит или название компании, отчёт сразу показывает новое значение.

Схему заявок не переименовывай и не удаляй, добавлять можно. Свой код вне базы (сервисы, прокси, обёртки) не пиши.

Закончив, напиши «ГОТОВО» и коротко: что сделано и чем.

## Среда A″ — две системы

Заявки и договоры живут в S1, компании — в другой системе S2.

- **S1 «Заявки»** — база `app` PostgreSQL 16, API — PostgREST v12, публикуется схема `api`. Таблицы компаний в S1 нет: заявка и заявитель ссылаются на компанию по ИНН (`api.application.company_inn`, `api.app_user.company_inn`). Проверка лимита при одобрении заявки уже читает лимит из S2 через `postgres_fdw`: сервер `registry`, внешняя таблица `reg.counterparty`.
- **S2 «Реестр контрагентов»** — отдельная PostgreSQL + PostgREST другого поставщика. Компании — `api.counterparty(inn, legal_name, funding_limit)`. Источник данных о компаниях — S2.
- Из базы S1 база S2 доступна по сети логином только на чтение: `host=crm1055c-db port=5432 dbname=registry user=crm_reader password=0QkoByjfwnFHtlJwE9K60cds`.

Имена объектов в S1:
- таблица `api.contract(number, application_id, amount, signed_on, status)`, статус — текст «Проект» или «Подписан»;
- отчёт — представление `api.limit_balance(company, funding_limit, approved, contracted, remaining)`.

Пользователь API S1 определяется JWT `{"role": <роль PostgreSQL>, "login": <логин>}`, роль для JWT берётся из `api.app_user.role`. Роли PostgreSQL: `fund_admin`, `expert`, `applicant` (все заявители), `lawyer` (пока без прав), `anon` (без прав; она сейчас у `lawyer1` и `delta_user`).

Инструменты:
- `sql` — SQL в базу `app` S1 от суперпользователя;
- `api` — запрос к PostgREST S1 от имени любого пользователя (`as_user`). Запросы помечаются заголовком `X-Client: ai`, если не указано `ai: false`;
- `crm_api` — запрос к PostgREST S2 от имени администратора реестра;
- `WebFetch` — документация PostgreSQL (www.postgresql.org/docs/16) и PostgREST (docs.postgrest.org/en/v12).
