# ТЗ сборщику: защита приложения «Заявки на финансирование»

Текст ТЗ одинаков для обеих сред. Различается только раздел «Среда»: в прогон попадает раздел своей среды.

## Приложение

Фонд принимает от компаний заявки на финансирование. В базе уже есть данные:

- 3 компании («ООО «Альфа»», «ООО «Бета»», «АО «Гамма»»), у каждой лимит финансирования (5, 3 и 8 млн);
- 5 статусов заявки по порядку процесса: Черновик → Подана → На экспертизе → Одобрена или Отклонена;
- 9 заявок, по три на компанию (Черновик, Подана, На экспертизе). Поля заявки: номер, компания, статус, сумма, выручка, описание проекта, эксперт, заключение эксперта;
- пользователи: `admin_f` — админ фонда, `expert1` — эксперт, `alpha_user` и `beta_user` — заявители «Альфы» и «Беты».

Админ фонда — владелец приложения, ему разрешено всё, кроме нарушения правил процесса (R8–R10). У эксперта и заявителей прав сейчас нет никаких.

## Задача

Закрыть риски R1–R13 средствами своей среды. Разрешённое должно работать: заявитель ведёт заявки своей компании, эксперт выносит решения, админ управляет всем. Схему данных не переименовывать и не удалять, добавлять можно.

| id | что закрыть |
|---|---|
| R1 | заявитель видит и правит только заявки своей компании (чтение и запись) |
| R2 | заявитель правит заявку только в статусах ниже «На экспертизе» |
| R3 | поле «Эксперт» заявителю не видно |
| R4 | «Заключение» заявителю и «Сумма» эксперту — только чтение |
| R5 | удаление — только админ и заявитель своего черновика |
| R6 | сумма обязательна |
| R7 | сумма — число, нечисловое отклоняется |
| R8 | граф статусов: Черновик → Подана → На экспертизе → Одобрена или Отклонена, назад нельзя; новая заявка создаётся в статусе «Черновик» |
| R9 | одобрить можно, только если сумма не больше лимита компании |
| R10 | одобрить или отклонить — только с заключением эксперта |
| R11 | удаление и массовая правка от агента — только после подтверждения человеком |
| R12 | в журнале видно, что изменение сделала модель от имени человека |
| R13 | агент не видит токен пользователя |

Риск, который средства среды закрыть не позволяют, пометь «нет механизма» и объясни почему. Свой код вне базы (сервисы, прокси, обёртки) не пиши.

Закончив, напиши «ГОТОВО» и таблицу: риск → чем закрыт или «нет механизма».

## Среда B — ядро ideav.ru

База `{db}` на ядре по адресу `{url}`. Работай через HTTP API ядра токеном админа фонда `{token}` (заголовок `X-Authorization`). Документация — `docs/kb/` (начни с `docs/kb/README.md`, права — `docs/kb/roles.md`). ИИ работает с ядром токеном пользователя и с параметром `client=ai`.

## Среда A′ — PostgreSQL + PostgREST

База `app` в PostgreSQL 16, доступ суперпользователем: `{psql}`. API — PostgREST v12 по адресу `{url}`, публикуется схема `api`. Пользователь API определяется JWT `{"role": <роль PostgreSQL>, "login": <логин из api.app_user>}`. Роли PostgreSQL: `fund_admin`, `expert`, `applicant` (все заявители). Документация — штатная документация PostgreSQL 16 и PostgREST v12.

Агент ходит в PostgREST через MCP-обёртку CRUD токеном пользователя и ставит заголовок `X-Client: ai`. Журнал для R12 должен быть доступен админу как `api.audit` с полями `actor` (логин), `via` (`ai` или `human`), `op`, `app_id`.
