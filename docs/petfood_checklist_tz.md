# ТЗ: система ввода показателей контроля («Отчет Производства за смену», ПЕТФУД)

**Основание:** задача [#4703](https://github.com/ideav/crm/issues/4703).
**Платформа:** low-code **Интеграм** (таблицы БД + HTML/JS рабочие места, авторизация по токену).
**Исходные данные заказчика:** файл `01--_new (1).xlsx`, лист «Технология производства» — бумажный
чек-лист «Фасовка» ПЕТФУД (разбор — [Приложение А](#приложение-а-исходная-форма--модель)).
**Образец продукта:** кейс [«Мастерская по резке рулонов»](https://ideav.ru/blog/posts/keis-masterskaya-rezki-rulonov-perestala-teryat-zakazy/)
с заменой терминов: «Заказ» → **«Отчет»**, «Заказы на резку» → **«Отчеты за смену»**.
**Опорные документы платформы:** [`kb/schema.md`](kb/schema.md) (структура),
[`kb/roles.md`](kb/roles.md) (роли/меню/права), [`kb/queries.md`](kb/queries.md) (отчёты),
[`StructureRules.md`](StructureRules.md), [`UI_UX_GUIDELINES.md`](UI_UX_GUIDELINES.md).

---

## 1. Назначение, цели, границы

**1.1. Цель.** Перевести заполнение нескольких чек-листов (Производство продукта и Простои оборудования)
на производстве с бумаги и Excel в приложение.

**1.1.1. Цель.** 'Оператор по продукту' вносит только **значение показателя**, время фиксируется системой;
замесы добавляются по ходу смены в нужном количестве; руководитель видит отклонения и статистику сразу.

**1.1.2. Цель.** 'Оператор по оборудованию' вносит время начала простоя агрегата и время окончания
с причиной из списка; руководитель видит простои оборудования и статистику.

**1.2. Объекты автоматизации.**
- Контроль технологических параметров (температуры и времена по этапам от куттера до упаковки) при производстве кормов для животных.
- Учет простоев оборудования.

**1.3. Что решается.**
- Бумажный лист заполняется задним числом, время пишется по памяти → время недостоверно.
- Ширина листа ограничена 13 колонками замесов; при большем числе замесов заводится второй лист.
- Отклонение от нормы видно только при ручной вычитке → реакция приходит поздно.
- Сводных данных по процессу замесов нет: чтобы посчитать долю замесов с отклонением, листы перебирают руками.
- Сводных данных по простою оборудования нет: листы перебирают руками.

**1.4. Границы.** В объём входят: справочники, задания производства, замесы, замеры показателей,
простои, четыре роли, рабочие места и дашборд. **Не входят:** планирование производства, склад
сырья и готовой продукции, учёт брака и выхода продукции, ТОиР, расчёт себестоимости, интеграция
с 1С/MES, нативное мобильное приложение (рабочее место оператора — веб на планшете).

## 2. Термины

| Термин | Значение |
|---|---|
| **Задание производства** | Сменное задание на выпуск продукта в конкретной упаковке на конкретной линии. Аналог «Заказа» в кейсе-образце. |
| **Замес** | Партия массы, проходящая линию. Внутри задания их несколько; каждый замес контролируется отдельно (колонка бумажной формы). |
| **Показатель контроля** | Контролируемый параметр из графы «Наименование контролируемого показателя» (температура после куттера, температура перед фасовкой …). |
| **Замер** | Одна введённая температура по одному показателю одного замеса вместе со временем фиксации. |
| **Карта контроля** | Набор показателей, назначенный виду упаковки/продукту. Инструмент руководителя — «распределение показателей». |
| **Справочник** | Таблица с повторно используемыми значениями (`unique=1` на первой колонке). |
| **Ссылка (ref)** | Поле-указатель на запись другой таблицы. |
| **Подчинённая таблица (arr)** | Таблица, записи которой принадлежат родителю (`up=<id родителя>`). |
| **Рабочее место (РМ)** | HTML/JS-экран под конкретную роль. |

## 3. Роли

| Роль | Логин | Назначение |
|---|---|---|
| **Руководитель** | `director` | Дашборды, карты контроля (распределение показателей), нормы и допуски, справочники. |
| **Мастер** | `master` | Создаёт задания, назначает оператора, ведёт простои, закрывает смену, правит ошибочные замеры. |
| **Оператор** | `operator` | Вносит показания по назначенным заданиям, добавляет замесы, регистрирует простой. |
| **Администратор** | — | Системная роль (145): структура, пользователи, права. |

Сотрудники ведутся в системной таблице **«Пользователь» (18)**; отдельный справочник сотрудников
не заводится (требование задачи «Сотрудники — таблица пользователь»).

## 4. Требования к модели данных (ТД)

### 4.1. Состав таблиц

**ТД-1.** Система строится на 12 таблицах: шесть справочников, шаблон чек-листа из двух таблиц,
и четыре рабочие таблицы (задание → замес → замер, плюс простой).

```
Задание производства ──arr──► Замес ──arr──► Замер ──ref──► Показатель контроля
        │                                        
        ├──arr──► Простой ──ref──► Оборудование, Вид поломки
        ├──ref──► Вид упаковки, Оборудование, Статус задания, Пользователь (Оператор)
        └──ref──► Карта контроля ──arr──► Строка карты ──ref──► Показатель контроля
```

### 4.2. Справочники

**ТД-2. `Вид упаковки`** (SHORT, `unique=1`): `Код` (SHORT), `Порядок` (NUMBER).
Записи из шапки формы: `пауч`, `ламистер`, `дойпак`, `жб банка`.

**ТД-3. `Показатель контроля`** (SHORT, `unique=1` — наименование как в бумажной форме):
`Код` (SHORT, латиница — для отчётов), `Группа` (SHORT — этап: куттер, линия, фасовка),
`Тип замера` (**ref → Тип замера**), `Ед. изм.` (SHORT), `Норма мин` (SIGNED),
`Норма макс` (SIGNED), `Порядок` (NUMBER). Наполнение — [Приложение А](#приложение-а-исходная-форма--модель).

**ТД-3.1. Измеряемая величина — температура, единственная.** Все показатели контроля меряют
температуру в **°C** (решение заказчика от 11.08.2026). `Ед. изм.` у всех записей справочника —
`°C`; значение замера (`Замер.Значение`, `Замер.Значение окончания`) — температура.

**ТД-3.2. Единый диапазон значений: `Норма мин` = `+1`, `Норма макс` = `+100` °C.** Границы
проставляются всем записям справочника «Показатель контроля» при наполнении и действуют, пока
технолог не задаст более узкие допуски по этапам (п. 14.1). Пересмотр допусков выполняется
переопределением границ в строке карты контроля (ТД-9), правка справочника при этом не требуется.

**ТД-4. `Тип замера`** (SHORT, `unique=1`): `Код` (SHORT). Две записи:

| Наименование | Код | Что вводит оператор |
|---|---|---|
| Значение | `value` | одна температура; время ставится автоматически |
| Интервал | `interval` | два замера — «начало» и «окончание», у каждого своя температура и своё время; температура окончания необязательна |

**ТД-5. `Оборудование`** (SHORT, `unique=1`): `Код`, `Тип оборудования` (SHORT),
`Инвентарный номер` (SHORT), `В работе` (BOOLEAN). Линии и агрегаты: куттер, эмульситатор,
паровая линия, смеситель, фасовочный автомат.

**ТД-6. `Вид поломки`** (SHORT, `unique=1`): `Код`, `Плановая остановка` (BOOLEAN),
`Описание` (MEMO).

**ТД-7. `Статус задания`** (SHORT, `unique=1`): `Код` (SHORT), `Порядок` (NUMBER), `Цвет` (SHORT).
Три записи: `Новое` (`new`), `В работе` (`in_work`), `Выполнено` (`done`) — под пункты меню
раздела 6.

### 4.3. Шаблон чек-листа (распределение показателей)

**ТД-8. `Карта контроля`** (SHORT, `unique=1`): `Вид упаковки` (**ref**), `Продукт` (SHORT),
`Действует с` (DATE), `Активна` (BOOLEAN), `Строка карты` (**arr**).
Пример записи: `Фасовка ПЕТФУД — пауч`.

**ТД-9. `Строка карты`** (подчинена карте): первая колонка `Строка карты` (NUMBER, `unique=1` —
автонумерация), `Показатель контроля` (**ref**), `Порядок` (NUMBER), `Обязателен` (BOOLEAN),
`Норма мин` (SIGNED), `Норма макс` (SIGNED) — последние две переопределяют норму справочника для
этой карты; пустые означают «взять из справочника».

### 4.4. Рабочие таблицы

**ТД-10. `Задание производства`**: первая колонка (NUMBER, `unique=1`) — номер задания,
автонумерация платформой.

| Поле | Тип | Источник в бумажной форме |
|---|---|---|
| `Дата` | DATE | «Дата: ___ 2026» |
| `Смена` | SHORT | — (уточняется, п. 14.5) |
| `Продукт` | SHORT | «Сведения о продукте» |
| `Граммовка` | NUMBER | «граммовка» |
| `Дата на упаковке` | BOOLEAN | «Дата / без даты на упаковке» |
| `Вид упаковки` | **ref → Вид упаковки** | «Вид фасовки» |
| `Оборудование` | **ref → Оборудование** | линия |
| `Карта контроля` | **ref → Карта контроля** | набор строк формы |
| `Оператор` | **ref → Пользователь (18)** | — |
| `Мастер` | SHORT | — (см. ТД-14) |
| `Проверяющий` | SHORT | «Ф.И.О. проверяющего» |
| `Статус` | **ref → Статус задания** | — |
| `Начато` / `Завершено` | DATETIME | — |
| `Комментарии/проблемы/замечания` | MEMO | нижняя строка формы |
| `Замес` | **arr → Замес** | колонки H…T |
| `Простой` | **arr → Простой** | — |

**ТД-11. `Замес`** (подчинён заданию): первая колонка `Замес` (NUMBER) — порядковый номер внутри
задания; `Маркировка тележки` (SHORT — строка «Маркировка тележки с замесом»),
`Начат` (DATETIME), `Завершён` (DATETIME), `Комментарий` (MEMO), `Замер` (**arr**).
**Количество замесов не ограничено** — поле «количество замесов» бумажной формы (`=SUM(H6:Q6)`)
вычисляется как число записей «Замес» задания и руками не вводится.

**ТД-12. `Замер`** (подчинён замесу): первая колонка `Замер` (NUMBER, `unique=1` — автонумерация);
`Показатель контроля` (**ref**), `Значение` (SIGNED — температура, °C), `Время` (DATETIME),
`Значение окончания` (SIGNED — температура, °C), `Время окончания` (DATETIME),
`Оператор` (**ref → Пользователь**), `Комментарий` (SHORT). Пара «окончание» заполняется только
для показателей с типом `interval`.

**ТД-13. `Простой`** (подчинён заданию): первая колонка `Простой` (NUMBER, `unique=1`);
`Оборудование` (**ref**), `Вид поломки` (**ref**), `Начало` (DATETIME), `Окончание` (DATETIME),
`Комментарий` (MEMO). Длительность вычисляется отчётом.

### 4.5. Ограничения платформы, влияющие на схему

**ТД-14. Одна ссылка на одну таблицу в записи.** Ref-тип определяется целевой таблицей, а `_d_req`
идемпотентен по типу: второй `_d_req` на «Пользователь» вернёт уже существующий реквизит
([`kb/schema.md`](kb/schema.md), issue #4655). Поэтому «Мастер» и «Оператор» ссылками на
«Пользователя» одновременно не выражаются. Решение: **`Оператор` — ссылка** (нужна для маски
`[USER_ID]`, п. 6.2), **`Мастер` и `Проверяющий` — текстовые поля** с автоподстановкой ФИО
создателя задания. Если заказчику потребуется выбор мастера списком (п. 14.2) — заводится
отдельный справочник «Мастер» и ссылка на него.

**ТД-15. Признак отклонения не хранится.** «Вне нормы» вычисляется при чтении (в отчёте и в
рабочем месте) сравнением `Значение` с границами карты/справочника. Хранимая копия разошлась бы
с нормами после их пересмотра.

**ТД-16. Самопроверка схемы.** После создания структуры обязательна проверка `metadata?JSON=1`:
- `Задание производства.Замес`, `Задание производства.Простой`, `Замес.Замер`,
  `Карта контроля.Строка карты` — имеют `arr_id` и **не имеют** `ref`;
- `Задание.Вид упаковки`, `Задание.Оборудование`, `Задание.Карта контроля`, `Задание.Оператор`,
  `Задание.Статус`, `Замер.Показатель контроля`, `Простой.Оборудование`, `Простой.Вид поломки` —
  имеют `ref` и `ref_id`;
- появление `Вид упаковки`, `Показатель контроля`, `Оборудование`, `Вид поломки` как `arr_id` —
  **дефект**: справочник ошибочно сделан подчинённой таблицей.

## 5. Функциональные требования (ФТ)

### 5.1. Руководитель

**ФТ-1.** Ведение справочников: виды упаковки, показатели контроля с единицами измерения и
нормами, оборудование, виды поломок.
**ФТ-2.** Создание карты контроля: выбор вида упаковки/продукта, добавление показателей,
порядок строк, признак «обязателен», переопределение норм.
**ФТ-3.** Копирование карты контроля как основы для новой (кнопка «Дублировать»).
**ФТ-4.** Дашборд: показатели раздела 8.
**ФТ-5.** Просмотр любого задания со всеми замерами и историей правок.

### 5.2. Мастер

**ФТ-6.** Создание задания: дата, смена, продукт, вид упаковки, граммовка, признак даты на
упаковке, линия, карта контроля, оператор. Карта контроля подставляется по виду упаковки
и остаётся доступной для замены вручную.
**ФТ-7.** Назначение и смена оператора у задания.
**ФТ-8.** Списки заданий по статусам (раздел 6.3) с сортировкой по дате и смене.
**ФТ-9.** Регистрация простоя: оборудование, вид поломки, время начала и окончания, комментарий.
**ФТ-10.** Правка ошибочного замера (значение, время) с сохранением исходных значений в журнале
правок и указанием автора правки (НФТ-5).
**ФТ-11.** Закрытие задания: статус `Выполнено`, штамп `Завершено`. При незаполненных обязательных
показателях — предупреждение со списком пропусков и подтверждение.

### 5.3. Оператор

**ФТ-12.** Список назначенных ему заданий; чужие задания скрыты маской (п. 6.2).
**ФТ-13.** Взятие задания в работу: статус `Новое` → `В работе`, штамп `Начато`.
**ФТ-14.** Добавление замеса кнопкой «+ Замес»: номер присваивается по порядку, вводится
маркировка тележки, ставится штамп `Начат`. Число замесов не ограничено.
**ФТ-15.** Ввод значения показателя: одна температура в одно поле, °C. **Время замера
проставляется системой** в момент сохранения (НФТ-3) и оператору для ввода не предлагается.
**ФТ-16.** Для показателя типа `interval` — две кнопки: «Начало» и «Окончание»; каждая фиксирует
своё время, температура при необходимости вводится к каждой из них.
**ФТ-17.** Значение за пределами нормы (`+1…+100` °C по ТД-3.2, либо более узкие границы карты
контроля): строка подсвечивается, запрашивается комментарий, сохранение выполняется (запрет на
ввод не ставится — факт важнее удобства).
**ФТ-17.1.** Значение за пределами диапазона `+1…+100` °C дополнительно проверяется как описка:
показывается сообщение «проверьте значение» с исходным вводом, сохранение проходит по
подтверждению оператора и помечается комментарием.
**ФТ-18.** Счётчик заполнения по текущему замесу и по заданию («Заполнено 7 из 11»).
**ФТ-19.** Регистрация простоя (тот же состав, что у мастера, ФТ-9).
**ФТ-20.** Комментарий к замесу и к заданию (нижняя строка бумажной формы).
**ФТ-21.** Завершение задания оператором с теми же проверками, что в ФТ-11.

### 5.4. Общие

**ФТ-22.** Каждый замер сохраняется отдельным запросом сразу после ввода; общей кнопки
«Сохранить всё» на экране ввода нет.
**ФТ-23.** Все списки заданий поддерживают фильтр по дате, смене, линии, оператору, виду упаковки.
**ФТ-24.** Выгрузка заполненного чек-листа задания в файл в раскладке бумажной формы
(строки — показатели, колонки — замесы) — при подтверждении п. 14.3.

## 6. Роли, права, меню

### 6.1. Гранты (таблица «Объекты» 116, уровни 53=READ, 54=WRITE)

| Роль | WRITE | READ |
|---|---|---|
| Руководитель | все справочники, `Карта контроля`, `Строка карты` | `Задание производства`, `Замес`, `Замер`, `Простой`, отчёты |
| Мастер | `Задание производства`, `Замес`, `Замер`, `Простой` | справочники, карты контроля, отчёты |
| Оператор | `Замес`, `Замер`, `Простой`, `Задание производства` (маска, п. 6.2) | `Показатель контроля`, `Тип замера`, `Карта контроля`, `Строка карты`, `Вид упаковки`, `Оборудование`, `Вид поломки`, `Статус задания`, отчёты |

│ Задание №128 · пауч · 85 г · Линия 2    [▾]  │  ← шапка, сворачивается в одну строку

**ФТ-28.** Строка показателя содержит: наименование, норму (`+1…+100` °C или границы карты),

## 9. Нефункциональные требования (НФТ)

**НФТ-1. Единая модель данных.** Все экраны работают с одной схемой; копий таблиц под экран нет.
**НФТ-2. Без хардкода идентификаторов.** Id таблиц и реквизитов запрашиваются из `metadata`.
**НФТ-3. Время — серверное.** Штамп замера берётся от сервера (смещение вычисляется по заголовку
`Date` ответа API и пересчитывается перед каждым сохранением). Часы планшета на достоверность
чек-листа не влияют.
**НФТ-4. Устойчивость к обрыву связи.** Неотправленные замеры складываются в очередь в
`localStorage` и досылаются при восстановлении сети; введённое значение не теряется при
перезагрузке страницы.
**НФТ-5. Аудит.** Правка и удаление замера сохраняют исходное значение, исходное время, автора и
время правки. Заполненный чек-лист — документ качества, поэтому история изменений обязательна.
**НФТ-6. Планшет.** Портретная ориентация 10", целевые элементы ≥ 44 px, контрастная подсветка
отклонений, читаемость при заводском освещении.
**НФТ-7. Кэш ассетов.** Ссылки на `.js`/`.css` рабочих мест несут версию `?{_global_.version}`;
при правке скрипта версия поднимается, иначе изменение не доедет до планшета.
**НФТ-8. Производительность.** Открытие задания с 30 замесами и 11 показателями (330 замеров) —
за одно обращение к `pf_measurements`, без запроса на каждый замес.
**НФТ-9. Язык интерфейса** — русский; наименования показателей совпадают с бумажной формой
дословно, чтобы оператор находил строку глазами.

## 12. Критерии приёмки

- Ввод одного показателя — **температура и подтверждение**; время оператор не вводит ни разу за

  количестве.

- Дашборд собирается из отчётов, ручного сведения нет.
- Сквозной сценарий раздела 11 проходит целиком.

Строки «время» бумажной формы отдельными показателями не заводятся: время фиксируется вместе со
значением (ФТ-15). У показателей 3 и 4 замер типа `interval` держит пару «начало/окончание»:
у показателя 4 температура вводится к обоим замерам, у показателя 3 — к началу, окончание несёт
только время.
