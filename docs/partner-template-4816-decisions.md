# Решения по §7 ТЗ «Партнёрский шаблон „Сопоставление каталогов"»

**Задача:** #4816 (обещан в плане разбивки: «Трек §7 … оформлю черновиком на утверждение»).
**Статус: утверждено автором 11.09.2026, включая все параметры.** Документ — источник правды для гайдов и one-pager.
**Зачем до пилота:** ТЗ §7 — «требуют решения ДО начала работ». Программная часть шаблона закрыта (issue #4817–#4822, #4825), но без п.1–4 рычаг не сработает: нет экономики — партнёр не разворачивает, нет границы ответственности — всё равно пишет автору. Решения 2 и 4 нужны к пилоту #4823: наблюдатель должен знать, что считать эскалацией.

## Решение 1. Экономика для партнёра

**Вопрос:** как партнёр зарабатывает — фикс за внедрение, доля от лицензии клиента, наценка на облачный тариф?

| Вариант | За | Против |
| --- | --- | --- |
| A. Фикс за внедрение (партнёр сам называет цену клиенту) | Проще всего стартовать; не требует биллинга и учёта | Автору достаётся только тариф платформы; партнёру выгоднее «кастом за дорого», чем быстрый шаблон |
| B. Наценка на облачный тариф (партнёрская цена ниже публичной, маржа — партнёру, recurring) | Стимул разворачивать много и быстро; выравнивает интерес автора и партнёра; учёт уже есть на стороне тарифов | Нужна партнёрская цена/скидка в тарифах; маржа с одного клиента мала — работает на объёме |
| C. Доля от лицензии клиента | Привычно интеграторам | У платформы подписная модель, «лицензии» как сущности нет — надо изобретать |

**Утверждено 11.09.2026: A + B, партнёрская скидка — 30%.** Внедрение партнёр монетизирует фиксом сам (в его цену входит его же время по нормативу 60 минут из `pilot-protocol.md` — это и есть аргумент продажи). На облачный тариф партнёр получает **скидку 30% от публичной цены**; разница между публичной ценой и партнёрской остаётся партнёру как постоянная маржа на всё время подписки клиента. Вариант C не берём.

## Решение 2. Поддержка второй линии

**Вопрос:** кто чинит шаблон на нетиповых данных партнёра — партнёр по гайду или эскалация к автору?

**Утверждено 11.09.2026: трёхуровневая схема, привязанная к уже существующим артефактам.**

1. **Первая линия — партнёр**, строго по `docs/xcom-matching/guide-integrator.md` (разделы «Диагностика плохого качества», «Грабли»). Всё, что лечится правкой конфига/пресета, — зона партнёра, к автору не уходит.
2. **Вторая линия — автор, только через issue** с обязательным минимумом: версия из `templates/xcom/manifest.json`, конфиг базы, шаги из гайда, которые уже пройдены, обезличенный образец данных. Без этого набора issue возвращается на первую линию.
3. **Критерий границы** — Решение 4 (ниже): если случай в списке «шаблон», чинится в репо и докатывается всем (Решение 3); если «кастом» — отдельный проект за отдельные деньги.

«Без личного участия автора» честно трактуется как «без участия в типовых случаях»: полного нуля эскалаций не обещаем, а меряем её метрикой рычага из #4823 (число разворачиваний без единого тикета к автору).

## Решение 3. Версионирование шаблона

**Вопрос:** как улучшения докатываются до уже развёрнутых инсталляций?

**Утверждено 11.09.2026: манифест + идемпотентный инсталлятор как механизм обновления, semver, без авто-апдейта.**

- Версия шаблона живёт в `templates/xcom/manifest.json` (semver). Правило: patch — правки JS/CSS/гайдов без схемы; minor — новые таблицы/колонки/отчёты, добавляемые идемпотентно; major — несовместимые изменения схемы (требуют миграционных заметок в release notes).
- Обновление = повторный прогон `docs/create_xcom_matching.ps1` новой версии на той же базе: скрипт уже идемпотентен (`Ensure-*`), досоздаёт недостающее и обновляет ассеты; конфиг базы (рантайм-слой) не перетирается — дефолты только дополняются через безопасное слияние.
- Автообновления нет намеренно: партнёр обновляет в своё окно, по release notes. Канал оповещения — GitHub releases репо (партнёр подписан).
- Это же отвечает на «версионирование онтологий» в рамках шаблона: схема — часть дистрибутива, её версия = версия манифеста.

## Решение 4. Граница «шаблон» / «кастомный проект»

**Вопрос:** явный список признаков, по которым партнёр сам понимает «это ещё шаблон» vs «зовите автора».

**Утверждено 11.09.2026: критерий одной фразы — «шаблон — всё, что решается данными; кастом — всё, что требует правки кода или схемы».** Разворачивается в чек-лист:

Остаётся шаблоном (первая линия, конфиг/данные):
- другая категория номенклатуры: свои обязательные атрибуты, веса, маппинг колонок (`xcom_matching_config`, пресеты);
- другие имена колонок/листов Excel — мастер (#4819) и `column_mapping`;
- настройка серой зоны и включение/выключение LLM-режима;
- правка порогов качества, журнал решений, выгрузки.

Кастомный проект (к автору, за рамками шаблона):
- новые сущности схемы или связи, которых нет в `xcom_metadata.json`;
- изменение алгоритма скоринга (не весов, а самой формулы/токенизации);
- интеграции с внешними системами дальше документированного JSON-экспорта;
- иная модель процесса (не «два каталога → кандидаты → ручная проверка → выгрузка»).

Чек-лист признаков живёт также в `docs/xcom-matching/guide-integrator.md`, раздел «Поддержка и граница ответственности» — там его читает партнёр; сюда же он входит в one-pager (ТЗ §8а, этап 1).
