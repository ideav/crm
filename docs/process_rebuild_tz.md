Длина тикета на возвраты **не влияет**: тикеты с телом <200 символов дают повтор по тому же файлу
за 14 дней в 91% случаев, с телом ≥600 символов — в 94%. То есть проблема не в том, «как ставится
задача».

## 2. Диагноз: три причины, все устранимые

**2.1. Правила живут в прозе, а не в коде.** «Не лезть в замороженный день», «не двигать
зафиксированное», «фольга в конец дня» описаны словами и продублированы 175 условиями,
разбросанными по контроллеру. Прозу нельзя нарушить — её можно только не прочитать. Каждый новый
обработчик (их 106) обязан вспомнить весь список правил; рано или поздно не вспоминает — и это
приходит тикетом, а не ошибкой.

**2.2. Нет единой границы записи.** План сохраняется из **26 разных мест**. Проверки стоят внутри
команд (`moveCutToDay` и др.), а не на границе персистентности, поэтому любой новый путь записи
по умолчанию бесправен: он может записать что угодно.

**2.3. Сеть регрессов есть, но ни к чему не подключена.** 565 тестов, 49 секунд, ноль запусков CI
за историю репозитория. 64 файла красные прямо сейчас — и никто не знает, какие из них «устарел
тест», а какие «сломалась функция», потому что суд не заседает. Среди красных —
`atex-production-planning-4163/4171` (июль): они утверждают, что повреждённая «сирота» удаляется,
а лишняя чистка не зовётся. Сейчас это неправда.

**Отдельно — про два документа.** Агент лезет в `atex_production_planning_algorithm.md` (2054
строки) вместо `atex_planning_tz.md` (473) не по своей воле:

- `CLAUDE.md` прямым текстом объявляет алгоритм-док источником истины и требует «ВСЕГДА сверяйся с
  ним ПЕРЕД правкой логики». ТЗ в `CLAUDE.md` **не упомянут ни разу**;
- сам ТЗ в футере отправляет к алгоритм-доку («источник истины по уже работающему алгоритму»);
- ссылки на ТЗ есть только изнутри других документов (`RESUME-4085.md`,
  `atex_planning_actual_behavior.md`), то есть с точек, куда агент не заходит первым.

Плюс терминологическая ловушка: и ТЗ §12.1, и `CLAUDE.md` описывают механизм одинаково — фольга
уводится в конец дня **штрафом** `FOIL_NOTEND_COST_MN`, а не жёстким правилом. Но `CLAUDE.md`
называет это «инвариантом (#3717)». Мягкое предпочтение, названное инвариантом, гарантированно
порождает тикет «почему фольга не последняя» каждый раз, когда другой штраф пересилил, — таких
тикетов за два месяца 22. Слово «инвариант» должно означать ровно одно: «проверяется реестром и
запрещено машине».

Алгоритм-док **описывает код** и растёт вместе с ним: нарушить его нельзя по определению, он всегда
«прав». Нормативным может быть только ТЗ.

## 3. Целевой контур

1. **Инвариант — это код**, лежащий в одном реестре, а не абзац и не 175 условий.
2. **Любая запись плана идёт через один шлюз**, который прогоняет реестр и отказывает автоматике
   при нарушении.
3. **Гейт в CI**: красный тест = мержа нет. Известный долг — в карантине, список только сокращается.
4. **Иерархия документов однозначна**: ТЗ нормативен, алгоритм-док описателен, реестр инвариантов
   исполняем и главнее обоих.
5. **Тикет производит правило**, а не патч: у инварианта — тест на все входы, а не на кнопку, где
   заметили.

## 4. Этапы

### Этап 1 — гейт (сделано в этом PR, осталось включить)

- `scripts/run-tests.sh` — прогон сети без зависимостей; файлы из `experiments/quarantine.txt` в
  гейт не входят, прогоняются отдельно и, если позеленели, печатаются как кандидаты на вывод.
- `experiments/quarantine.txt` — 64 красных файла на сегодня, с правилом «список только
  сокращается».
- `.github/workflows/tests.yml` — прогон на каждый PR и push в main.
- `.gitignore`: каталог `experiments/` целиком игнорировался («local research artifacts for
  #2895») — при этом в нём живёт вся регрессионная сеть, 835 файлов, попавших в индекс
  принудительно. Любой новый тест не подхватывался `git add -A` и мог молча не доехать до PR.
  Теперь игнорируется содержимое, кроме тестов, фикстур и карантина.

**Что сделать вам:** в настройках репозитория сделать чек `tests / regression` **обязательным** для
мержа в `main` (Settings → Branches → Branch protection). Без этого шага PR остаётся декорацией.

**DoD:** на любом PR виден статус-чек; гейт зелёный (проверено: 501 файл, 31 с).

**Дальше:** разбирать карантин темпом ~10 файлов в неделю, начиная со свежих тикетов (4163, 4171,
4173, 4007, 4066, 4131). Для каждого — решение из двух: «тест прав, чиним код» или «тест устарел,
удаляем вместе с обоснованием в PR». Срок: 6 недель до нуля.

Шлюз в контроллере — единственная точка, из которой уходит `_m_save` по плановым полям
(`planStart`, день, станок, фиксация):

```js
// commitSchedule(next, opts) — ЕДИНСТВЕННЫЙ путь записи плана.
//   next  — желаемое состояние (массив резок с planStart/slitter/fixed)

//   actor==='auto'  → ОТКАЗ: ничего не пишем, показываем оператору какое правило и где нарушено,
//                     пишем строку в журнал (id инварианта, reason, затронутые резки);
//   actor==='human' → пишем, но показываем предупреждение (человек вправе, §12.2), кроме
//                     инвариантов с actor:'any' — эти запрещены всем.
// Только после проверки — существующие вызовы _m_save/_m_set, перенесённые внутрь шлюза.
```

- `grep -c "_m_save" 20-controller.js` вне шлюза = **0** (сейчас 26);
- в `05-invariants.js` перечислены все пункты ТЗ §15 плюс заморозка и фиксация;

### Этап 3 — тесты инвариантов вместо тестов на кнопку

Один файл `experiments/atex-pp-invariants.test.js`:

- прогоняет **каждый** инвариант из реестра против сгенерированных планов (fuzz: случайные наборы
  заданий, отпусков, замороженных дней, фиксаций — фиксированный seed, чтобы падение
  воспроизводилось);
- прогоняет **каждый вход**: `generate`, `order`, `manual-move`, `recalc-setup`, `delete` — таблицей
  (входы × инварианты), а не по одному тесту на кнопку;
- при добавлении инварианта в реестр тест автоматически покрывает все входы — новый обработчик
  ничего «не забывает» по построению.

Тесты на тикет (`atex-production-planning-NNNN.test.js`) остаются для разовых дефектов; правила
переезжают в инвариантный файл.

**DoD:** удаление проверки заморозки из любого одного входа роняет инвариантный тест (проверяется
руками при приёмке этапа).

### Этап 4 — иерархия документов

Правка `CLAUDE.md` (в этом PR) устанавливает порядок:

1. **`docs/atex_planning_tz.md` — нормативный документ.** Что должно быть верно. Меняется только
   вместе с решением заказчика. Правило спора: если код расходится с ТЗ — прав ТЗ.
2. **`05-invariants.js` — исполняемая часть ТЗ §15.** Главнее любого текста: то, что в реестре,
   проверяется машиной.
3. **`docs/atex_production_planning_algorithm.md` — карта кода.** Описывает, как сделано сейчас.
   Нормативной силы не имеет, в спорах не участвует, обновляется в том же PR, что и код.

Там же — снять расхождение по фольге: либо она жёсткое правило (тогда переносится в §15 ТЗ и в
реестр), либо штраф (тогда из `CLAUDE.md` убирается слово «инвариант»). **Решение за заказчиком**,
см. §8.

### Этап 5 — тикет как источник правила

- Шаблон `.github/ISSUE_TEMPLATE/rule.md` (в этом PR): заголовок — правило или симптом, **не путь к
  файлу**; обязательные поля «Область действия» (все входы, а не только замеченный) и «Тип»
  (жёсткое / мягкое / разовый дефект / вопрос).
- Правило работы агента (в `CLAUDE.md`): **сначала падающий тест, потом код.** В PR обязателен
  ответ на вопрос «какой инвариант это могло задеть» — при пустом ответе PR не принимается.
- Мультидефектные тикеты (как #4434 с пятью пунктами) разбиваются по одному правилу на тикет:
  иначе половина пунктов теряется и возвращается через неделю.

## 5. Что это даёт по каждой причине

| Причина | Чем закрывается | Ожидаемый эффект |
|---|---|---|
| Правила в прозе | Этап 2 (реестр) + Этап 3 (тесты) | Повторные нарушения одного правила («замороженный день» ×3) исчезают как класс |
| Нет границы записи | Этап 2 (шлюз) | Новый обработчик не может записать нарушающий план — физически |

## 8. Открытые вопросы к заказчику (нужно ваше решение)

1. **Фольга — жёсткое правило или штраф?** Механизм сейчас мягкий (штраф `FOIL_NOTEND_COST_MN`), и
   так написано и в ТЗ §12.1, и в `CLAUDE.md`; но там же это названо «инвариантом». Если фольга
   обязана быть последней **всегда** — она идёт в §15 и в реестр, и автоматика начинает
   отказывать. Если это предпочтение — из `CLAUDE.md` убирается слово «инвариант», а тикеты «почему
   фольга не последняя» закрываются ответом «пересилил другой штраф, вот числа» (панель качества
   плана, §13 ТЗ).
2. **Заморозка дня и фиксация задания** сейчас в ТЗ описаны в §16 как действия оператора, а не в §15
   как запреты. Предлагается перенести в §15 в формулировках: «автоматика не изменяет содержимое
   замороженного дня» и «автогенерация не меняет день зафиксированного задания». Подтвердите
   формулировки — они станут кодом.
3. **Ручное действие против жёсткого правила**: оператор вправе нарушить срок (§12.2) — а вправе ли
   он положить задание в замороженный день вручную? Предлагаемый ответ: да, с предупреждением;
   запрещено только автоматике. Подтвердите.

### Вместо #4436 «Зачем залез в замороженный день что-то менять?»

**Заголовок:** Автогенерация изменила содержимое замороженного дня

**Правило.** Автоматика (Сгенерировать, Упорядочить, Пересчитать наладку, авто-разбиение по дням)
никогда не изменяет задания в замороженном дне: ни порядок, ни время старта, ни состав, ни удаление.

**Область действия.** Все автоматические входы: `generate`, `order`, `recalc-setup`, авто-split при
переносе. Ручные действия оператора — вне правила (см. §8.3 ТЗ после уточнения).

**Как воспроизвести.** День 28.07 заморожен, в нём 4 задания на станке 2; нажать «Сгенерировать» с
диапазоном, включающим 28.07. Журнал: `ideav.ru-1785164694457.log`.

**Сейчас / должно.** Сейчас: задания в замороженном дне переставлены, два поставлены на 08:00.
Должно: замороженный день не изменился ни на минуту; если автоматике «нужно» в него залезть — она
отказывается и показывает, какие задания не удалось разместить.

**Тип.** Жёсткое правило (инвариант) → `FROZEN_DAY`, ТЗ §15.

**Приёмка.** Первым пишется падающий тест `atex-pp-invariants.test.js::FROZEN_DAY × generate`;
проверка встаёт в `commitSchedule`, а не в обработчик кнопки «Сгенерировать»; после фикса тест
таблицей проходит по всем четырём автоматическим входам.

### Вместо #4440 «Почему не переставляются задания? Выгодно поменять местами 3 и 4»

**Заголовок:** «Упорядочить» не меняет местами соседние задания, когда обмен снижает суммарный штраф

**Правило.** Если перестановка двух соседних заданий дня уменьшает суммарный штраф (переналадка +
срок + баланс, ТЗ §8.2), «Упорядочить» обязана её выполнить; если не выполняет — обязана показать,
какой компонент штрафа этому мешает.

**Область действия.** Кнопка «Упорядочить» (`order`) в пределах дня и станка; на замороженные и
зафиксированные задания правило не распространяется (см. `FROZEN_DAY`, `FIXED_CUT_DAY`).

**Как воспроизвести.** Станок 2, день из журнала `ideav.ru-1785172195446.log`, задания 3 и 4:
ручной обмен даёт меньше переналадки, чем оставленный порядок.

**Сейчас / должно.** Сейчас: порядок не меняется, объяснения нет. Должно: либо обмен выполняется,
либо в панели качества плана видно, какой штраф удерживает текущий порядок (число, а не «так вышло»).

**Тип.** Мягкое (штраф) → §8.2 ТЗ; веса — §14. В реестр инвариантов **не** идёт.

**Приёмка.** Тест `atex-production-planning-4440.test.js`: фикстура из журнала, ожидание — после
`order` суммарный штраф не больше, чем при любом обмене соседних пар (локальный оптимум по
транспозициям). Тест сравнивает штраф, а не конкретный порядок, — иначе он сломается от следующей
настройки весов.

### Вместо #4442 «Красные сообщения должны стоять стопкой»

**Заголовок:** Висящие сообщения перекрывают друг друга — не видно, сколько их и какие

**Правило.** Одновременно видимые уведомления, живущие до закрытия (#4418), выкладываются стопкой с
частичным перекрытием: у нижних видна кромка, счётчик показывает общее число.

**Область действия.** Компонент уведомлений рабочего места «Планирование производства» (все
источники сообщений, включая ошибки шлюза записи из этапа 2 — их станет больше).

**Как воспроизвести.** Вызвать подряд 3+ ошибки (например, три отказа автоматики) — все ложатся в
правый нижний угол одна на другую.

**Сейчас / должно.** Сейчас: видно только последнее. Должно: стопка с перекрытием, старые под
новыми, каждое закрывается своим «×».

**Тип.** Разовый дефект (UI), правил планирования не меняет.

**Приёмка.** Тест `atex-production-planning-4442.test.js` на DOM-фикстуре: после трёх вызовов
`notify()` у контейнера три потомка с разным `top`/`z-index`, ни один не перекрыт полностью.
