# Учебная база spz

Готовая песочница на Интеграме: заполненный слой финансовых данных, роли под каждый профиль
пользователя и рабочая связь с Google Sheets. Основа, из которой собирается заготовка для
дэшбордов и финмоделей.

Все данные в базе синтетические. Ломать здесь можно что угодно: ни одного живого человека,
ни одной настоящей суммы за этими цифрами нет.

---

## С чего начать

1. Откройте [ideav.ru/spz](https://ideav.ru/spz).
2. Войдите под учебной учётной записью — они заведены по одной на каждую роль.
3. Пароль общий для всех учебных учёток, **выдаётся отдельно** владельцем базы.
4. Начните с `edu_admin` — у неё видно всё; потом переключайтесь на нужную роль, чтобы понять,
   что видит конкретный профиль.

| Логин | Роль | Логин | Роль |
|---|---|---|---|
| `edu_admin` | Администратор | `edu_ddo` | ДДО |
| `edu_user` | Пользователь | `edu_ddl` | ДДЛ |
| `edu_hr` | Персонал | `edu_audit` | Аудит |
| `edu_qa` | Качество | `edu_investor` | Инвестор |
| `edu_ceo` | Руководитель | `edu_gs` | Интеграция |
| `edu_komblok` | Коммерческий блок | `edu_read` | Только чтение |
| `edu_online` | Онлайн-школа | `edu_finotdel` | Финансовый отдел |

## Как устроены данные

**90 таблиц, 310 реквизитов, 61 таблица с данными.**

Интеграм не делит таблицы на системные и пользовательские технически — работают они одинаково.
Но по смыслу в этой базе три группы.

**Служебные.** `Пользователь` (18), `Роль` (42), `Меню` (151), `Запрос` (22), `Настройка` (269)
и ещё десяток. Через них настраивается доступ и навигация.

**Справочники.** Плоские списки без вложенности: `Должность` (254 записи), `Департамент` (76),
`Статус`, `Стадия` (60), `Источник лида` (64), `Месяц` (133), `Квартал` (41). На них ссылаются
все остальные — трогать их опаснее всего, потому что удаление записи, на которую кто-то
ссылается, база просто не даст.

## Слой финмодели

**Заполнен и готов к работе.**

Финансовая модель здесь разложена не по листам, как в таблице, а на четыре связанные сущности.
Понять эту связку — половина дела.

| Сущность | Роль в модели | Записей |
|---|---|---:|
| `Строка бюджета` (1040) | Статья: «Выручка», «EBITDA», «ФОТ» | 160 |
| `Столбец бюджета` (1043) | Разрез по вертикали | 6 |
| `Колонка группы` (1102) | Группировка: план, факт, отклонение | 25 |
| `Значение` (1010) | Само число на пересечении | 243 |

Одна запись `Значение` ссылается на строку бюджета, единицу измерения и колонку группы. То есть
число всегда знает, *что* оно измеряет и *в каком разрезе*. Отчёт собирается запросом поверх этой
связки, а не формулой в ячейке — в этом главное отличие от таблицы, и на этом строится вся
переиспользуемость.

## Слой представления

**Пустой — это ваше рабочее пространство.**

Конструктор дэшбордов в базе есть, но не наполнен. Таблицы стоят готовые и пустые:

| Таблица | Назначение | Записей |
|---|---|---:|
| `Дэшборд` (1137) | Верхний уровень | 1 |
| `Лист` (985) | Вкладка дэшборда, привязана к году, периоду и роли | 0 |
| `Панель` (986) | Блок на листе: заголовок, запрос, фильтр, сноски | 0 |
| `RG` (992) | Таблица внутри панели: тип, запрос, группировка | 0 |
| `Тип RG` (1016) | Виды представления | 8 |
| `Стиль` (1000), `Формат значений` (1013) | Оформление | 0 |

Иерархия читается так: **Дэшборд → Лист → Панель → RG**. Панель знает, какой запрос выполнить;
RG описывает, как разложить результат по строкам и колонкам.

> Пустота здесь — не пробел, а точка входа. Данные под представлением уже лежат, поэтому первую
> панель можно собрать сразу и увидеть на ней настоящие числа, а не заглушки.

## Связь с Google Sheets

Рабочее место `gssync`. Настроенное подключение забирает данные из книги Google и раскладывает их
по записям базы. Конфигурация лежит в файле, а не в таблице, и правится через форму на
`/spz/gssync`.

- Конфигурация — `my_config1`, хранится в `templates/custom/spz/gss/`.
- Источник — учебная книга с тремя листами: **ШР**, **(План-Факт) (2026)**, **ОПиУ**.
- Приёмник — `Лист GS` (449960) как родитель и `Значение GS` (443296) как подчинённая таблица под ним.
- Запуск — `POST /spz/gssync?JSON&config=my_config1`. Последний прогон прочитал 2 568 записей.

Для каждого листа в конфигурации задаются правила: какие строки искать и какие колонки с них
снимать. Шаблоны вроде `01.01.202*` и `ПЛАН||ФАКТ` позволяют не переписывать настройку каждый год.

> **Важно.** В поле `spreadsheet_id` должен лежать голый идентификатор книги, а не ссылка на неё
> целиком. Идентификатор подставляется в адрес запроса как есть, поэтому вставленный URL
> превращает запрос в мусор и Google отвечает `404 Requested entity was not found`.

## Справочник по API

### Авторизация

```bash
curl -H "X-Authorization: $TOKEN" -b "token=$TOKEN" \
     "https://ideav.ru/spz/terms?JSON"
```

Токен пользователя лежит в его карточке в таблице `Пользователь`, колонка `Token`. Для рабочего
места **Файлы** кука называется иначе — `idb_spz`.

### Чтение

| Запрос | Что отдаёт |
|---|---|
| `terms?JSON` | Список таблиц |
| `metadata?JSON` | Все таблицы с реквизитами и ссылками |
| `metadata/{id}?JSON` | Одна таблица подробно |
| `object/{id}?JSON_OBJ&LIMIT=0,500` | Записи таблицы |
| `object/{id}?JSON_OBJ&F_U={родитель}` | Записи подчинённой таблицы |
| `report/{имя}?JSON_KV` | Готовый отчёт |
| `xsrf?JSON` | Токен формы, нужен для записи |

### Запись

```
# новая запись (название задаётся сразу)
POST /spz/_m_new/{таблица}?up=1&JSON     t{таблица}=Название

# реквизиты существующей записи
POST /spz/_m_set/{запись}?JSON            t{реквизит}=Значение

# первая колонка (название) существующей записи
POST /spz/_m_save/{запись}?JSON           t{таблица}=Новое

# удаление
POST /spz/_m_del/{запись}?JSON
```

В теле каждого запроса обязателен `_xsrf`, полученный из `xsrf?JSON`.

## Грабли

Шесть мест, где легко потерять час.

**Тихий отказ.** Без суффикса `&JSON` запись отвечает редиректом и молча ничего не делает. Ответ
выглядит успешным, данные не меняются.

**403 на первой колонке.** Название записи через `_m_set` изменить нельзя — только через
`_m_save`. У новой записи название задаётся сразу в `_m_new`.

**Пустой ответ вместо данных.** Подчинённая таблица читается фильтром `F_U={родитель}`. Параметр
`up=` для неё возвращает ноль записей и никакой ошибки — данные при этом на месте.

**409 при удалении.** Запись, на которую есть ссылки, база удалить не даст. Сначала переведите
ссылки на другую запись, потом удаляйте. Порядок важен: сперва то, на что никто не ссылается.

**Сервер падает на выборке.** Запрос без разумного `LIMIT` на большой таблице упирается в лимит
памяти PHP. Читайте страницами по 200–500 записей.

**Кэш вместо правок.** Файлы рабочих мест подключаются со счётчиком версии. Изменив `.html` или
`.js`, поднимите номер в ссылке — иначе браузер отдаст старую версию, и правка «не доедет».

## Как сделать из этого шаблон

**Оставить.** Структуру целиком — 90 таблиц со связями и есть главная ценность. Справочники
(должности, департаменты, месяцы, статусы) тоже: без них ссылки повиснут, а наполнять их заново
долго и бессмысленно.

**Уменьшить.** Данные оставлены в объёме, которого хватает для демонстрации, но мало для скорости.
Если заготовка должна разворачиваться быстро, сократите `Лид`, `Сделка` и `ID задачи` до сотни
записей — на вид дэшборда это не влияет.

**Собрать.** Слой представления. Соберите один образцовый дэшборд с двумя-тремя панелями поверх
готовых `Значение` и `Строка бюджета` — он станет и примером, и точкой старта для тех, кто возьмёт
заготовку.

**Описать.** Соответствие между статьями бюджета и листами исходной книги. Это единственное место,
которое каждый новый проект настраивает под себя, и именно там застревают.

> Проверять правки удобнее всего через `edu_read`: роль видит данные, но ничего не сломает.
> Заметили расхождение — переключились на `edu_admin` и поправили.
