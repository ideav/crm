# Read-only доступ к базе по строке подключения MySQL (ext-вьюхи)

Любую базу Интеграма можно открыть внешним SQL-клиентом (DBeaver, DataGrip, Excel/Power BI
через ODBC, `mysql`) только на чтение. Для базы `<db>` ядро строит отдельную схему MySQL
`ext_<db>` из настоящих `VIEW` поверх таблицы базы и заводит пользователя MySQL `ext_<db>`,
которому видна только эта схема. Код — `include/ext_views.php`, тест — `experiments/ext-views-5373.test.php`.

## Что лежит в схеме `ext_<db>`

| вьюха | что это |
| --- | --- |
| `t_<таблица>` | плоская вьюха таблицы: `id`, `parent_id`, `ord`, главное значение (колонка с именем таблицы) и по колонке на реквизит |
| `t_<таблица>__<реквизит>_list` | строки множественного реквизита: `parent_id`, `item_id`, `value`, `ord` |
| `q_<запрос>` | вьюха Запроса (отчёта): тот же SELECT, что строит движок отчётов `Compile_Report` |

Имена — в нижнем регистре, всё кроме букв и цифр заменено на `_`, подряд идущие `_` схлопнуты,
поэтому `__` в имени — только разделитель частей. Предел имени MySQL — 64 символа: длинное имя —
префикс, `_` и 8 символов md5 полного имени. Одноимённые таблицы, запросы и колонки различаются
суффиксом `_<id>`.

Вьюху получает термин, у которого есть реквизиты или записи. Записи таблицы — строки `t=<id
таблицы>`, у которых родитель — запись (`up=1` для независимых таблиц, id записи-владельца для
подчинённых); строки-реквизиты (родитель — термин, `up=0`) записями не считаются.

### Колонки таблицы

- Имя колонки — псевдоним реквизита (`ALIAS`), иначе имя термина реквизита; для ссылки — имя
  таблицы-цели. Совпадение со служебной или соседней колонкой — суффикс `_<id реквизита>`.
- Тип — по базовому типу: NUMBER → целое, SIGNED → `DECIMAL(38,10)`, DATE (`YYYYMMDD`) → `DATE`,
  DATETIME (unix-секунды) → `DATETIME` в часовом поясе сессии читателя, BOOLEAN → `0/1`, прочее —
  текст. Значение не по формату даёт `NULL`, а не ломает выборку.
- Ссылка — две колонки: `<имя>` (главное значение записи-цели) и `<имя>_id`.
- Подчинённая таблица — колонка `<имя>_count` (число записей); сами записи — во вьюхе
  подчинённой таблицы, связь по `parent_id`.
- Множественный реквизит (`:MULTI:` / `"multi": true`) — во вьюхе `_list`, в плоской вьюхе его нет.

### Секреты не выводятся

Термин и реквизит с базовым типом PWD (пароль, токен, xsrf) не дают ни вьюхи, ни колонки; то же
для имён `token`, `xsrf`, `secret`, `password`, `пароль`, `pwd` (без учёта регистра).

### Вьюхи Запросов

SQL берётся из `Compile_Report` в режиме «только SQL» (`$GLOBALS["EXT_SQL_ONLY"]`): без параметров
запроса (`FR_`, `LIMIT` и т.п.) и с правами того, кто пересобирает. Фильтры и сортировку внешний
клиент накладывает сам — `WHERE`/`ORDER BY` поверх вьюхи. Значения во вьюхе Запроса — как в
выдаче отчёта (дата — `YYYYMMDD`). Встроенные значения (сегодняшняя дата, текущий пользователь)
вычисляются в момент пересборки. Запрос, которому нужен id объекта из адреса (`%..._OBJ_ID%`),
и Запрос, SQL которого MySQL не принял (например, повтор имени колонки), во вьюху не переносятся —
причина в поле `errors` ответа.

## Пересборка — вручную

Вьюхи сами не обновляются: изменилась структура — пересоберите.

```
POST /<db>/_ext_rebuild?JSON       # владелец базы или супер-админ, _xsrf обязателен
     password=<новый пароль>       # необязательно
→ {
    "schema": "ext_<db>",
    "rebuilt": ["t_клиент", "t_клиент__тег_list", "q_заказы", ...],
    "dropped": [...],              // вьюхи удалённых таблиц и запросов
    "errors": [{"view": ..., "object": <id>, "error": ...}],
    "login": "ext_<db>",
    "connection": "mysql://ext_<db>:<пароль>@<хост>:<порт>/ext_<db>",
    "password": "..."              // только когда пароль установлен этим вызовом
  }
```

- Ошибка одной вьюхи пересборку не роняет: прежняя вьюха с этим именем остаётся.
- Пароль: у нового читателя генерируется и возвращается один раз; `password` в теле задаёт или
  меняет его; без `password` существующий пароль не трогается.
- Ядро меняет только своего читателя — записанного в реестре `ext__registry.readers` за этой
  базой. Если пользователь MySQL `ext_<db>` уже есть и создан не ядром — ответ 409.
- Отозвать доступ: `DROP USER 'ext_<db>'@'%'; DELETE FROM ext__registry.readers WHERE login='ext_<db>';`
  и при желании `DROP DATABASE ext_<db>;`.

## Права и настройка сервера

Вьюхи работают правами создателя (`SQL SECURITY DEFINER`), поэтому читателю выдано только
`SELECT, SHOW VIEW ON ext_<db>.*` — таблица базы ему закрыта (`SELECT command denied`). Новые
вьюхи после пересборки видны ему сразу: право выдано на схему целиком.

DDL выполняет учётка `INTEGRAM_EXT_ADMIN_USER` / `INTEGRAM_EXT_ADMIN_PASSWORD`, если задана, иначе
учётка приложения. Ей нужны права:

```sql
GRANT SELECT ON ideav.* TO 'integram_ext'@'%';
GRANT ALL ON `ext\_%`.* TO 'integram_ext'@'%' WITH GRANT OPTION;
GRANT CREATE USER ON *.* TO 'integram_ext'@'%';
```

`ext\_%` покрывает схемы баз и реестр `ext__registry`. Хост и порт в строке подключения —
`INTEGRAM_EXT_PUBLIC_HOST` / `INTEGRAM_EXT_PUBLIC_PORT`, по умолчанию адрес сервера БД из
`INTEGRAM_DB_HOST` / `INTEGRAM_DB_PORT`. Читатель заводится с хостом `'%'`: подключиться снаружи
можно, если сервер MySQL слушает внешний адрес и порт открыт.

В `compose.yaml` DDL идёт учёткой `root` локальной MariaDB; порт БД наружу не опубликован —
для внешнего клиента добавьте сервису `db` `ports: ["127.0.0.1:3306:3306"]`.

## Грабли

- **GRANT на `ext_<db>` отклонён при праве на `ext\_%`.** В `GRANT … ON db.*` имя базы — шаблон:
  `_` в `ext_ateh` — любой символ, и право на шаблон `ext\_%` его не покрывает (ERROR 1044).
  Имя в GRANT экранируется (`Ext_grant_db`): `` `ext\_ateh` ``.
- **`SHOW GRANTS FOR` чужой учётки** требует права на схему `mysql`, которого у учётки приложения
  нет; принадлежность читателя ядру поэтому хранится в `ext__registry.readers`.
- Неквалифицированные имена таблиц в SQL Запроса MySQL разрешает при `CREATE VIEW` по текущей
  базе соединения (схема приложения), поэтому SQL отчёта переносится во вьюху без правки.
