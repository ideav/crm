# SQL-доступ пользователя к базе (ext-вьюхи)

Внешний SQL-клиент (DBeaver, DataGrip, Excel/Power BI через ODBC, `mysql`) читает базу Интеграма
только на чтение и только в пределах прав роли пользователя. Доступ выдаётся конкретному
пользователю базы: для него в схеме MySQL `ext_<db>` строятся настоящие `VIEW`, и заводится учётка
MySQL `ext_<db>_<id пользователя>`, которой видны только его представления. Подключение — через
SSH-туннель. Код — `include/ext_views.php`, вкладка «SQL-доступ» в `dir_admin` — `js/ext-access.js`,
туннель — `scripts/ext-ssh-tunnel.sh`, тесты — `experiments/ext-user-views-5373.test.php`,
`experiments/ext-views-5373.test.php`.

## Что видит пользователь

| представление | что это |
| --- | --- |
| `<пользователь>_<таблица>` | плоская вьюха таблицы: `id`, `parent_id`, `ord`, главное значение (колонка с именем таблицы) и по колонке на доступный реквизит |
| `<пользователь>_<таблица>__<реквизит>_list` | строки множественного реквизита: `parent_id`, `item_id`, `value`, `ord` |
| `<пользователь>_<запрос>` | вьюха Запроса: тот же SELECT, что строит движок отчётов `Compile_Report` от имени пользователя |

Таблица и Запрос с одним именем дают вьюху Запроса; таблица в этом случае вьюхи не получает.

Имена — в нижнем регистре, всё кроме букв и цифр заменено на `_`, подряд идущие `_` схлопнуты,
поэтому `__` в имени — только разделитель частей. Предел имени MySQL — 64 символа: длинное имя —
префикс, `_` и 8 символов md5 полного имени. Одноимённые таблицы, запросы и колонки, а также имя,
уже занятое вьюхой другого пользователя, различаются суффиксом `_<id>`.

### Права роли

Набор вьюх считается по грантам роли пользователя (таблица Объекты 116) так же, как ядро
(`Grant_1level`, `Check_Grant` в `index.php`):

- **Таблица** видна при уровне READ или WRITE: явный грант на таблицу; у подчинённой — грант на
  реквизит-массив, иначе уровень родителя; у независимой — грант на корень (`1`). Явный `BARRED`
  закрывает таблицу.
- **Справочник без своего гранта**, на который ссылается таблица с явным грантом, виден ради значений
  ссылок: только `id`, `parent_id`, `ord` и главное значение, без реквизитов и подчинённых таблиц.
- **Колонка** — явный грант на реквизит, иначе уровень таблицы; `BARRED` её убирает. Колонка
  `<имя>_count` подчинённой таблицы есть, только когда подчинённая таблица видна.
- **Запрос** — явный грант на запрос, иначе на таблицу Запросов (`22`), иначе на корень. Грант на
  запрос открывает все его колонки, как и в ядре.
- **Владелец базы** (пользователь с логином = имя базы) видит всё.
- Маски строк роли (`t49`) во вьюхах таблиц не применяются.

### Колонки таблицы

- Имя колонки — псевдоним реквизита (`ALIAS`), иначе имя термина реквизита; для ссылки — имя
  таблицы-цели. Совпадение со служебной или соседней колонкой — суффикс `_<id реквизита>`.
- Тип — по базовому типу: NUMBER → целое, SIGNED → `DECIMAL(38,10)`, DATE (`YYYYMMDD`) → `DATE`,
  DATETIME (unix-секунды) → `DATETIME` в часовом поясе сессии читателя, BOOLEAN → `0/1`, прочее —
  текст. Значение не по формату даёт `NULL`, а не ломает выборку.
- Ссылка — две колонки: `<имя>` (главное значение записи-цели) и `<имя>_id`.
- Множественный реквизит (`:MULTI:` / `"multi": true`) — во вьюхе `_list`, в плоской вьюхе его нет.
- Термин и реквизит с базовым типом PWD (пароль, токен, xsrf) и с именами `token`, `xsrf`, `secret`,
  `password`, `пароль`, `pwd` (без учёта регистра) не дают ни вьюхи, ни колонки.

### Вьюхи Запросов

SQL берётся из `Compile_Report` в режиме «только SQL» (`$GLOBALS["EXT_SQL_ONLY"]`) от имени
пользователя (`BtAsUser`): встроенные значения `[USER]`, `[USER_ID]`, `[ROLE]`, сегодняшняя дата —
его и на момент пересборки. Параметров запроса (`FR_`, `LIMIT` и т.п.) нет: фильтры и сортировку
внешний клиент накладывает сам — `WHERE`/`ORDER BY` поверх вьюхи. Значения — как в выдаче отчёта
(дата — `YYYYMMDD`). Запрос, которому нужен id объекта из адреса (`%..._OBJ_ID%`), и Запрос, SQL
которого MySQL не принял, во вьюху не переносятся — причина в поле `errors` ответа.

## Выдать, пересобрать, отозвать

Вкладка «SQL-доступ» в `dir_admin`: выбрать пользователя → «Выдать доступ / пересобрать». Ответ
показывает логин, пароль (один раз), параметры SSH-туннеля и список вьюх; ниже — кому доступ уже
выдан, с кнопкой «Отозвать». Вьюхи сами не обновляются: изменились структура или права роли —
пересоберите.

```
POST /<db>/_ext_rebuild?JSON       # владелец базы или супер-админ, _xsrf обязателен
     action=rebuild user=<id> [password=<новый пароль>]
→ { "schema": "ext_<db>", "user": "<логин>", "login": "ext_<db>_<id>",
    "rebuilt": [...], "dropped": [...], "errors": [{"view", "object", "error"}],
    "connection": "mysql://ext_<db>_<id>:<пароль>@127.0.0.1:13306/ext_<db>",
    "ssh": {"host", "port", "user", "db_host", "db_port", "local_port", "command"},
    "password": "..." }            // только когда пароль установлен этим вызовом
     action=revoke user=<id>       → вьюхи пользователя и его учётка удаляются; 404, если доступа нет
     action=list                   → readers (кому выдан), users (пользователи с ролями), ssh
```

- Пароль: у новой учётки генерируется и возвращается один раз; `password` задаёт или меняет его.
- Ошибка одной вьюхи пересборку не роняет: прежняя вьюха с этим именем остаётся.
- Вьюха, которая пользователю больше не положена, удаляется вместе с правом на неё (`REVOKE` до
  `DROP VIEW`: право на таблицу при удалении вьюхи не исчезает и перешло бы к одноимённой вьюхе).
- Ядро меняет только свои учётки — записанные в реестре `ext__registry.readers`; чужая одноимённая
  учётка MySQL — ответ 409. Чья вьюха — реестр `ext__registry.views`.

## SSH-туннель

Порт MySQL наружу не открывается. Пользователь поднимает туннель через учётку `dbtunnel`, у которой
нет командной строки и пароля, а её ключи открывают ровно один адрес — сервер MySQL.

На сервере (один раз; `DB_HOST`/`DB_PORT` — адрес MySQL со стороны сервера):

```bash
sudo DB_HOST=127.0.0.1 DB_PORT=3306 scripts/ext-ssh-tunnel.sh setup
```

`setup` заводит учётку, кладёт блок `Match User dbtunnel` в `/etc/ssh/sshd_config.d/ext-tunnel.conf`
(`AllowTcpForwarding local`, `PermitOpen`, `ForceCommand nologin`, без TTY и пароля), проверяет
`sshd -t` и `sshd -T`, что блок применился к `dbtunnel` и не задел других пользователей, и только
тогда перечитывает sshd.

Выдать ключ пользователю (он присылает открытую часть, `~/.ssh/id_ed25519.pub`):

```bash
sudo DB_HOST=127.0.0.1 DB_PORT=3306 scripts/ext-ssh-tunnel.sh add-key /tmp/ivan.pub
sudo scripts/ext-ssh-tunnel.sh list
sudo scripts/ext-ssh-tunnel.sh remove-key ivan@laptop     # по комментарию или части ключа
```

Ключ пишется с `restrict,port-forwarding,permitopen="<DB_HOST>:<DB_PORT>"`.

У пользователя: `ssh -N -L 13306:<db_host>:<db_port> -p <порт> dbtunnel@<сервер>` и подключение к
`127.0.0.1:13306`, база `ext_<db>`. В DBeaver — вкладка «SSH» подключения (хост, порт, `dbtunnel`,
свой ключ), на вкладке «Main» — `db_host`, `db_port`, логин, пароль и база из ответа.

## Настройка ядра

| переменная | смысл | по умолчанию |
| --- | --- | --- |
| `INTEGRAM_EXT_ADMIN_USER` / `_PASSWORD` | учётка MySQL для DDL, учёток и GRANT | соединение приложения |
| `INTEGRAM_EXT_SSH_HOST` / `_PORT` / `_USER` | SSH-сервер туннеля для ответа и вкладки; пусто — прямое подключение | — / 22 / `dbtunnel` |
| `INTEGRAM_EXT_DB_HOST` / `_PORT` | адрес MySQL со стороны SSH-сервера (без туннеля — для клиента) | `INTEGRAM_DB_HOST` / `_PORT` |
| `INTEGRAM_EXT_READER_HOST` | хост учёток-читателей MySQL | `%` |

Через туннель на `127.0.0.1:3306` читатель приходит с `127.0.0.1`/`localhost`; `INTEGRAM_EXT_READER_HOST=localhost`
не пускает его ни с какого другого адреса. Учётке DDL нужны права:

```sql
GRANT SELECT ON ideav.* TO 'integram_ext'@'%';
GRANT ALL ON `ext\_%`.* TO 'integram_ext'@'%' WITH GRANT OPTION;
GRANT CREATE USER ON *.* TO 'integram_ext'@'%';
```

`ext\_%` покрывает схемы баз и реестр `ext__registry`. В `compose.yaml` DDL идёт учёткой `root`
локальной MariaDB.

Вьюхи работают правами создателя (`SQL SECURITY DEFINER`): читателю выдано только
`SELECT, SHOW VIEW` на каждую свою вьюху, таблица базы и чужие вьюхи ему закрыты (`SELECT command denied`).

## Грабли

- **GRANT на базу `ext_<db>` отклонён при праве на `ext\_%`.** В `GRANT … ON db.*` имя базы — шаблон:
  `_` — любой символ, и право на шаблон `ext\_%` его не покрывает (ERROR 1044). Для права на базу имя
  экранируется (`Ext_grant_db`); права читателей выдаются на отдельные вьюхи (`db.view`), где имя
  базы шаблоном не считается.
- **`SHOW GRANTS FOR` чужой учётки** требует права на схему `mysql`, которого у учётки приложения
  нет; принадлежность учёток и вьюх поэтому хранится в `ext__registry`.
- **Предупреждения движка отчётов в JSON-ответе.** `Compile_Report` пишет PHP-предупреждения в вывод
  (`trace()` склеивает строку с массивом), и они ломали JSON пересборки → вывод компиляции в режиме
  «только SQL» буферизуется и отбрасывается (`Ext_core_report_sql`).
- Неквалифицированные имена таблиц в SQL Запроса MySQL разрешает при `CREATE VIEW` по текущей
  базе соединения (схема приложения), поэтому SQL отчёта переносится во вьюху без правки.
- Учётка, созданная пересборкой, которая потом упала, остаётся без известного пароля — задайте его
  полем «Пароль».
