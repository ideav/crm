# Иерархический OLTP: разрезы аналитики на верхнем уровне
> Часть базы знаний Integram. Индекс: [docs/kb/README.md](README.md)

## На пальцах (для человека)

Квартетная модель и так иерархична: у каждой записи есть родитель `up`. Обычно
транзакционные записи (заказы, платежи, события) лежат плоско — все корневые, а
их реквизиты при них. Иерархический OLTP — это когда часть реквизитов с низкой
вариативностью (дата, филиал, валюта, тип) выносится в отдельную запись-«разрез»
уровнем выше, а транзакции становятся её детьми. Значения разреза хранятся один
раз на группу, и аналитика «сколько/чего по филиалам за неделю» ходит по тысячам
строк разреза вместо миллионов строк реквизитов. Уровней может быть больше двух;
что на какой уровень попадает, определяет частотность повторов.

Это инструмент, а не оптимизация по умолчанию: неправильно выбранный разрез
делает хуже и хранение, и запросы. Ниже — измеренные правила выбора
(1 млн транзакций × 45 реквизитов, Postgres 16.4, индексы `(up,t)` и
`(t, lower(left(val,127)))`; методика и скрипты — backlogram
`experiments/hier-oltp-569/`, исходная идея — issue backlogram#569).

## Правила выбора разреза (для агента)

**1. Правило частотности — главное.** Вынос допустим, пока
`N_записей / |декартово произведение кардинальностей разреза|` ≳ 10.
Измерено: разрез (дата, филиал, валюта, тип) при 1 млн транзакций даёт 9,8
записи на группу и −7% строк; добавление ещё четырёх полей (ISO, ПК, POS,
статус) даёт 1,1 записи на группу и **+3% строк** — иерархия становится хуже
плоской раскладки. Кардинальности проверяются до внедрения обычным
`SELECT count(DISTINCT ...)`.

**2. Разрез ускоряет только агрегаты по СВОИМ размерностям.** Счёт по филиалам
за 7 дней: плоско 2,6 с → разрез (дата, филиал) 0,05 с (53×) → разрез из 4 полей
0,19 с (14×). Счёт по полю, которого в разрезе нет, работает как у плоской
раскладки. Разрез проектируется от реальных запросов приложения, не «на всякий
случай».

**3. Меры (суммы) нижнего уровня иерархия ЗАМЕДЛЯЕТ.** Сумма `amount` по
филиалам: плоско 2,7 с, через иерархию 9,5 с (потеря локальности: путь
разрез → транзакция → мера — случайный доступ). Если нужны суммы — выноси на
разрез **накопитель меры** (реквизит «сумма детей», инкремент при каждой
вставке): сумма по филиалам 0,8 с, по валютам за квартал 4,7 с против 28,3 с у
плоского. Цена накопителя: +1 запись/обновление на вставку и горячая запись на
популярной группе.

**4. Точечный OLTP-доступ не страдает.** Поиск по значению реквизита и полная
карточка — ~3 мс и в плоской, и в иерархической раскладке (карточка = свои
реквизиты + подъём к разрезу за вынесенными). Вставка дополнительно делает
найти-или-создать группу — один поиск по `(t, val)`.

**5. Хранение.** Экономия ≈ (доля вынесенных реквизитов) × (1 − 1/размер
группы): 4 поля из 45 при группе ≥10 → ~7% строк и байт. Пустые реквизиты не
хранятся в любой раскладке — это свойство модели, не иерархии.

**6. Ориентир по цене унификации.** Та же база в классической широкой таблице:
0,46 ГБ против 5,5–5,9 ГБ и в разы быстрее на простых агрегатах. Иерархия
сокращает этот разрыв, но не отменяет; унификация покупается ради схемы без DDL.

### Как построить в Интеграме

Разрез — обычная таблица (термин) с реквизитами-размерностями; транзакция —
подчинённые записи (`up` = id записи разреза, см. [schema.md](schema.md)
«подчинённая таблица» и [crud.md](crud.md) — создание детей с `up`).
Найти-или-создать группу: `object/{cutTable}/?JSON_OBJ&F_{tableId}={ключ}`,
при пустом ответе — `_m_new`. Накопитель — NUMBER-реквизит разреза,
инкремент — `_m_set` после вставки транзакции.

## Грабли

- **Симптом:** после «оптимизации» иерархией база выросла, запросы не ускорились → **Причина:** разрез слишком детальный — групп почти столько же, сколько записей (правило 1 нарушено) → **Фикс:** посчитать кардинальности, убрать поля из разреза до `N/групп ≥ 10`; поля «на всякий случай» держать реквизитами нижнего уровня. *(замер 10.09.2026, backlogram#569: 8 полей → 1,1 зап./группу, +3% строк)*
- **Симптом:** сумма по мере через иерархию медленнее плоской раскладки в разы → **Причина:** мера на нижнем уровне, путь разрез→дети→мера теряет локальность → **Фикс:** накопитель меры на разрезе (правило 3) либо считать по плоскому пути. *(тот же замер: 9,5 с против 2,7 с)*
- **Симптом:** агрегат по полю X не ускорился, хотя «всё вынесли» → **Причина:** X не входит в разрез → **Фикс:** разрез проектируется от формы запросов (правило 2); при двух несовместимых формах — подуровни (дата,филиал)→(валюта,тип), но их выигрыш пока не замерен.
