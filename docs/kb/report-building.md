# Построение запросов: типовые приёмы
> Часть базы знаний Integram. Индекс: [docs/kb/README.md](README.md)

## На пальцах (для человека)
Запрос (отчёт) — это список колонок. У каждой колонки есть источник (таблица или её
реквизит) и несколько полей: имя, формула, фильтр, функция, «скрыть», сортировка. Как
соединить таблицы и по чему группировать, ядро определяет само по метаданным. SQL
пишется только в формулах, и в них на другие колонки ссылаются **псевдонимом**: это
слово, записанное в поле «Формула» колонки-источника. Внутренние имена ядра (`a10012.val`,
`a21056_val`) для построения запроса не нужны.

Приёмов немного, они одинаковы во всех базах. Ниже они разобраны по 165 запросам и 1312
колонкам из пяти рабочих баз. Самые частые поля: функция `abn_ID` (251 колонка), `SUM`
(54), фильтр `%` (23), `[USER_ID]` (17). Около трёхсот колонок имеют формулу, и в
большинстве случаев это одно слово-псевдоним. Отдельно разобран рецепт «Остаток лимита»,
проверенный на стенде.

## Поля колонки и запроса

Колонка — запись таблицы 28, подчинённая запросу (`up` = id запроса). Создаётся одним
вызовом, все поля сразу:

```bash
POST /{db}/_m_new/22?JSON   up=1 t22=<имя запроса>                       # → {"id": queryId}
POST /{db}/_m_new/28?JSON&up={queryId}   up={queryId} t28=<источник> t100=… t101=… t104=…
GET  /{db}/report/{queryId}?JSON_KV                                     # проверить
GET  /{db}/object/28/?JSON_OBJ&F_U={queryId}                            # колонки запроса
```

| Поле | Реквизит | Что задаёт |
|---|---|---|
| Источник | `t28` | id таблицы (её главное значение) или id реквизита из `metadata/{таблица}?JSON`. `0` — вычисляемая колонка без источника |
| Имя в отчёте | `t100` | ключ в `JSON_KV` и имя внешнего фильтра `FR_<имя>`/`TO_<имя>`. В формулах **не** используется |
| Формула | `t101` | у колонки с источником — **псевдоним** (одно слово), на него ссылаются формулы других колонок; у вычисляемой (`t28=0`) — SQL-выражение над псевдонимами |
| Значение (от) / (до) | `t102` / `t103` | фильтр строк (WHERE), см. приём 6 |
| Функция | `t104` | `SUM`, `COUNT`, `AVG`, `MIN`, `MAX`, `GROUP_CONCAT`, `JSON_ARRAYAGG` — агрегат; `abn_ID` — id записи, `abn_ORD` — порядок, `abn_UP` — id родителя. Это ссылка на справочник «Функция» (63): в `_m_new` можно писать имя (`t104=SUM`), в `_m_set` — только id (`object/63?JSON_OBJ`) |
| Функция (от) / (до) | `t105` / `t106` | фильтр по значению агрегата (HAVING) |
| Скрыть | `t107` | `1`: колонка работает (фильтр, псевдоним, связь), но не выводится и не участвует в группировке |
| Формат | `t84` | `NUMBER`, `SIGNED`, `DATE`, `HTML`… (ссылка на справочник форматов) |
| Сорт. | `t109` | порядок сортировки: `1`, `2`, …; минус — по убыванию |
| Итог | `t72` | итог по колонке в форме отчёта (`SUM`, `COUNT`) |
| Присвоить | `t132` | SET-запрос — изменение данных ([queries.md](queries.md)) |

У самого запроса (таблица 22) в типовых случаях нужны только `t22` (имя), иногда
`LIMIT` (`t134`) и «Если пусто, вернуть» (`t113`, значение отчёта без строк — например,
`0` для подзапроса). Записи FROM/JOIN (тип 44) и поля WHERE/HAVING/ORDER BY запроса
типовые приёмы не используют: соединения, фильтры и сортировка задаются колонками.

## Приёмы

### 1. Колонка таблицы и её реквизита
**Задача:** список записей таблицы с её полями.
**Поля:** `t28` = id таблицы (главное значение записи) или id реквизита; `t100` — имя.
**Важно:** первая колонка задаёт главную таблицу — строки отчёта будут её записями.

```
t28=<Задача>                  t100=Задача
t28=<Задача → Крайний срок>   t100=Срок
```

### 2. Реквизит связанной таблицы
**Задача:** показать поле из таблицы, на которую ссылается главная (или которая ссылается
на неё, или подчинённой).
**Поля:** просто `t28` = id реквизита той таблицы. Путь соединения ядро находит само:
ссылка «от нас», ссылка «на нас», подчинённая таблица, родитель. Промежуточные таблицы
добавлять не нужно.

```
t28=<Задача>                  t100=Задача
t28=<Сотрудник → ФИО>         t100=ФИО            # Задача ссылается на Сотрудника
t28=<Сотрудник → Отдел>       t100=Отдел
```

Если до таблицы ведут несколько ссылок, ядро идёт через ту, чья ссылочная колонка стоит
в отчёте: добавьте её (можно скрытой, `t107=1`).

### 3. Id записи и служебные значения
**Задача:** отдать клиенту id записи или id значения справочника (для ссылок, фильтров,
связи с подзапросом).
**Поля:** `t104=abn_ID`. На колонке таблицы — id записи, на ссылочном реквизите — id
записи справочника. Реже: `abn_ORD` (порядок записи), `abn_UP` (id родителя).

```
t28=<Задача>                    t100=ЗадачаID    t104=abn_ID
t28=<Задача → Статус>           t100=СтатусID    t104=abn_ID
```

### 4. Агрегат с группировкой
**Задача:** сумма, количество, среднее по группам.
**Поля:** у агрегируемой колонки `t104=SUM|COUNT|AVG|MIN|MAX|GROUP_CONCAT`. `GROUP BY`
ядро строит само: по всем видимым колонкам без агрегата. Скрытые колонки (`t107=1`)
группу не дробят. Итог по колонке в форме — `t72=SUM`.

```
t28=<Задача → Статус>   t100=Статус
t28=<Задача>            t100=Задач        t104=COUNT    t72=SUM
```

### 5. Псевдоним и вычисляемая колонка
**Задача:** значение, которого нет в данных: разность, доля, условие, склейка строк.
**Поля:**
- у колонки-источника `t101` = псевдоним: одно слово без пробелов (кириллица подходит),
  обычно колонка скрыта (`t107=1`);
- у вычисляемой колонки `t28=0`, `t100` — имя, `t101` — SQL-выражение, где поля названы
  псевдонимами.

```
t28=<Смена → Мест>               t100=Мест        t101=мест
t28=<Смена → Куплено путёвок>    t100=Куплено     t101=куплено
t28=0                            t100=Загрузка, % t101=ROUND(куплено/мест*100, 2)
```

Ядро заменяет псевдоним целым словом на поле колонки. Отсюда правила:
- в формуле — псевдоним (`t101` источника), а **не** имя в отчёте (`t100`). Имя
  в отчёте в формуле даёт `Unknown column '<имя>'`;
- псевдоним не совпадает с SQL-словами и функциями (`id`, `val`, `SUM`) и с другими
  псевдонимами запроса;
- в формулах нельзя писать `SELECT`, `FROM`, `TABLE` — сумма по другой таблице делается
  подзапросом (приём 7).

**Агрегат в вычисляемой колонке** — двумя способами:
- функция колонки над выражением: `t101=СтатусID=<id «Завершена»>`, `t104=SUM` — число
  завершённых в группе;
- агрегат внутри формулы: `t101=ROUND(SUM(Оценка), 1)`. Такая колонка не попадает
  в `GROUP BY`.

Псевдоним агрегированной колонки означает её значение **до** агрегации. Чтобы получить
сумму в формуле, пишите агрегат явно: `Лимит-IFNULL(SUM(Контракты),0)`. Вычисляемая
колонка без агрегата в отчёте с группировкой сама становится полем группировки.

`[THIS]` в формуле колонки с источником — её собственное значение:
`t101=COALESCE([THIS], DATE_FORMAT(CURDATE(), '%Y%m%d'))`.

### 6. Фильтр по значению, пользователю или параметру
**Задача:** отобрать строки.
**Поля:** `t102` (от) и `t103` (до) на колонке, по которой фильтруем. Если колонка
нужна только для фильтра, её скрывают (`t107=1`).

| `t102` | Смысл |
|---|---|
| `Одобрена` | равно значению (у ссылки — по названию значения справочника) |
| `<id>` при `t104=abn_ID` | ссылка равна записи справочника с этим id |
| `%` / `!%` | непусто / пусто |
| `!1` | не равно 1 |
| `>=[WEEK_AGO]`, `[TODAY]`, `[NOW]` | относительные даты |
| `1.1` и `t103=31.12` | диапазон дат текущего года |
| `[USER_ID]` при `t104=abn_ID` на колонке «Пользователь» | строки текущего пользователя |
| `_request_.ProjID` | параметр из URL (`?ProjID=…`) |
| `[ИмяДругогоЗапроса]` | значение другого запроса (приём 7) |

Условие сложнее одного поля — вычисляемой колонкой: `t28=0`, `t101` — логическое
выражение над псевдонимами, `t102=1`, `t107=1`.
По значению агрегата фильтрует `t105`/`t106` (HAVING), например «где больше одной».
Снаружи фильтр передаётся как `FR_<t100>`/`TO_<t100>` и перекрывает `t102`/`t103`
([queries.md](queries.md)).

### 7. Сумма по подчинённым и ссылающимся записям
**Задача:** у каждой записи — сумма (количество) по записям, которые на неё ссылаются.

**Одна ветка — колонкой с агрегатом.** «Компания + сумма её заявок»:

```
t28=<Компания>          t100=Компания
t28=<Заявка → Сумма>    t100=Заявлено    t104=SUM
```

**Две суммы по разным уровням — подзапросами.** В одном запросе строки всех
присоединённых таблиц перемножаются: в цепочке Компания ← Заявка ← Договор сумма по
заявкам повторяется столько раз, сколько у заявки договоров. Поэтому в одном запросе
суммируют только по самому нижнему уровню цепочки, а каждую следующую сумму считают
отдельным запросом-подзапросом.

Подзапрос — обычный запрос:
- первая **видимая** колонка — значение (обычно `t104=SUM`);
- скрытая колонка-связь: `t104=abn_ID`, `t102=[Псевдоним]`, где псевдоним — колонка
  внешнего запроса;
- если строк нет, значение пустое: `IFNULL(...)` во внешней формуле или «Если пусто,
  вернуть» (`t113=0`) у подзапроса.

Во внешнем запросе:
- скрытая колонка с id: `t104=abn_ID`, `t101=<Псевдоним>`;
- вычисляемая колонка: `t28=0`, `t101=[Имя подзапроса]`.

Пример из рабочей базы (названия заменены): остаток склада по артикулу позиции.

```
# подзапрос «Склад по артикулу»
t28=<Позиция → Артикул>      t104=abn_ID   t102=[art_id]   t107=1
t28=<Партия → Остаток>       t100=Остаток  t104=SUM
# во внешнем запросе
t28=<Позиция → Артикул>      t104=abn_ID   t101=art_id     t107=1
t28=0                        t100=stock    t101=[Склад по артикулу]
```

### 8. Права на запрос
**Задача:** дать роли отчёт и только её строки.
- READ-грант роли на сам запрос: `POST /{db}/_m_new/116?JSON up={roleId} t116={queryId}
  t136=<READ>` ([roles.md](roles.md)). Грант на запрос открывает все его колонки,
  даже если на их таблицы у роли прав нет; маски строк к запросу не применяются.
- Строки «только свои» — фильтром в самом запросе: колонка «Пользователь» (или ссылка
  на него) с `t104=abn_ID`, `t102=[USER_ID]`, `t107=1`.

### 9. Оформление: сортировка, формат, ссылка
- `t109=1`, `2`, … — сортировка, `-1` — по убыванию; сортировать можно и по скрытой колонке.
- `t84=NUMBER|DATE|HTML`. HTML-ссылка — вычисляемой колонкой:
  `t101=CONCAT('<a href="', Адрес, '">открыть</a>')`, `t84=HTML`.

## Рецепт: «Остаток лимита»

**Задача.** По каждой компании: компания, лимит финансирования (реквизит компании),
одобрено (сумма заявок компании в статусе «Одобрена»), законтрактовано (сумма договоров
по заявкам компании), остаток = лимит − законтрактовано.

**Схема.** Компания (реквизит «Лимит финансирования»); Заявка (ссылки «Компания»,
«Статус», реквизит «Сумма»); Договор (ссылка «Заявка», реквизит «Сумма»). Id таблиц
и реквизитов берутся из `metadata?JSON`, ниже вместо них — названия в угловых скобках.

Две суммы лежат на разных уровнях цепочки Компания ← Заявка ← Договор, поэтому каждая
считается своим подзапросом (приём 7), а остаток — вычисляемой колонкой (приём 5).

```bash
# 1. Подзапрос «Одобрено компании»: сумма одобренных заявок компании [КомпанияID]
POST _m_new/22?JSON   up=1 t22=Одобрено компании                                   # → Q1
POST _m_new/28?JSON&up=Q1  up=Q1 t28=<Заявка → Сумма>     t100=Сумма t104=SUM
POST _m_new/28?JSON&up=Q1  up=Q1 t28=<Заявка → Статус>    t102=Одобрена t107=1
POST _m_new/28?JSON&up=Q1  up=Q1 t28=<Заявка → Компания>  t104=abn_ID t102=[КомпанияID] t107=1

# 2. Подзапрос «Законтрактовано компании»: сумма договоров по заявкам компании
POST _m_new/22?JSON   up=1 t22=Законтрактовано компании                            # → Q2
POST _m_new/28?JSON&up=Q2  up=Q2 t28=<Договор → Сумма>    t100=Сумма t104=SUM
POST _m_new/28?JSON&up=Q2  up=Q2 t28=<Заявка → Компания>  t104=abn_ID t102=[КомпанияID] t107=1

# 3. Отчёт «Остаток лимита»
POST _m_new/22?JSON   up=1 t22=Остаток лимита                                      # → Q
POST _m_new/28?JSON&up=Q   up=Q t28=<Компания>                        t100=Компания
POST _m_new/28?JSON&up=Q   up=Q t28=<Компания>  t100=КомпанияID t101=КомпанияID t104=abn_ID t107=1
POST _m_new/28?JSON&up=Q   up=Q t28=<Компания → Лимит финансирования> t100=Лимит t101=Лимит
POST _m_new/28?JSON&up=Q   up=Q t28=0 t100=Одобрено        t101=[Одобрено компании]
POST _m_new/28?JSON&up=Q   up=Q t28=0 t100=Законтрактовано t101=[Законтрактовано компании]
POST _m_new/28?JSON&up=Q   up=Q t28=0 t100=Остаток         t101=Лимит-IFNULL([Законтрактовано компании],0)

GET report/Q?JSON_KV
# [{"Компания":"…","Лимит":"5000000","Одобрено":"2500000","Законтрактовано":"1500000","Остаток":"3500000"}, …]
```

В подзапросе договоров нет колонки «Договор → Заявка»: от договора до компании ядро
проходит через ссылку само. Компания без договоров получает пустое «Законтрактовано»,
а остаток — полный лимит, благодаря `IFNULL`.

**Короткий вариант.** Если договор бывает только один на заявку, обе суммы можно
посчитать в одном запросе без подзапросов:

```
t28=<Компания>                        t100=Компания
t28=<Компания → Лимит финансирования> t100=Лимит            t101=Лимит
t28=<Заявка → Сумма>                  t100=Одобрено         t104=SUM
t28=<Заявка → Статус>                 t102=Одобрена         t107=1
t28=<Договор → Сумма>                 t100=Законтрактовано  t101=Контракты  t104=SUM
t28=0                                 t100=Остаток          t101=Лимит-IFNULL(SUM(Контракты),0)
```

Здесь фильтр «Одобрена» отбирает и договоры: учитываются только договоры одобренных
заявок. При втором договоре на ту же заявку «Одобрено» удваивается. Правильные значения
в этом случае даёт только вариант с подзапросами.

**Проверка.** Оба варианта собраны на стенде замера python2node#1060 в чистой копии
базы B. Пробы группы R и S (`T1.R1`, `T1.S1`, `T1.S2`) прошли. Проба «второй договор на
одобренную заявку» прошла у варианта с подзапросами и не прошла у короткого: «Одобрено»
4 000 000 вместо 2 500 000. Скрипт проверки —
[`docs/research/agent-env-1008/kb-5243/check_report_recipe.py`](../research/agent-env-1008/kb-5243/check_report_recipe.py).

## Грабли
- **Симптом:** `Unknown column 'Лимит' in 'SELECT'` в формуле вычисляемой колонки → **Причина:** в формуле написано имя в отчёте (`t100`) колонки-источника, а у неё нет псевдонима: формулы видят только `t101` источников → **Фикс:** колонке-источнику `t101=Лимит` (одно слово), в формуле — это слово. Внутренние имена из текста ошибки (`a10012.val`, `a21056_val`) не копировать: они зависят от набора колонок и в подзапросе другие. *(23.10.2026, issue #5243)*
- **Симптом:** сумма по заявкам больше настоящей ровно на сумму заявок с несколькими договорами → **Причина:** в одном запросе строки цепочки Компания ← Заявка ← Договор перемножаются, `SUM` по среднему уровню считает заявку столько раз, сколько у неё договоров → **Фикс:** в одном запросе суммировать только нижний уровень цепочки, остальные суммы — подзапросом (приём 7). *(23.10.2026, issue #5243)*
- **Симптом:** `Недопустимое значение вычисляемого поля: нельзя использовать служебные слова SQL. Найдено: SELECT` → **Причина:** в формулах запрещены `SELECT`, `FROM`, `TABLE` → **Фикс:** выборку из другой таблицы оформить отдельным запросом и вставить в формулу как `[Имя запроса]`. *(23.10.2026, issue #5243)*
- **Симптом:** `Невозможно связать колонки отчета` после добавления записи FROM/JOIN (тип 44) или поля `ALIAS` (`t58`) → **Причина:** явное соединение не нужно: путь между таблицами ядро находит по ссылкам, а запись 44 с неверным условием ломает построение → **Фикс:** удалить записи 44 и `t58`; если путь неоднозначен, добавить в отчёт ссылочную колонку нужной таблицы (скрытой). *(23.10.2026, issue #5243)*
- **Симптом:** после добавления вычисляемой колонки строки отчёта размножились → **Причина:** вычисляемая колонка без агрегата в отчёте с группировкой сама становится полем группировки; псевдоним агрегированной колонки означает значение до агрегации → **Фикс:** агрегат внутри формулы (`SUM(Контракты)`) или `t104=SUM` у вычисляемой колонки. *(23.10.2026, issue #5243)*
