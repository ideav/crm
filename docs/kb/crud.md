# Данные (DML) — команды `_m_*` и чтение
> Часть базы знаний Integram. Индекс: [docs/kb/README.md](README.md)

## На пальцах (для человека)
Когда схема (таблицы и колонки) уже готова, в неё кладут сами записи: заказы,
клиентов, позиции. Создание, правка и удаление записей — это семейство команд
`_m_*`, а чтение — GET-запросы к `object/`. Главный фокус, на котором все
спотыкаются: значение первой колонки (имя/номер записи) пишется не в `t3`, а в
`t<id таблицы>` — например для таблицы 1075 это `t1075`. Дочерние записи
(позиции заказа) создаются с указанием родителя `up=<id заказа>`, а ссылочные
поля заполняются id записи из целевого справочника. Подробности структуры — в
[schema.md](schema.md), формат метаданных там же.

> ────────── дальше — справочник для агента ──────────

## Операции (для агента)

Поля записи можно передавать по именам (`fields={"Имя поля": значение}` в `_m_new`/`_m_set`,
имена ключами в `_m_batch`) и читать по именам (`object/{таблица}/?JSON_OBJ&NAMED`) —
[schema-json.md](schema-json.md).

Авторизация — см. [00-start.md](00-start.md). `_m_*` — POST с `token`+`_xsrf`.

### Создать запись
```bash
POST /{db}/_m_new/{tableId}?JSON=1
# Корневая запись:
Fields: up=1, t{tableId}="Название записи", t{colId1}=значение, t{colId2}=значение
# Дочерняя (подчинённая) запись — родитель в up:
Fields: up={parentRecordId}, t{tableId}="Название", t{colId1}=значение
# Ссылочное (ref) поле — значение = id записи целевой таблицы:
Fields: t{refReqId}=579     # 579 — id записи в целевом справочнике
# Мульти-ссылка (multi) — id через запятую одной строкой, тем же ключом:
Fields: t{refReqId}=579,612
# Полезные флаги: ?full=1 (вернуть полный объект), up=1 (корень)
```
**Главное значение записи = `t{tableId}`, а не `t3`.** Пример: имя заказа в
таблице 1075 → `t1075=...`; логин пользователя (таблица 18) → `t18=...`; имя роли
(таблица 42) → `t42=...`; имя меню (таблица 151) → `t151=...`.

### Обязательные поля: строгий режим `strict`
По умолчанию `_m_new` создаёт запись и без обязательных (`"required":true`) полей — форма и
таблица дозаполняют их потом, а ответ `200` с `"next_act":"edit_obj"` успехом не отличается.
API-клиенту и ИИ-агенту нужен флаг `strict` (`?strict`, `strict=1` в адресе или теле;
в `_m_batch` — на весь пакет или в `fields` операции):
```bash
POST /{db}/_m_new/{tableId}?JSON=1&strict=1
# не хватает обязательного поля → 400, запись не создаётся:
[{"error":"Не заполнены обязательные поля: Сумма (t10203)"}]
```
- `_m_new`: каждое обязательное поле приходит непустым — `t{reqId}`, `NEW_{reqId}` (ссылка
  по имени) или файлом; значение по умолчанию из атрибутов колонки засчитывается.
- `_m_save`: проверяются только присланные поля — присланное пустым обязательное поле даёт
  400 до любой записи, не присланное остаётся как было.
- Не проверяются подчинённые таблицы, кнопки и поля без права записи у пользователя.
- В `_m_batch?strict=1` отказ — ошибка своей операции (`"ok":false`), остальные выполняются.

### Изменить запись
```bash
POST /{db}/_m_set/{objId}?JSON=1
Fields: t{reqId}=новое_значение         # любую колонку, включая первую t{tableId}
```
Первая колонка (`t{tableId}`) сохраняется теми же проверками, что и через `_m_save`:
права на запись, уникальность/составной ключ, запрет пустого имени.

### Галка (BOOLEAN): да / нет / не задано
| в базе | запись (`t{reqId}=`) | чтение API (`object/`, `edit_obj`, отчёт `?JSON`) | интерфейс |
|---|---|---|---|
| `1` — да | `1`, `true`, `X` | `1` | галка отмечена (`X`) |
| `-1` — нет | `-1`, `0`, `false` | `-1` | галка снята |
| строки нет — не задано | пусто (`t{reqId}=`) — строка удаляется | `null` (в `object/` ключа нет) | галка снята |

- Поле, которого нет в запросе, не меняется.
- Маркер `b{reqId}` формы `edit_obj` без `t{reqId}` — сброс отмеченной галки (строка `1`
  удаляется, становится «не задано»); `-1` маркер не трогает.
- Фильтр `F_{reqId}=%` («не пусто») = «да»: `-1` в него не попадает; `F_{reqId}=!%` — «нет»
  и «не задано» вместе; `F_{reqId}=-1` — только явное «нет».
- Импорт: `-1`/`false`/`0` пишутся как `-1`, пробел — «не задано».
- Флаги-галки запроса («Скрыть» колонки, InTransaction и т.п.) со значением `-1` выключены.
*(issue #5442)*

### Изменить пачку записей одним запросом
```bash
POST /{db}/_m_batch
Fields: _xsrf={xsrf}&token={token}&ops=<массив JSON>
```
`ops` — массив операций, `save`, `set`, `new` и `del` можно смешивать:
```json
[{"op":"save","id":831921,"fields":{"t1078":"1790106240"}}
,{"op":"set", "id":824686,"fields":{"t1085":"12"}}]
```
Каждая операция выполняется обработчиком одиночной команды, поэтому набор проверок
тот же: `op` — какая команда (`_m_save`, `_m_set`, `_m_new`, `_m_del`), `id` — запись
(у `new` — таблица, как в `_m_new/{tableId}`), `up` — родитель для `new`, `fields` — те же
ключи `t{reqId}`, что и в одиночном вызове. У `new` поля необязательны, у `del` не нужны.

Записи, созданные в том же пакете, адресуются значением `":id"` — запись последней
операции `new` — или `":idN"` — запись операции `new` с номером `N` (с нуля). Ссылка
подставляется в `id`, `up` и значения `fields`, если значение равно ей целиком:
```json
[{"op":"new","id":18, "up":1,      "fields":{"t18":"Заказ"}}
,{"op":"new","id":300,"up":":id0", "fields":{"t300":"Позиция 1"}}
,{"op":"new","id":300,"up":":id0", "fields":{"t300":"Позиция 2"}}
,{"op":"new","id":400,"up":":id",  "fields":{"t400":"1"}}
,{"op":"set","id":":id1",          "fields":{"t301":":id2"}}]
```
Строка ответа `new` несёт `"id"` созданной записи и `"type"` — таблицу. Если запись с
таким ключом уже есть, `"id"` — существующая запись и `"warnings"`, и `:id` ведёт на неё.
Ссылка на упавшую `new`, на не-`new` операцию или вперёд — ошибка своей операции, она
не выполняется. Ответ — состояние по каждой операции:
```json
{"results":[{"n":0,"op":"save","id":831921,"ok":true}
           ,{"n":1,"op":"set","id":824686,"ok":false,"error":"нет доступа к реквизиту объекта"}]
,"ok":1,"failed":1}
```
Предел — 1000 операций (`BATCH_OPS_LIMIT`), время обработки — 300 секунд. Ответ всегда
JSON, `?JSON` в адресе не нужен. Копия записи (`copybtn`) и загрузка файлов в пакет не
входят — для них одиночный `_m_save`.

### Удалить запись
```bash
POST /{db}/_m_del/{objId}?JSON=1
# Работает для любых таблиц, включая системные.
# Удаление родителя/пункта меню каскадит на подчинённые записи.
```

### Перенести дочернюю запись к другому родителю (`_m_move`)
```bash
POST /{db}/_m_move/{childRecordId}?JSON=1&up={newParentRecordId}   # + token, _xsrf
```
`up` — id новой родительской **записи**, не таблицы. Сервер проверяет права на
переносимую запись и нового родителя; если тип нового родителя другой, у него должен
быть реквизит этой подчинённой таблицы. После переноса запись становится последней у
нового родителя, порядок у старого пересчитывается сам (`_m_ord` не нужен). Проверка:
`object/{childTableId}/?JSON_OBJ&F_U={newParentRecordId}`.

### Прочитать записи
```bash
GET /{db}/object/{typeId}/?JSON_KV&LIMIT=100&pg=1   # массив под ключом "object"
GET /{db}/object/Заказ/?JSON_KV                     # по имени таблицы (не зная ID)
GET /{db}/table/Заказ/Заказ №100?JSON_OBJ           # конкретная запись по имени
```
Форматы: `JSON_OBJ` — объекты с полями записи (ссылка приходит как `"id:Значение"`,
мульти — `"id1,id2:знач1,знач2"`); `JSON_KV` — «key-value», удобен для UI.

Для рабочих мест и скриптов рекомендована связка **`JSON_OBJ` + `metadata`**: id и
порядок колонок (`reqs[]`) стабильны и переживают аддитивные правки схемы, тогда как
ключи `JSON_KV` — имена колонок — меняются при переименованиях. Ответ `JSON_OBJ` —
массив `{i,u,o,r}`: `i` — id записи, `u` — родитель (`1` у верхнего уровня), `o` —
порядок, `r[0]` — первая колонка, `r[1..]` — реквизиты в порядке `reqs[]` из
`metadata/{typeId}`. Чтение по именам колонок — `?JSON_OBJ&NAMED` (ссылка приходит
`{"id","val"}`, подчинённая таблица — `{"table","count"}`), запись по именам —
`fields={...}`; подробно — [schema-json.md](schema-json.md). Образец практик (кэш
`metadata`, обнаружение дрейфа схемы, пагинация) — `js/integram-table.js`.

Фильтры/параметры:
| Параметр | Назначение |
|---|---|
| `F_U={parentId}` | только дочерние записи родителя `up=<parentId>` (подчинённые таблицы, меню роли) |
| `F_I={recordId}` | только запись с этим id (карточка) |
| `F_{reqId}={val}` | фильтр по колонке |
| `F_{tableId}={val}` | фильтр по **первой колонке** (главному значению): её ключ = id самой таблицы |
| `_count=` | вернуть только число записей (`?JSON_KV&_count=`) |
| `LIMIT=N` · `pg=N` | страница до N записей · номер страницы (1-based) |
| `LIMIT=<offset>,<count>` | постраничная выборка (offset 0-based) |
| `ORDER={colId}` | сортировка по колонке (`-colId` — по убыванию) |

Имя для URL кодировать (`encodeURIComponent`), если есть пробелы/кириллица.
Поиск по имени (таблицы и записи) возвращает **самую старую** подходящую запись
(`ORDER BY id LIMIT 1`), сравнение в MySQL регистронезависимо: две таблицы
«Заказ»/«заказ» дадут ту, что с меньшим id. Таблицам — уникальные имена; где нужна
гарантированная однозначность — числовой id.

### Массовая загрузка / импорт
Набор записей — одним пакетом `_m_batch` (выше). Тысячи записей — файлом:
```bash
POST /{db}/object/{таблица}?JSON&import=1     # multipart, файл в поле bki_file
curl -s -X POST "https://ideav.ru/{db}/object/Клиент?JSON&import=1" \
  -H "X-Authorization: {TOKEN}" -F "_xsrf={XSRF}" \
  -F "bki_file=@clients.bki;type=text/plain"
```
Первая строка файла — `DATA`, далее значения колонок через `;` в порядке метаданных;
справочные колонки — названиями, даты — `ДД.ММ.ГГГГ`, `;` внутри значения — `\;`.
Если первая колонка уникальна, существующие записи обновляются. Файл — до 8 МБ; для
подчинённой таблицы — `F_U={id родителя}` в адресе. Составной ключ уникальности
соблюдается. На Windows/PowerShell следить за кодировкой файла-скрипта (UTF-8),
иначе кириллица ломается — см. монолит
[../integram-app-workflow.md](../integram-app-workflow.md) «Кодировка PowerShell».

### Набор одиночных команд из JS — пул и семафор
Если рабочему месту всё же нужен набор отдельных команд (каждая зависит от своего
ответа сервера), независимые команды отправляются **пулом до пяти потоков**, а на сам
транспорт ставится семафор: пулы вкладываются (лист → его панели → их строки), и
потолок обязан жить в одной точке, через которую идут ВСЕ `_m_*`. Готовый инструмент —
`js/integram-batch.js` (`Batch.runWithConcurrency(tasks, 5)` — результаты в порядке
исходного массива; `Batch.limiter(apiCall, 5)` — семафор на транспорт), своей
реализации не писать. Параллелить нельзя создание потомка до родителя (его id нужен
в `up=`) и любые цепочки «следующий запрос зависит от ответа». И не писать то, что не
менялось: перед записью сравнивать с текущим значением — на массовых путях это снимает
большую часть трафика. Примеры: `download/atex/js/production-planning/10-planning-engine.js`,
`js/dash-import.js`. *(issue #3998, #4477, #4480, #4716)*

## Грабли
- **Симптом:** в уникальной таблице две записи с одним значением, хотя `_m_new` второй должен был ответить «Запись уже существует» (ideav.ru/timepad: 12 гостей одновременно на один слот — 2 слота из 25 записаны дважды) → **Причина:** проверка дубля (`SELECT`) и вставка (`INSERT`) — разные запросы без блокировки; два параллельных запроса оба не находили дубля → **Фикс:** `FindUniqueRecordDuplicateFromRequest` берёт именованную блокировку MySQL `GET_LOCK` на «таблица + родитель + значение» (составной ключ — на таблицу и родителя) и держит её до конца запроса — перед отложенными триггерами её снимает `BtRunDeferred` (`UniqueKeyLock`/`UniqueKeyUnlock`, `index.php`); не дождался за `UNIQUE_LOCK_WAIT` секунд — `409`. Ответ на дубль — по-прежнему не ошибка, а `warning` с id существующей записи: клиент проверяет `warning`. Мерка — `experiments/unique-key-race-5465.test.php`. *(08.11.2026, issue #5465)*
- **Симптом:** снятая галка BOOLEAN после перезагрузки снова «стоит» (снятая фиксация задания возвращается 🔒, партия «не в работе» видна активной) → **Причина:** API отдаёт BOOLEAN как `1` (да) / `-1` (нет) / пусто (не задано), а клиент читал «непусто = да» или сверял только `X` → **Фикс:** «да» — только `1` (и `X` из интерфейсных шаблонов), `-1`/`0`/пусто — нет; в разборе флага `-1` всегда в списке «нет». *(10.11.2026, issue #5475)*
- **Симптом:** имя/номер записи не задаётся (создаётся пустое) → **Причина:** писали главное значение в `t3` вместо ключа таблицы → **Фикс:** главное значение = `t{tableId}` (например `t22`, `t1075`, `t18`), а не `t3`. *(issue #597)*
- **Симптом:** `object/{subTableId}` без фильтра возвращает `0` записей / «таблица пустая», хотя данные есть → **Причина:** подчинённая таблица хранит записи как дочерние (`up`=id родителя); без `F_U` сервер отдаёт только уровень `up=1` → **Фикс:** читать по родителям — для каждой записи родителя запрашивать `object/{subTableId}?…&F_U=<parentId>`. Опасно перед удалением колонки. *(monolith §3.5)*
- **Симптом:** при пагинации часть записей дублируется → **Причина:** между страницами `LIMIT`/`pg` возможны дубли → **Фикс:** дедуплицировать по `id` при склейке страниц. *(monolith §3.5)*
- **Симптом:** ссылочное (ref) поле «не сохраняется» → **Причина:** в `t{refReqId}` передали отображаемое имя, а не id записи → **Фикс:** значение ref-поля = id записи целевой таблицы (см. [schema.md](schema.md)). *(monolith §6.4)*
- **Симптом:** реквизит не удаётся ОЧИСТИТЬ: галка BOOLEAN остаётся стоять, стёртое поле возвращается прежним значением, хотя `_m_set` отвечает успехом → **Причина:** клиент выбрасывал пустые значения из тела запроса (`if (params[k] !== '') body.set(...)`), и «очистка» просто не доезжала; писались только непустые поля → **Фикс:** пустое значение = очистка, слать его обязательно (`t{req}=`); не отправлять только `undefined`/`null` («поле не трогаем»). Галку BOOLEAN сбрасывать пустым значением `t{req}=` (строка удаляется — «не задано»); `t{req}=0` / `-1` пишет явное «нет» (`-1`), см. «Галка (BOOLEAN)» выше. Пустое `t16411=` стирает DATETIME «Закончено». *(24.07.2026, issue #4366; #5442)*
- **Симптом:** фильтр по ссылочной колонке id записи-цели (`object/{t}/?JSON_KV&F_{refReqId}=1000175`) ничего не находит, хотя ссылка записана → **Причина:** простое значение фильтра сравнивается с **подписью** ссылки (главным значением цели), а не с id; поиск по id — префикс `@` (`index.php`, `Construct_WHERE`, ветка «Search by ID») → **Фикс:** `F_{refReqId}=@{id}`, несколько — `F_{refReqId}=@IN(id,id)`; условия на разные колонки складываются по И. Так пульт высечки читает смену станка: `F_{Станок}=@{id}&F_{Тип}=@{id}`. *(31.10.2026, issue #5330)*
- **Симптом:** фильтр по первой колонке (`object/{tableId}/?JSON_OBJ&F_{имя колонки}=…`) не отбирает ничего или роняет SQL → **Причина:** ключ фильтра первой колонки — **id самой таблицы**, как и при записи `t{tableId}` (`index.php`, `&uni_obj_all`: `$cur_typ = $id`) → **Фикс:** `F_{tableId}={значение}`, например поиск планшета по токену в 673803 — `object/673803/?JSON_OBJ&F_673803={токен}`. Значения с `!`, `>`, `<`, `%`, `@`, `.` меняют смысл условия (`Construct_WHERE`) — ключи-токены генерировать hex. *(09.08.2026, issue #4666)*
- **Симптом:** поле читается пустым из `object/{tableId}/?JSON_OBJ`, хотя в записи значение есть → **Причина:** это **главное значение** записи (`r[0]`), а не реквизит: в `metadata?JSON` реквизита с таким именем нет, поиск колонки по имени даёт `-1`.
