# Web-socket: живые таблицы, уведомления, события для внешних систем

## На пальцах

Открытая таблица обновляется сама, когда её записи меняет другой пользователь, триггер или
внешняя система. Изменённые строки приходят готовыми и подставляются на месте, без
перечитывания. Новые записи копятся на плашке «Добавлено N — показать». Пользователю можно послать уведомление: оно всплывает на любой открытой
странице базы. Внешняя система подписывается на изменения таблицы и не опрашивает API по таймеру.

Соединения держит отдельный демон `ws-server/` (Node, без зависимостей), потому что PHP-ядро
постоянных соединений не держит. Ядро после каждого запроса с записью сообщает демону, какие строки
изменились: только адреса, без значений. Значения демон берёт у ядра обычным листингом
`object/<тип>/?JSON_OBJ`, одним запросом на группу подписчиков с одинаковыми правами и входом
участника группы. Поэтому на строки действуют все права и маски ядра.

Подписчик сообщает демону, какие записи у него на экране. Правка или удаление записи доходят
только до тех, у кого она на экране. Новая запись доходит только счётчиком, без id и только до
тех, кому она видна. Запись, скрытая маской, не сообщается ничем: ни значением, ни id.

```
браузер / внешний клиент ──ws──► nginx /ws ──► ws-server :8790 ──► GET /<база>/ws_auth?JSON (ядро)
index.php ── POST /push (HMAC) ──► ws-server ──► GET /<база>/object/<тип>/?JSON_OBJ&F_<тип>=@IN(…)
                                    │             (раз на группу прав, входом её участника)
                                    └──► подписчикам: строки, «убрать», счётчик новых
```

## Справочник

### Ядро (`include/ws_push.php`, `index.php`)

- `logChange()` (журнал изменений) отдаёт каждую записанную строку в `Ws_collect()`.
  Строки авторизации (TOKEN, XSRF, ACTIVITY, PASSWORD, SECRET) пропускаются.
- После ответа `Ws_flush()` (shutdown) строит события и отправляет их одним POST на `WS_PUSH_URL`.
  Подпись лежит в заголовке `X-Ws-Signature` = HMAC-SHA256(тело, `WS_SECRET`).
  Таймаут 500 мс: если демон лежит, запрос пользователя его не ждёт.
- Событие данных: `{"k":"change","op":"insert|update|delete","id","up","t","types":[…],"chain":[[id,тип],…]}`.
  `chain` — строка и её предки до объекта первого уровня (`up=1`). Подписчик таблицы `t` получает
  изменение ближайшей записи типа `t` из цепочки; правка значения реквизита или подчинённой
  записи для неё — правка записи. `types` — типы цепочки, при переносе с типами старого места.
- Строка, созданная и поправленная в одном запросе, — `insert`.
- Правка метаданных (тип `up=0` или определение его реквизита) даёт `{"k":"schema","t":<тип>}`.
- Сырой SQL, DDL, сводка импорта или больше `WS_MAX_CHANGES` (500) строк за запрос дают
  `"bulk":true`, то есть «перечитать всё».
- Транзакция запроса (InTransaction): откат или выход без COMMIT — её изменения не рассылаются.
- `GET /<база>/ws_auth?JSON[&t=<тип>]` возвращает `{user,user_id,role,fp[,t,read,masked]}`. Через
  него демон проверяет вход клиента и право подписки.
  `fp` (`Ws_rights_fp`) — хеш роли и прав с уже подставленными масками (`[USER]`, `[Запрос]`
  подставляет `getGrants` на входе): одинаковый `fp` — одинаково видимые строки. `masked`
  (`Ws_type_masked`) — у пользователя есть маска на таблицу, её колонку или таблицу-родителя.
  Право подписки (`Ws_type_readable`): явное право на тип
  или на его строку-массив; иначе подчинённая таблица наследует право родителя, а таблица первого
  уровня проверяется по `Grant_1level`.
- `POST /<база>/_m_notify` (`_xsrf`): `to` — логины через запятую (до 50), `msg` — текст (до 2000),
  `link` — `/…` или `http(s)://…`. Гостю запрещено. Из PHP: `Ws_notify($логины, $data)`.

Настройки (`include/connection.php`, переменные окружения):

| Константа | Переменная | Пример |
|---|---|---|
| `WS_PUSH_URL` | `INTEGRAM_WS_PUSH_URL` | `http://127.0.0.1:8790/push` |
| `WS_SECRET` | `INTEGRAM_WS_SECRET` | длинная случайная строка, та же у демона |
| `WS_PUBLIC_URL` | `INTEGRAM_WS_PUBLIC_URL` | `/ws` (тот же хост) или `wss://host/ws` |

Пустой `WS_PUSH_URL` или `WS_SECRET` — ядро ничего не копит и не отправляет. Пустой
`WS_PUBLIC_URL` — браузер не подключается.

### Демон (`ws-server/server.js`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `WS_CORE_URL` | — (обязательна) | адрес ядра для `ws_auth`, например `https://ideav.ru` |
| `WS_SECRET` | — (обязательна) | равна `INTEGRAM_WS_SECRET` ядра |
| `WS_PORT` / `WS_HOST` | `8790` / `127.0.0.1` | где слушать |
| `WS_ALLOWED_ORIGINS` | пусто | сайты через запятую, с которых браузер может подключаться, кроме своего хоста |
| `WS_REAUTH_SEC` | `300` | как часто перепроверять вход, права подписок и `fp` |

- Подключение: `GET /ws?db=<база>` с `Upgrade: websocket`. Вход — куки `idb_<база>` (ядру
  уходит только он) или заголовок `X-Authorization` / `Authorization`. Токен в строке адреса не
  принимается: он попал бы в журналы.
- Подключение со страницы чужого сайта (`Origin` не свой и не из `WS_ALLOWED_ORIGINS`) получает
  403. Иначе чужой сайт подключился бы с куки пользователя.
- Сообщения клиента:
  - `{"op":"sub","t":500,"shown":[id…]}` — подписка и записи на экране;
  - `{"op":"sub","t":500,"feed":true}` — лента для внешней системы: все видимые изменения;
  - `{"op":"shown","t":500,"ids":[…]}` — новый список записей на экране (до 5000);
  - `{"op":"unsub","t":500}`, `{"op":"ping"}`.
- Сообщения демона:
  - `{"op":"hello","db","user"}`, `{"op":"sub","t","ok"}`;
  - `{"op":"rows","t","by","rows"?,"remove"?,"added"?,"stale"?}` (`ws-server/lib/hub.js`):
    - `rows` — новые значения записей на экране, `{i,u,o,r}` как у `JSON_OBJ` (ленте — всех видимых);
    - `remove` — id записей с экрана, которые удалены или больше не видны по маске;
    - `added` — родители (`u`) новых видимых записей, для счётчика; id новых записей не уходят;
    - `stale` — `schema` (правка схемы), `bulk` (массовое изменение или больше 200 записей на
      группу), `lost` (ядро не отдало строки): данные устарели, строк в сообщении нет;
  - `{"op":"notify","from","data"}`;
  - `{"op":"unsub","t","revoked":true}` — право снято.
- Строки: `GET /<база>/object/<t>/?JSON_OBJ&F_<t>=@IN(<id…>)&LIMIT=0,<N>` — один запрос на группу
  (база, таблица, `fp`) на пачку, входом первого участника группы, чей вход ядро приняло.
  Запрашиваются записи на экране участников и новые записи; правка записи, которой нет ни у кого
  на экране, ядро не нагружает.
- Ленте (`feed`) при `masked` удаления не сообщаются: удалённая запись могла быть скрыта маской.
- Вход отозван — закрытие с кодом `4401`, переподключаться бесполезно.
- `GET /health` → `{"clients":N}`.

### Браузер (`js/ws-client.js`, компонент таблиц)

- `main.html` задаёт `wsUrl = '{_global_.ws}'` и подключает `js/ws-client.js`.
- `IntegramWS.subscribe(typeId, fn)` возвращает функцию отписки `off`; `off.shown([id…])` — записи
  на экране (демону уходит объединение по всем таблицам типа на странице). `fn` получает
  `{by, rows, remove, added, stale}`.
- `IntegramWS.onNotify(fn)`. По умолчанию уведомление показывается через `showToast`.
- После обрыва клиент переподключается с паузой 1 → 30 с, повторяет подписки с записями на
  экране и передаёт подписчикам `stale:"lost"`: изменения за время обрыва потеряны.
- `integram-table` с источником `table` (`object/`) подписывается на свой тип (`liveAttach`) и после
  каждой загрузки сообщает записи на экране:
  - `rows` — подставляет строки на месте, без запросов; строка ушла к другому родителю
    подчинённой таблицы — убирается; строка другой длины, чем колонки, — плашка схемы;
  - `remove` — убирает строки;
  - `added` — плашка «Добавлено N — показать» над таблицей, по нажатию `reload()`; новые записи
    под другим родителем и свои в активной вкладке не считаются;
  - `stale` — плашка «Данные изменились — обновить» (`reload()`), для схемы — «Структура таблицы
    изменилась — обновить» (`refreshData()`);
  - пока ячейка в правке или новая строка не сохранена, изменения ждут;
  - отключается опцией `live: false`. Таблица на отчёте (`report/`) не подписывается.

### Внешний клиент

```js
const WebSocket = require('ws');   // npm-пакет ws: встроенный WebSocket заголовков не передаёт
const ws = new WebSocket('wss://ideav.ru/ws?db=acme', { headers: { 'X-Authorization': TOKEN } });
ws.onmessage = (e) => console.log(JSON.parse(e.data));
ws.onopen = () => ws.send(JSON.stringify({ op: 'sub', t: 500, feed: true }));
```

Встроенный `WebSocket` Node и браузера заголовков не передаёт. Внешнему клиенту с токеном нужен
клиент с заголовками, например пакет `ws`.

### Выкладка

1. Демон — systemd-юнит:

   ```ini
   [Service]
   WorkingDirectory=/var/www/crm/ws-server
   ExecStart=/usr/bin/node server.js
   Environment=WS_CORE_URL=https://ideav.ru WS_SECRET=… WS_PORT=8790
   Restart=always
   User=www-data
   ```

2. nginx в server-блоке сайта:

   ```nginx
   location = /ws {
       proxy_pass http://127.0.0.1:8790;
       proxy_http_version 1.1;
       proxy_set_header Upgrade $http_upgrade;
       proxy_set_header Connection "upgrade";
       proxy_set_header Host $host;
       proxy_read_timeout 3600s;
   }
   ```

   Вариант без nginx — свой порт TLS у демона (так на ideav.ru: там Apache в режиме prefork, см.
   «Грабли»). Браузер ходит на `wss://<сайт>:8443/ws`, на этом порту открыт только `/ws`. Ядро
   по-прежнему шлёт события на `http://127.0.0.1:8790/push`. Сертификат сайта доступен только root —
   systemd передаёт его службе через `LoadCredential`, а path-юнит перезапускает службу после
   продления:

   ```ini
   # /etc/systemd/system/integram-ws.service, секция [Service]
   LoadCredential=cert:/var/www/httpd-cert/www-root/ideav.ru_le2.crtca
   LoadCredential=key:/var/www/httpd-cert/www-root/ideav.ru_le2.key
   Environment=WS_TLS_PORT=8443 WS_TLS_CERT=%d/cert WS_TLS_KEY=%d/key
   Environment=WS_ALLOWED_ORIGINS=https://ideav.ru,https://www.ideav.ru

   # /etc/systemd/system/integram-ws-cert.path
   [Path]
   PathChanged=/var/www/httpd-cert/www-root/ideav.ru_le2.crtca
   Unit=integram-ws-cert.service
   [Install]
   WantedBy=multi-user.target

   # /etc/systemd/system/integram-ws-cert.service
   [Service]
   Type=oneshot
   ExecStart=/usr/bin/systemctl restart integram-ws.service
   ```

   `WS_ALLOWED_ORIGINS` обязателен: `Host` на своём порту — `ideav.ru:8443`, он не равен `Origin`
   страницы.

3. Ядру — `INTEGRAM_WS_PUSH_URL`, `INTEGRAM_WS_SECRET`, `INTEGRAM_WS_PUBLIC_URL=/ws`
   (окружение php-fpm или `include/connection.php` сервера). Для своего порта
   `INTEGRAM_WS_PUBLIC_URL=wss://<сайт>:8443/ws`.

Проверка: `curl -s 127.0.0.1:8790/health`, затем открыть таблицу в двух браузерах и изменить
запись в одном.

## Грабли

- Симптом: при сотне открытых вкладок сайт перестаёт отвечать. Причина: Apache в режиме
  `mpm_prefork` держит на каждое web-socket-соединение через `mod_proxy_wstunnel` отдельный процесс
  (предел `MaxRequestWorkers` 150). Фикс: свой порт TLS у демона мимо Apache или nginx перед
  демоном (#5269).
- Симптом: плашка «Добавлено N» считает и записи, которые не проходят фильтр таблицы. Причина:
  фильтры и сортировку экрана знает только браузер, демон проверяет видимость по правам и
  маскам. Фикс: плашка ведёт на перечитывание с фильтрами (#5269).
- Симптом: запись, которая правкой попала под маску пользователя (раньше была скрыта), не
  появляется ни строкой, ни на плашке. Причина: её не было на экране, и это не `insert`. Фикс:
  видна после перечитывания (#5269).

- Симптом: браузер получает 403 при подключении, хотя сайт свой. Причина: nginx не передаёт
  `Host`, и демон сравнивает `Origin` с `127.0.0.1:8790`. Фикс: `proxy_set_header Host $host` или
  сайт в `WS_ALLOWED_ORIGINS` (#5269).
- Симптом: события не приходят, а в журнале ядра пусто. Причина: не задан один из
  `INTEGRAM_WS_PUSH_URL` / `INTEGRAM_WS_SECRET`, или секрет ядра не равен `WS_SECRET` демона
  (на `/push` демон отвечает 401). Фикс: одинаковый секрет по обе стороны (#5269).
