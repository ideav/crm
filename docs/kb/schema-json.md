# Схема одним JSON и поля по именам
> Часть базы знаний Integram. Индекс: [docs/kb/README.md](README.md)

## На пальцах (для человека)
Маленькое приложение (таблицы, ссылки, роли с правами, отчёт) собирается **одним вызовом**
`_d_schema`: в него передаётся описание по именам — «таблица Договор, поле Заявка — ссылка на
Заявку, роль Юрист пишет Договоры и читает Заявки». Ядро само находит, что уже есть, и создаёт
недостающее; повторный вызов того же описания ничего не дублирует. В ответе — id всего
описанного. Записи тоже можно писать и читать по именам полей, а не по числовым ключам `t<id>`.
Это первый способ для агента; пошаговые `_d_*`/`_m_*` с кодами ([schema.md](schema.md),
[crud.md](crud.md), [roles.md](roles.md)) — для того, чего описание не покрывает.

> ────────── дальше — справочник для агента ──────────

## Операции (для агента)

Авторизация и `_xsrf` — [00-start.md](00-start.md). Описание передаётся полем формы
`json=<JSON>` или телом запроса `Content-Type: application/json` (тогда `_xsrf` — ключом в
том же теле). Ответ всегда JSON.

### Схема: `POST /{db}/_d_schema?JSON`
```json
{"tables": [
   {"name": "Компания", "unique": true, "fields": [
      {"name": "ИНН"},
      {"name": "Лимит", "type": "NUMBER"}]},
   {"name": "Заявка", "fields": [
      {"name": "Компания", "ref": "Компания", "required": true},
      {"name": "Сумма заявки", "type": "SIGNED"}],
    "children": [
      {"name": "Позиция заявки", "fields": [{"name": "Кол-во", "type": "NUMBER"}]}]},
   {"name": "Договор", "fields": [
      {"name": "Заявка", "ref": "Заявка"},
      {"name": "Сумма договора", "type": "SIGNED"},
      {"name": "Дата договора", "type": "DATE"}]}],
 "reports": [
   {"name": "Договоры", "columns": [
      {"name": "Договор", "table": "Договор"},
      {"name": "Заявка", "table": "Договор", "field": "Заявка"},
      {"name": "Сумма", "table": "Договор", "field": "Сумма договора", "func": "SUM"}]}],
 "roles": [
   {"name": "Юрист", "description": "Ведёт договоры", "grants": [
      {"table": "Договор", "level": "WRITE"},
      {"table": "Заявка", "level": "READ"},
      {"table": "Компания", "level": "READ"},
      {"table": "Заявка", "field": "Сумма заявки", "level": "BARRED"},
      {"report": "Договоры", "level": "READ"}]}]}
```
Ответ:
```json
{"ok": true,
 "tables": {"Компания": {"id": 465, "created": true, "fields": {"ИНН": 471, "Лимит": 473}},
            "Заявка": {"id": 466, "created": true, "fields": {"Компания": 475, "Сумма заявки": 477}},
            "Позиция заявки": {"id": 467, "created": true, "fields": {"Кол-во": 479}, "parent": 466, "req": 469},
            "Договор": {"id": 468, "created": true, "fields": {"Заявка": 481, "Сумма договора": 483, "Дата договора": 485}}},
 "reports": {"Договоры": {"id": 486, "created": true, "columns": {"Договор": 487, "Заявка": 489, "Сумма": 491}}},
 "roles": {"Юрист": {"id": 494, "created": true, "grants": [
            {"object": "«Договор»", "object_id": 468, "id": 496, "level": "WRITE", "created": true}, …]}},
 "created": 24, "updated": 0, "existing": 0}
```
`fields` в ответе — id реквизитов: это ключи `t<id>` для старых вызовов и фильтров `F_<id>`.

**Таблица** (`tables[]`, подчинённые — в `children[]` родителя, вложенность любая):

| Ключ | Что |
|---|---|
| `name` | имя таблицы = имя её первой колонки (главного значения записи) |
| `type` | тип первой колонки, по умолчанию `SHORT` |
| `unique` | `true` — справочник: главное значение уникально |
| `fields[]` | поля |
| `children[]` | подчинённые таблицы (табличные части): записи создаются с `up=<id записи родителя>` |

**Поле** (`fields[]`):

| Ключ | Что |
|---|---|
| `name` | имя колонки |
| `type` | `SHORT` (по умолчанию), `CHARS`, `MEMO`, `NUMBER`, `SIGNED`, `DATE`, `DATETIME`, `BOOLEAN`, `FILE`, … — или синонимы `STRING`, `TEXT`, `INT`, `DECIMAL`/`FLOAT`/`MONEY`, `BOOL` |
| `ref` | имя таблицы-цели: поле — ссылка (FK). Имя поля, отличное от цели, становится псевдонимом |
| `multi` | ссылка на несколько записей |
| `required` | обязательное |
| `key` | часть составного ключа уникальности |
| `default` | значение по умолчанию (`[TODAY]`, `[USER_ID]`, …) |

**Роль** (`roles[]`): `name`, `description`, `grants[]`. **Право** (`grants[]`):

| Ключ | Что |
|---|---|
| `table` (+ `field`) | таблица или её поле |
| `report` | отчёт по имени |
| `object` | служебный объект: `types` (редактор структуры), `all` (все таблицы), `files` (файлы), или id |
| `level` | `READ`, `WRITE` или `BARRED` |
| `mask` | маска строк (`[USER_ID]`, `[USER]`, id, …) — см. [roles.md](roles.md) «Маски» |
| `export`, `delete` | флаги «Экспорт» и «Удаление» |

**Отчёт** (`reports[]`): `name`, `columns[]`. **Колонка**: `name` (имя в отчёте, ключ в
`JSON_KV` и фильтр `FR_<имя>`), источник `table` (+ `field`; без `field` — главное значение
таблицы) или вычисляемая `formula` (текст формулы сохраняется как есть), `func`
(`SUM`/`COUNT`/`MAX`/…), `hide`, `sort`, `from`/`to` (фильтры колонки). Как ядро связывает
колонки разных таблиц и считает агрегаты — [queries.md](queries.md) и
[../integram-reports.md](../integram-reports.md).

**Правила:**
- Существующее находится по имени: таблица — по имени, поле — по имени колонки (псевдоним или
  имя типа), роль, отчёт, колонка отчёта — по имени, право — по роли и объекту. Повторный вызов
  того же описания: `created: 0`.
- У существующего поля меняются только флаги `required`/`multi`/`key`/`default`, у таблицы —
  `unique`, у права — уровень, маска и флаги, у колонки отчёта — её параметры. Тип поля и цель
  ссылки не меняются: расхождение — ошибка в `errors`, поле остаётся как было.
- Ошибки описания (неизвестный тип, нет таблицы-цели, вторая ссылка на ту же таблицу, неверный
  уровень) проверяются **до записи**: ответ `400 {"ok":false,"errors":[…]}`, в базе ничего не
  меняется. Ошибки отдельных ролей, прав и колонок (например, нет прав на запись в таблицу
  ролей) — в `errors` при `ok:false`; остальное описание применяется (транзакций в платформе нет,
  как и у `_m_batch`). Повтор вызова после исправления безопасен.
- Права вызывающего: `_d_schema` — команда структуры (нужен доступ к редактору типов, как у
  `_d_*`); роли, права и отчёты пишутся обработчиками `_m_new`/`_m_set` с их проверками.

### Записи по именам полей
```bash
POST /{db}/_m_new/Договор?JSON      # таблица — именем или id
     fields={"Договор":"Д-1","Заявка":"З-1","Сумма договора":300}  up=1
POST /{db}/_m_set/{id записи}?JSON
     fields={"Сумма договора":350,"Дата договора":"2026-10-01"}
```
То же телом JSON: `{"up":1,"fields":{…},"_xsrf":"…"}`. Ключ `fields`:
- имя колонки (как в `metadata`: псевдоним или имя типа, без учёта регистра);
- имя самой таблицы — главное значение записи (вместо `t<id таблицы>`);
- прежний ключ `t<id>` — как раньше.

Ссылка — id записи или её главное значение: запись ищется в таблице-цели и должна найтись
ровно одна (иначе ошибка с подсказкой дать id). Множественная ссылка — массив. Неизвестное
имя — ошибка `400` со списком полей таблицы.

В `_m_batch` имена пишутся прямо ключами `fields`, а таблица операции `new` — именем в `id`:
```json
[{"op":"new","id":"Договор","up":1,"fields":{"Договор":"Д-2","Заявка":"З-1","Сумма договора":200}},
 {"op":"set","id":":id0","fields":{"Сумма договора":250}}]
```
В пакете имя, которого нет в таблице, не роняет операцию: оно называется в `warnings`
операции («Нет полей: …»), а поле не пишется.

### Чтение по именам: `object/{таблица}/?JSON_OBJ&NAMED`
```json
[{"id":512,"up":1,"ord":1,
  "Заявка":"З-1",
  "Позиция заявки":{"table":467,"count":1},
  "Компания":{"id":509,"val":"Альфа"},
  "Сумма заявки":"500.50"}]
```
Те же записи и фильтры, что у `JSON_OBJ` (`F_I`, `F_U`, `F_<id>`, `LIMIT`), с теми же правами:
закрытое `BARRED` поле не приходит. Ссылка — `{"id","val"}` (множественная — массив),
подчинённая таблица — `{"table","count"}`; её записи — `object/{table}/?JSON_OBJ&NAMED&F_U={id записи}`.

## Грабли
- **Симптом:** `object/Заявка/?JSON_OBJ` (имя таблицы и косая черта в конце) отдаёт `[]`, а `object/466/?JSON_OBJ` — записи → **Причина:** пустой сегмент после имени считался именем записи и находил ссылочный тип таблицы (строку `up=0, val=''`) → **Фикс:** ядро не ищет запись по пустому сегменту и ищет её только среди записей (`up!=0`); на старом ядре — без косой черты или по id. *(23.10.2026, issue #5242)*
- **Симптом:** `_d_schema` отвечает «имя занято типом поля другой таблицы» → **Причина:** типы в базе общие: поле «Лимит» любой таблицы — это тип «Лимит», и таблица с тем же именем стала бы тем же типом, а поле — подчинённой таблицей → **Фикс:** назвать таблицу иначе (или сделать поле ссылкой на справочник). *(23.10.2026, issue #5242)*
- **Симптом:** две ссылки на одну таблицу («Заказчик» и «Плательщик» → «Компания») в описании — ошибка → **Причина:** ссылка на таблицу у записи одна (см. [schema.md](schema.md) «Создать ссылку») → **Фикс:** вторую роль — текстом или отдельным справочником. *(23.10.2026, issue #5242)*
