# Движок запросов Интеграма: возможности на конкретных примерах

Ответ на возражение (issue #5181):

> «Единая таблица со структурой и данными может упрощать динамическое создание сущностей
> и избавлять от части миграций. Но это не означает автоматически, что система лучше
> справляется с аналитическими запросами, связями, транзакционной целостностью, изменением
> типов, многопользовательской нагрузкой и сопровождением больших приложений.»

Документ разбирает каждый пункт по коду ядра (`index.php`) и по отчётам, которые реально
работают в проектах (`templates/`, `docs/`). Ссылки вида `index.php:NNNN` — на ветку `main`
на момент написания.

**Коротко.** Запрос Интеграма — декларативное определение, которое ядро компилирует
в **один** SQL-запрос MySQL со всеми JOIN, GROUP BY,
HAVING, подзапросами и `WITH RECURSIVE`. Всё, что выражается в SQL над реляционной моделью,
выражается и здесь — потому что на выходе тот же SQL.

---

## 1. Как устроен запрос

Запрос (отчёт) хранится в той же таблице, что и данные: запись типа `REPORT = 22`,
колонки — подчинённые записи `REP_COLS = 28`. Атрибуты колонки (`index.php:682-704`):

| Атрибут | Тип | Назначение |
|---|---|---|
| Имя в отчёте | 100 | имя колонки и ключ параметров `FR_<имя>` |
| Функция | 63 | агрегат или служебная функция |
| Формула | 101 | SQL-выражение, `[THIS]`, ссылки на другие колонки |
| Фильтр от / до | 102 / 103 | условие WHERE |
| HAVING от / до | 105 / 106 | условие на агрегат |
| Сортировка | 109 | приоритет, минус — DESC |
| Скрыть | 107 | колонка участвует в условиях, но не выводится |
| Значение (SET) | 132 | выражение для массового изменения данных |
| JOIN / ON | 44 / 265 / 266 | явное соединение с псевдонимом |

Компилятор — `Compile_Report()` (`index.php:3383`). Всё определение читается одним
запросом и раскладывается в `STORED_REPS`, после чего строится SQL:

1. **Главная таблица** — родитель первой колонки (`:3635-3641`).
2. **Соединения выводятся из метаданных** (`:3623-3835`): ядро само находит путь между
   таблицами отчёта — через ссылку «на нас», ссылку «от нас», подчинённую таблицу или
   родителя — и строит `LEFT JOIN`. Пользователь не пишет условия соединения: он выбирает
   колонки, путь вычисляется.
3. **Несколько ссылок на одну таблицу** разрешаются по тому, какая ссылочная колонка стоит
   в отчёте (`refAnchors()`, `:3364-3381`).
4. **Явный JOIN** (запись типа 44) с псевдонимом позволяет подключить одну таблицу дважды
   или соединить по произвольному условию (`:3646-3691`).
5. **Каждая присоединённая таблица оформляется производной таблицей** (`LEFT JOIN (SELECT …)`)
   со своим `GROUP BY`, если внутри агрегат (`:4816-4869`). Это защищает от размножения
   строк при агрегации по нескольким подчинённым таблицам.

Пример. Колонки: «Заказ» и «Сумма» с функцией `SUM`. Получается:

```sql
SELECT a1000.val AS 'order', SUM(CAST(a1010.val AS DOUBLE)) AS 'amount'
FROM db a1000
  LEFT JOIN db a1010 ON a1010.up=a1000.id AND a1010.t=1010
WHERE a1000.up!=0 AND a1000.t!=a1000.up AND length(a1000.val)!=0 AND a1000.t=1000
GROUP BY a1000.val
```

Числовые типы и даты приводятся через `CAST` при агрегации и сортировке (`:3907-3917`).
Сгенерированный SQL виден в трассировке (`:4876`).

## 2. Аналитические запросы

### 2.1. Что поддерживает компилятор

| Возможность | Где в ядре | Как задаётся |
|---|---|---|
| Агрегаты `SUM, COUNT, AVG, MIN, MAX, GROUP_CONCAT, JSON_ARRAYAGG` | `:3401`, `:3895-3944` | функция колонки |
| Любая SQL-функция над полем | `:3937-3944` | функция колонки: `FUNC(field)` |
| Автоматический `GROUP BY` по неагрегированным колонкам | `:4243-4268` | есть хоть один агрегат |
| `HAVING` | `:4269-4297` | HAVING от / до |
| Вычисляемые колонки — свободное SQL-выражение | `:4068-4118` | формула без источника |
| Ссылки на другие колонки в формуле | `:4685-4764` | `[Имя колонки]` |
| Подзапросы — любой запрос как вложенный | `:4595-4683` | `[Имя запроса]` в формуле, фильтре, ORDER, GROUP, HAVING |
| Рекурсия `WITH RECURSIVE` | `:4890-4932` | функция `RECURSIVE` у первой колонки |
| Служебные поля записи | `:3843-3860` | `abn_ID`, `abn_UP`, `abn_ORD`, `abn_TYP`, `abn_REQ` |
| Контекст и даты | `BuiltIn()`, `:3075-3117` | `[TODAY]`, `[NOW]`, `[MONTH_AGO]`, `[USER_ID]`, `[ROLE_ID]`… |
| Параметры извне | `:4381-4558`, `:3564-3594` | `FR_`/`TO_`, `_request_.X` |
| Колонки и итоги по запросу | `:3473-3513` | `?SELECT=…`, `?TOTALS=col:SUM` |
| Сортировка, пагинация, подсчёт | `:4125-4365`, `:4766-4802`, `:4968-4977` | `?ORDER`, `?LIMIT`, `?RECORD_COUNT` |

Синтаксис фильтра (`Construct_WHERE`, `:2007-2278`): равенство, `%маска%` (`LIKE`),
`!` (отрицание), `%` / `!%` (`IS [NOT] NULL`), `>`, `>=`, `<`, `<=`, `IN(…)`, `@id`,
`REGEXP:…`, диапазон `100..500` (`BETWEEN`), пара от/до, `[Запрос]` — подзапрос.

### 2.2. Подзапросы

Любое `[Имя]` в тексте запроса ядро пробует как имя другого запроса: компилирует его без
выполнения и подставляет `(<SQL>)` (`:4595-4683`). Вложенность не ограничена одним уровнем —
вложенный запрос сам может содержать `[…]`. Если у запроса задано «значение при пустом»,
подзапрос оборачивается в `COALESCE` (`:4935-4937`).

Тот же механизм работает в фильтре списков: реквизит с выпадающим списком из запроса
фильтруется через `IN(<id из запроса>)` (`:8100-8131`).

### 2.3. Рекурсия

Функция `RECURSIVE` у первой колонки заменяет запрос рекурсивным CTE (`:4890-4932`).
Поддерживаются оба вида иерархий:

```sql
-- дерево по ссылке на собственную таблицу
WITH RECURSIVE c AS (
  SELECT id, 0 t FROM db WHERE t=$typ AND up!=0 AND t!=up $cond
  UNION SELECT ref.up id, ref.t FROM db ref INNER JOIN c ON c.id=ref.t
        WHERE ref.val='<реквизит>' LIMIT N)
SELECT DISTINCT id FROM c

-- дерево подчинённых записей (по up)
WITH RECURSIVE c AS (
  SELECT id, 0 t FROM db WHERE t=$typ AND up!=0 AND t!=up AND val!='' $cond
  UNION SELECT ref.id, ref.t FROM db ref INNER JOIN c ON c.id=ref.up WHERE ref.t=$typ LIMIT N)
SELECT DISTINCT id FROM c
```

Корень обхода задаётся фильтром колонки или **другим запросом** (`AND id IN(<подзапрос>)`).
Рекурсивный запрос возвращает множество id и используется как подзапрос в других запросах —
так строятся, например, «все подразделения ниже данного» или «все пункты меню, доступные
роли».

### 2.4. Примеры из проектов

**xcom: сопоставление заявки с каталогом** — `docs/xcom_reports.json:44-139`, запрос
`mass_match`. Заявка покупателя (RFP) и номенклатура (SKU) напрямую не связаны: они
соединяются через общий справочник «Токен» множественными ссылками — связь
«многие-ко-многим» через третью сущность. В одном запросе:

```text
Токенов = COUNT(токен)
токены  = GROUP_CONCAT(токен)
Вес     = COUNT(DISTINCT токен) + COUNT(ТокенТовар) + COUNT(ТокенБренд) + COUNT(ТокенМодель)   -- сортировка 2, DESC
ТММ     = (COUNT(ТокенТовар)>0 AND COUNT(ТокенБренд)>0 AND COUNT(ТокенМодель)>0)               -- сортировка 1, DESC
```

Это ранжирование кандидатов весовой функцией над агрегатами, с параметром `FR_RFPID` и
лимитом. Запрос «Сопоставление» наследует это определение (`:140-145`).

**xcom: частотность токенов** — `docs/xcom_reports.json:194-238`, `token_usage`. Справочник
плюс два `COUNT` по двум разным таблицам, которые на него ссылаются: сколько номенклатур и
сколько заявок использует каждый токен. Обратная связь «кто ссылается на значение» в
разрезе двух источников.

**xcom: токенизация — ETL внутри базы** — `docs/xcom_reports.json:3-43`. Колонке задано
SET-выражение: цепочка из 8 `REGEXP_REPLACE` и 3 `REPLACE` (нормализация «ё», удаление
предлогов, разделение цифр и букв). GET показывает превью «было ⇒ станет», POST с
подтверждением применяет. Фильтр `!%` берёт только неразмеченные записи, поэтому прогон
идемпотентен (`docs/xcom-matching/guide-integrator.md:120`).

**atex: сквозной конвейер заказа** — `docs/integram-reports.md:60-102`, `order_pipeline`.
Цепочка из пяти таблиц Заказ → Позиция → Обеспечение → Резка → Партия ГП, 18 колонок:
статусы каждой стадии, ширина, метраж, план и факт. Незавершённые стадии приходят пустыми
(`LEFT JOIN`). Два таких запроса заменили в дашбордах около десяти выгрузок
(`docs/integram-reports.md:39-41`).

**atex: рабочее место упаковщика** — `docs/integram-reports.md:723-769`, `packers`.
Колонка `nk_stock` — вложенный запрос: остаток «Склад НК» по всем партиям артикула за всё
время, независимо от фильтров самого запроса (неделя, место). По смыслу это коррелированная
агрегация. Колонка `jumbos` собирает все номера джамбо задания в одну строку через

место).

**atex: ходовые ширины** — `docs/integram-reports.md:182-219`, `preferable_widths`.
Группировка позиций заказов по ширине, сырью, намотке и длине, `SUM(Кол-во)` с сортировкой по
убыванию, внешние фильтры по сырью и намотке. Результат питает подбор раскроя в

**atex: «есть ли событие» как полусоединение** — `docs/integram-reports.md:497-534`,

**atex: вход планировщика** — `docs/integram-reports.md:221-343`, `cut_planning`.

## 3. Связи

Ссылка в Интеграме — это отдельная запись `up=<владелец>, t=<цель>, val=<реквизит>`
(`docs/kb/schema.md:161`). Это даёт сразу оба направления связи и множественные ссылки
(«многие-ко-многим» без промежуточной таблицы), а компилятор строит соединения по ним
автоматически (§1).

Ссылочная целостность проверяется ядром при каждой записи:

- ссылка обязана указывать на существующую запись нужного типа (`index.php:12526`);
- запись, на которую ссылаются, удалить нельзя — `409 Conflict` (`:12704-12707`, для пакета
  — `:14414`); массовое удаление выборки пропускает такие записи (`:8217-8241`);
- тип, у которого есть записи, удалить нельзя (`:14709`);
- уникальность и составной ключ первой колонки проверяются при записи
  (`FindUniqueRecordDuplicate`, `:12221-12290`, `docs/kb/crud.md:40-41`).

## 4. Изменение типов и структуры

Структура — это данные той же таблицы, поэтому изменение типа реквизита — это изменение одной
записи метаданных (`_d_save`, `:14497-14514`), без `ALTER TABLE`, без остановки и без
миграции данных. Значения хранятся в `val` и читаются по новому типу (`Format_Val`,
`:2788-2834`).

Пример с живой базы: в запросе `cut_planning` источник колонки «Сырьё» переключили на другой
реквизит одной операцией `_m_save` и сверили на боевой базе — из 188 резок ноль расхождений,
12 ранее пустых значений заполнились (`docs/integram-reports.md:295-305`).

Оговорка: при смене типа ядро не проверяет, что уже записанные значения подходят новому
типу. Несовместимые значения не теряются (они в `val`), но и не конвертируются.

## 5. Транзакционная целостность

Здесь нужно говорить точно. **Явных транзакций в ядре нет**: нет `START TRANSACTION`,
`COMMIT`, `LOCK TABLES`; это прямо зафиксировано в коде (`index.php:12449-12452`). Каждая
запись — это отдельная атомарная операция InnoDB (одна строка = одно значение).

Как платформа обеспечивает целостность без транзакций:

- **Каждая операция проверяется полностью** — права, уникальность, ссылки — одинаково для
  одиночной команды и пакета (`ApplyMSave`/`ApplyMSet`, `:12530-12686`, `:12992`).
- **Пакет `_m_batch`** — до 1000 операций (`:12362`) со статусом каждой; упавшая операция не
  откатывает соседние, пакет доводится до конца (`docs/kb/crud.md:127`).
- **Массовые изменения идут через SET-запросы** с превью и подтверждением, а фильтр по
  «ещё не обработанным» делает повтор безопасным (пример с токенизацией, §2.4).
- **Бизнес-правила закрепляются правами**: в atex статус «Согласовано» и дату ставят только
  SET-запросы `approve_order` / `approve_position` под правами владельца запроса — у роли
  «Менеджер» эти поля только для чтения (`docs/integram-reports.md:463-495`).
- **Журнал изменений**: каждый изменяющий SQL пишется в `<база>_sql.jsonl` с состоянием до
  и после (`logChangeBefore/After`, `:1792-1824`).

Чего нет: атомарности группы операций «всё или ничего». Порядковый номер новой записи
(`MAX(ord)+1`) и проверка уникальности выполняются без блокировки (`:9585-9594`,
`:12221-12290`), поэтому при одновременной вставке одинаковых ключей возможен дубль — он
вычищается постфактум (`checkDuplicatedReqs`, `:12062-12070`).

## 6. Многопользовательская нагрузка

Что есть в ядре:

- индексы `PRIMARY(id)`, `up_t(up,t)`, `t_up(t,up)`, `t_val(t,val(191))`, `up_ord(up,ord)`
  (`docker/mysql/010-integram-bootstrap.sql`) покрывают все основные пути — по типу, по
  родителю, по значению;
- подсказки оптимизатору `USE INDEX` там, где фильтр не использует индекс (`HintNeeded()`,
  `:1826-1853`);
- лимит времени запроса (30 с по умолчанию, до 600 с) и принудительный `KILL QUERY`
  зависшего запроса (`:25-26`, `:59-104`);
- обязательная пагинация списков (20 строк по умолчанию, до 1000, `:8204-8213`) и потолок
  строк, заданный в самом запросе (`:4766-4802`);
- построчные маски прав в списках (`:8145-8161`) — каждый пользователь видит только своё,
  без отдельных представлений.

Как время запроса зависит от объёма. Запрос, который выбирает ограниченное число записей —
по ключу, родителю, ссылке, значению, — проходит через индексы на каждом соединении. Его время
определяется размером ответа, а не размером базы, и не зависит от числа соединений.
Агрегация по большой выборке читает каждую строку выборки и растёт с объёмом. Для неё служат
накопители или выгрузка в колоночное хранилище. Индекс по значению префиксный
(`t_val(191)`), поэтому фильтр `%…` в начале строки и сравнение через `CAST` его не
используют.

Пример: рабочее место упаковщика atex перечитывает свой запрос раз в минуту на каждом
посту, и ввод оператора на соседнем станке виден в пределах минуты
(`docs/integram-reports.md:768`).

Цифры производительности. Замер на 1 млн транзакций × 45 реквизитов, Postgres, модель
python2node (`docs/kb/hierarchical-oltp.md:60-70`):

| Раскладка | Хранение | Сумма по валютам за 90 дней | Карточка по ключу |
|---|---:|---:|---:|
| Широкая таблица | 458 MB | 1,27 с | 3 мс |
| jsonb | 1676 MB | 1,90 с | 1–4 мс |
| EAV как есть | 5896 MB | 28,26 с | 3 мс |
| EAV с разрезом и накопителями | 5510 MB | 4,67 с | 3 мс |
| ClickHouse | 133 MiB | 0,053 с | 120 мс |

Точечные операции (карточка, правка) — на уровне широкой таблицы. Тяжёлая агрегация по
миллионам строк без подготовки медленнее; с разрезом и накопителями разрыв сокращается
до ~4 раз, а для чистой аналитики больших объёмов уместна выгрузка в колоночное хранилище
(§2.4, DWH). Нагрузочного теста с многими одновременными пользователями в репозитории нет.

## 7. Сопровождение больших приложений

- **Запросы — это данные.** Их можно читать, менять и переносить тем же API, что и записи:
  в репозитории запросы xcom лежат как JSON (`docs/xcom_reports.json`), описания запросов atex
  — в `docs/integram-reports.md`. Правка запроса не требует выкладки кода.
- **Запрос — стабильный контракт.** Клиенты (рабочие места, дашборды, Airflow) обращаются к
  запросу по имени и колонкам; внутреннюю структуру можно менять, сохраняя колонки (пример с
  `cut_planning`, §4).
- **Права на уровне запроса.** Запрос работает как хранимая процедура: выполняется с правами
  автора и отдаёт роли ровно то, что нужно. Грант на запрос открывает все его колонки, маски
  строк к нему не применяются, SET-запрос меняет записи без проверки прав роли на каждую
  (`docs/kb/queries.md`). Внешней системе выдаётся право на один запрос, а не на таблицы
  (`docs/integram_airflow_dwh_runbook.md`).
- **Масштаб проектов:** spz — 90 таблиц и 310 реквизитов (`docs/spz-training-base.md:34-58`),
  atex — 37 запросов на одной базе (`docs/integram-reports.md:453`), производственный цикл от
  заказа до партии готовой продукции с планированием и рабочими местами по станкам.

## 8. Итог по пунктам возражения

| Пункт | Ответ |
|---|---|
| Аналитические запросы | Компилируются в один SQL: JOIN по метаданным, агрегаты, `GROUP BY`, `HAVING`, вычисляемые колонки, вложенные запросы любой глубины, `WITH RECURSIVE`. Примеры — xcom, atex, финмодель, sportzania. |
| Связи | Ссылки в обе стороны и «многие-ко-многим» без промежуточных таблиц; JOIN строится автоматически; ссылочная целостность — `409` при удалении, проверка цели при записи. |
| Изменение типов | Одна запись метаданных, без `ALTER TABLE` и миграций; пример переключения колонки на живой базе без расхождений. |
| Транзакционная целостность | Каждая операция атомарна и полностью проверена; есть журнал изменений и идемпотентные массовые операции. Групповых транзакций «всё или ничего» нет. |
| Многопользовательская нагрузка | Индексы по всем путям, лимиты времени, пагинация, построчные права. Время выборочного запроса определяется размером ответа, а не базы, при любом числе соединений; тяжёлые агрегаты по миллионам строк — через накопители или DWH. |
| Сопровождение | Запросы — данные и стабильный контракт; права на уровне запроса; правка без выкладки кода. |
