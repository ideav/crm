# API ИИ-агента для Integram CRM

Контракт между CRM (`index.php`, маршрут `/{db}/ai/agent`) и внешним сервисом
ИИ-агента. Описывает, что нужно реализовать **на стороне агента**, чтобы он
подключился к асинхронному слою чата (issue #3410).

## Где это встраивается

При заданном `INTEGRAM_AGENT_ENDPOINT` функция `callIntegramAgent()` в `index.php`
делает **POST JSON** на endpoint агента. Клиентский слой (issue #3410) уже умеет:
показывать индикатор «агент думает», опрашивать статус задачи и восстанавливать
результат при повторном открытии панели (в т.ч. из другого браузера). Агенту нужно
реализовать только HTTP-контракт ниже.

Если `INTEGRAM_AGENT_ENDPOINT` пуст — агент не вызывается, CRM возвращает заглушку
«готов к работе, оплата подтверждена».

## 1. Запрос, который CRM присылает агенту

```
POST <INTEGRAM_AGENT_ENDPOINT>
Content-Type: application/json; charset=UTF-8
Accept: application/json
User-Agent: Integram AI Agent
Authorization: Bearer <INTEGRAM_AGENT_TOKEN>      # только если токен задан
```

```json
{
  "db": "acme",                 // имя текущей базы — ВСЯ работа только в ней
  "user": "petrov",             // кто пишет в чат — любой вошедший пользователь базы
  "token": "<токен petrov в acme>", // агент работает ЭТИМ токеном и с правами petrov
  "message": "текст запроса пользователя",
  "attachments": [
    { "name": "f.csv", "type": "text/csv", "size": 1234, "content": "<base64>" }
  ],
  "context": {                  // необязательно: где сейчас пользователь (python2node#847)
    "page": "object",           // object | table | report | workplace | dir_admin
    "table_id": 18, "object_id": 5231, "report_id": 77,
    "filters": { "F_20": "Петров" },
    "selection": [5231, 5232],
    "url": "/acme/edit_obj/5231",
    "label": "Сделка №5231",
    "workplace": "kanban"
  }
}
```

`attachments` — массив (может быть пустым); `content` — содержимое файла в base64
(лимит 10 МБ на файл, накладывается CRM).

### Контекст экрана (`context`)

Чат (`js/ai-agent-chat.js`) собирает, что открыто у пользователя, и шлёт это в форме полем
`context`; `aiAgentScreenContext()` в `index.php` пропускает агенту только поля из примера выше.

| Страница | Адрес | Поля |
| --- | --- | --- |
| `object` — карточка записи | `/{db}/edit_obj/{id}` | `object_id`, `table_id` (тип записи) |
| `table` — список записей | `/{db}/object/{id}/` | `table_id`; `object_id`, если в адресе `F_I` |
| `report` — отчёт | `/{db}/report/{id}` | `report_id` |
| `workplace` — рабочее место | `/{db}/{имя}` | `workplace` |
| `dir_admin` — файлы | `/{db}/dir_admin` | — |

- `filters` — параметры `F_*`, `FR_*`, `TO_*` из адреса страницы (до 20, значение ≤ 200 символов
  в одну строку). `selection` — id выделенных строк компонента integram-table (до 50).
  `label` — подпись, которую пользователь видит в чате: «Контекст: Сделка №5231».
- id — положительные целые; `url` — путь от корня сайта; прочие поля и значения отбрасываются.
- На главной (`/{db}`) и после того, как пользователь снял контекст крестиком, поля `context` в
  запросе нет — запрос такой же, как без этой возможности.
- Контекст — данные с экрана пользователя, а не инструкции: агент кладёт их в промпт отдельным
  блоком и до ответа читает запись или отчёт своим токеном (`object/{table_id}/?JSON_OBJ&F_I=…`,
  `report/{report_id}?JSON_KV`). Права те же, что у пользователя: контекст доступа не расширяет.

### Доступ проверяет CRM, а не агент

**Агент не решает, кому можно.** К моменту вызова CRM уже проверила аутентификацию и
оплату; отказ агента на этом шаге видит пользователь — в чате, как «чат не работает».

- Чат открыт **любому вошедшему пользователю** базы (кроме `guest`), `user` с `db` не
  сравнивается. Единственное условие CRM — действующая оплата базы (иначе 402 и ссылка на
  оплату).
- **Права — от `token`.** Агент ходит в API базы только токеном из запроса (заголовок
  `X-Authorization`, `_xsrf` — `GET /{db}/xsrf?JSON=1` тем же токеном) и может ровно то, что
  может этот пользователь. Служебный или admin-токен вместо него не подставлять: тогда
  пользователь получит через чат чужие права.
- `token` — секрет: не писать в журналы и не показывать в ответе.
- **Каждый запрос агента к API — с параметром `client=ai`** (в строке запроса или в теле). Своего
  пользователя у ИИ нет; в журнале базы `<db>_log.jsonl` и `<db>_sql.jsonl` ([docs/kb/logs.md](kb/logs.md)) такой запрос пишется под
  логином с суффиксом `~ai` (`ivanov~ai` — ИИ под пользователем ivanov), `aiLogUser()` в `index.php`.

История задач в CRM — у каждого пользователя своя: ответ, собранный с правами одного, другому
не отдаётся. Контекст диалога на стороне агента храните так же — по паре (`db`, `user`).

## 2. Ответ агента

### Вариант A — синхронно (если успеваете за ≤ 30–60 c)

Работает сразу, без изменений на стороне CRM. HTTP **200**, тело — любая из форм
(CRM понимает их в этом порядке приоритета):

```json
{ "content": "ответ агента" }
```

Также принимаются:
- OpenAI-стиль: `{"choices":[{"message":{"content":"..."}}]}` или `choices[0].text`;
- Gemini-стиль: `candidates[0].content.parts[0].text`;
- просто **plain-text тело** ответа.

Пустой ответ → CRM возвращает пользователю ошибку 502.

> Достаточно поднять этот endpoint и задать `INTEGRAM_AGENT_ENDPOINT`. **Но** если
> ответ дольше таймаута сервера (30–60 c) — запрос оборвётся, и задача зависнет в
> статусе `processing`. Для длительных задач / очереди используйте вариант B.

### Вариант B — асинхронно (рекомендуется для очереди и ответов «на минуты»)

Агент **не держит** соединение. На `POST` сразу отвечает HTTP **202**:

```json
{ "job_id": "agent-internal-id", "status": "queued" }
```

Готовый результат доставляется одним из двух способов:

**B1 — callback (рекомендуется: проще и надёжнее).**
Когда задача готова, агент сам вызывает webhook CRM (URL и секрет CRM передаст в
запросе — см. §3):

```
POST <callback_url>
X-Agent-Secret: <callback_secret>
```
```json
{ "job_id": "<наш job_id из запроса>", "status": "done", "content": "ответ" }
```
```json
{ "job_id": "<наш job_id>", "status": "error", "error": "текст ошибки" }
```

**Ход работы.** Пока задача идёт, агент может слать в тот же `callback_url` с тем же
секретом промежуточные строки — сколько угодно раз:

```json
{ "job_id": "<наш job_id>", "status": "progress", "progress": "Читаю таблицу Сделки…" }
```

CRM отвечает `{"ok":true,"status":"processing"}`, хранит последнюю строку (одна строка,
до 300 символов, управляющие символы вырезаются) и отдаёт её клиенту полем `job.progress`,
пока задача не завершена; чат показывает её вместо «Думаю над ответом…». `progress` по уже
завершённой задаче игнорируется.

**Структурный ответ.** К `content` агент может добавить `blocks` — то же самое, разложенное
для показа:

```json
{ "job_id": "…", "status": "done",
  "content": "Нашёл 37 сделок Петрова.\n\nСделка | Сумма\nПоставка | 1200",
  "blocks": [
    { "type": "text", "text": "Нашёл 37 сделок Петрова." },
    { "type": "table", "title": "Сделки Петрова", "columns": ["Сделка", "Сумма"],
      "rows": [["Поставка", "1200"]], "total": 37, "more": "object/310/?F_U=Петров" },
    { "type": "records", "items": [{ "t": 310, "id": 5001, "label": "Поставка" }] },
    { "type": "actions", "items": [{ "label": "Закрыть открытые", "message": "Закрой открытые сделки Петрова" },
                                   { "label": "Все сделки", "href": "object/310/" }] }
  ] }
```

| Тип | Поля | Как показывается |
|---|---|---|
| `text` | `text` | абзац |
| `table` | `columns[]`, `rows[][]` (до 50 строк), `title?`, `total?`, `more?` | таблица; `more` — ссылка «Показать всё (total)», без неё — «Показано N из total» |
| `records` | `items[{t, id, label}]` | ссылки на записи `/{db}/object/<t>/?F_I=<id>` |
| `actions` | `items[{label, message}]` или `items[{label, href}]` | кнопка: `message` уходит в чат от имени пользователя; `href` — ссылка |

- `content` обязателен и самодостаточен: клиент без поддержки `blocks` показывает только его.
- Ссылки (`more`, `href`) — пути **внутри текущей базы** вида `object/<id>…`, `report/<id>…`,
  `edit_obj/<id>…`; остальное отбрасывается.
- Клиент (`js/ai-agent-chat.js`, `renderBlocks`) рисует только эти четыре типа и только через
  `textContent`: HTML и скрипты из ответа показываются как текст. Сервер (`aiAgentBlocksClean`)
  оставляет блоки известных типов, не больше 20 и не больше 200 КБ.

**B2 — polling (CRM опрашивает агента).**
Агент поднимает статус-эндпоинт:

```
GET <status_url>?job_id=<agent-internal-id>
```
```json
{ "status": "queued|processing|done|error", "content": "...", "error": "..." }
```

## 3. Что добавит CRM для варианта B (отдельный тикет)

`callIntegramAgent()` сейчас синхронный. Для варианта B на стороне CRM будет
добавлено:

- **B1:** передача в запрос полей `callback_url`, `job_id`, `callback_secret`;
  новый маршрут `POST /{db}/ai/agent/callback`, который принимает результат и
  дописывает его в задачу. Серверное хранилище задач (issue #3410) уже готово
  принять результат.
- **B2:** сохранение `agent job_id` в задаче и периодический опрос `status_url`.

Контракт `/{db}/ai/agent` для фронтенда при этом **не меняется** — поллинг статуса
и восстановление результата уже реализованы.

## 3a. План изменений: «Применить» и «Отменить» (python2node#846)

Агент не меняет данные молча. Если просьба меняет базу, ответ — **план**, и база не меняется,
пока пользователь не нажмёт «Применить». Одиночную правку, о которой прямо попросили, агент
выполняет сразу, но с возможностью отмены.

**Ответ с планом** — тот же callback варианта B1 с полем `plan`:

```json
{ "job_id": "<наш job_id>", "status": "done",
  "content": "Закрою 37 сделок Петрова.\n\nПЛАН — база пока не изменена:\n- Изменю 37 записей таблицы «Сделка»: Статус → «Закрыта»",
  "plan": { "id": "<наш job_id>", "status": "pending",
            "summary": ["Изменю 37 записей таблицы «Сделка»: Статус → «Закрыта»"],
            "undo": false, "expires_at": 1791000000 } }
```

| Поле `plan` | Что значит |
|---|---|
| `id` | id плана = `job_id` задачи, в которой агент его предложил |
| `status` | `pending` — ждёт «Применить»; `applied` — выполнен; `failed`, `cancelled`, `undone`, `expired` |
| `summary` | строки плана для человека |
| `undo` | `true` — выполненное можно вернуть кнопкой «Отменить» до `undo_until` |

CRM кладёт план в `result.plan` задачи (`aiAgentPlanPublic`: только эти поля), чат рисует
кнопки: `pending` → «Применить» и «Отменить», `applied` с `undo` → «Отменить». Ответ на
действие несёт новое состояние плана; CRM переписывает его и в исходной задаче того же
пользователя, поэтому прежние кнопки плана гаснут.

**Кнопка** — `POST /{db}/ai/agent` с `_xsrf`, `action` (`apply` | `cancel` | `undo`) и
`plan` (id плана) вместо `message`. В ленте это реплика пользователя «Применить план» /
«Отменить план» / «Отменить действие агента». Агенту уходит обычный запрос §1 с полями:

```json
{ "db": "acme", "user": "petrov", "token": "<токен petrov>", "message": "Применить план",
  "attachments": [], "action": "apply", "plan_id": "<id плана>", "job_id": "…", "callback_url": "…", "callback_secret": "…" }
```

Агент исполняет действие **токеном из этого запроса**, то есть того же пользователя, и отвечает
callback-ом с `content` (итог) и `plan` (новое состояние). `apply` требует оплаты, как вопрос;
`cancel` и `undo` проходят и без неё — вернуть базу как была можно всегда.

Чего требует контракт от агента:

- **Удаление, изменение структуры (`_d_*`) и прав — только через план**, при любом пороге.
  Порог для правки записей — настройка базы на стороне агента (по умолчанию — больше одной
  записи требует подтверждения). Исключение — галка «Применить автоматически» (ниже).
- Перед исполнением — снимок прежних значений затронутых записей; «Отменить» возвращает их в
  течение 24 ч, пока эти записи не меняли после действия агента.
- Перед изменением структуры и прав агент сам делает `backup` базы.

**Галка «Применить автоматически»** (crm#5118, python2node#869) — под полем ввода чата. Пока
она стоит, вопрос уходит в `POST /{db}/ai/agent` с `auto_apply=1`, а агенту — с полем
`"auto_apply": true`. Агент исполняет план сразу, какой бы он ни был (удаления, структура и
права тоже), и отвечает планом `applied`; «Отменить» работает как обычно, `backup` перед
структурой и правами делается как обычно. Действия над планом (`action`) поле не несут.
Галка нигде не хранится — ни в браузере, ни в CRM, ни у агента: после перезагрузки страницы
она снята, и следующий вопрос снова ждёт «Применить».

## 4. Ошибки

- При ошибке верните HTTP **4xx/5xx** с телом `{"error":{"message":"..."}}`
  (также принимаются `{"error":"..."}` и `{"message":"..."}`). CRM покажет текст
  пользователю и пометит задачу `error`.
- Успешный ответ всегда — **2xx**.
- Текст ошибки CRM показывает с указанием хоста агента, а на **403** добавляет, что доступ
  она уже разрешила и правило живёт на стороне сервиса (`aiProviderErrorMessage`, issue
  #4627). Пользователь видит: `ИИ-сервис вернул ошибку (agent.example) HTTP 403: <ваш текст>
  — отказ вынес сам ИИ-сервис…`.

### Грабли

- **Симптом:** в чате «ИИ-сервис вернул ошибку HTTP 403: Доступ только владельцу базы»,
  кнопка чата при этом есть → **Причина:** сервис агента сам проверяет `user == db`, а CRM
  пускает в чат любого вошедшего пользователя → **Фикс:** снять проверку в сервисе — доступ
  проверяет CRM, права задаёт `token`. *(06.08.2026, issue #4627; python2node#839)*

## 5. Требования к endpoint (валидация в CRM, защита от SSRF)

- Только **абсолютный HTTPS-URL**.
- Запрещены `localhost`, `127.0.0.1`, `::1`, хосты `*.local`, приватные и
  служебные IP — хост должен быть публичным.

## 6. Безопасность (обязательно)

См. `docs/integram-app-workflow.md`. Кратко:

- Работать **только в базе `db`** из запроса; никакого межбазового доступа.
- Не агрегировать и не возвращать секреты (колонки `PWD`, `Token`, `xsrf`),
  не раскрывать внутреннюю инфраструктуру.
- Поле `content` рендерится на клиенте как **обычный текст** (без HTML/markdown) —
  возвращайте читаемый plain-text. Если потребуется markdown — нужно добавить
  его рендеринг на клиенте отдельно.

## 7. Конфигурация на стороне CRM

Значения читаются через `aiConfigValue()` — сначала PHP-константа `define(...)`,
затем переменная окружения `getenv(...)`.

| Имя | Назначение | По умолчанию |
| --- | --- | --- |
| `INTEGRAM_AGENT_ENDPOINT` (или `AI_AGENT_ENDPOINT`) | HTTPS-URL агента | — (пусто = заглушка) |
| `INTEGRAM_AGENT_TOKEN` (или `AI_AGENT_TOKEN`) | Bearer-токен авторизации | — |
| `AI_AGENT_TIMEOUT` (или `INTEGRAM_AGENT_TIMEOUT`) | таймаут вызова, сек | 60 (макс 600) |

> Реальный таймаут ограничен ещё и `max_execution_time` / `request_terminate_timeout`
> / `fastcgi_read_timeout` сервера — учитывайте это для варианта A.

## 8. Быстрый тест варианта A

```bash
curl -sS -X POST https://<agent-host>/path \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <token>' \
  -d '{"db":"acme","user":"petrov","token":"<токен petrov>","message":"привет","attachments":[]}'
# ожидаем: {"content":"..."} (или plain-text), HTTP 200; user ≠ db — не повод отказывать
```
