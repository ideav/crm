# Запрос как хранимая процедура

В Интеграме единица серверной логики — таблица **«Запрос»** (t=22). Запрос не только
читает данные, но и **вносит изменения**: выражения присвоения, создание и удаление
записей, вызовы внешних сервисов. Это аналог хранимой процедуры классической СУБД:
логика хранится в базе, выполняется на сервере с правами владельца запроса, роли
получают доступ грантом на сам запрос, а не на таблицы.

Обзор всего движка запросов — [query-engine-capabilities.md](query-engine-capabilities.md).
Здесь сведены механизмы записи: что запускает изменение, что проверяется при нём и где
это в коде (`index.php`).

## 1. SET-запрос: изменение данных выражением

У колонки отчёта есть атрибут **«Присвоить»** (тип 132, `REP_COL_SET`,
`index.php:715`) — выражение, вычисляемое для каждой записи выборки; результат
присваивается колонке. Механика:

- Выражение поддерживает `BuiltIn`-переменные, `[THIS]` (текущее значение),
  `substring([THIS],n[,m])`, `CURL.*` (подстановка `[THIS]` — `index.php:4479-4482,
  4632-4633`).
- Обновление записи — `Update_Val` (`index.php:10503`); SET-выражение умеет и
  **создавать записи** (ветка «new rec», `index.php:5824-5843, 6076`).
- **Пустое значение удаляет запись** (`Delete($i)`, `index.php:6127`).
- Охват задаётся фильтрами `FR_/TO_` в вызове. Вместе с фильтром «ещё не обработанные»
  (`!%` = IS NULL) повторный прогон идемпотентен.
- Мультиссылочная колонка принимает набор значений в квадратных скобках:
  `[Тонер,картридж]` — каждое ищется в справочнике по отображаемому тексту,
  отсутствующее создаётся автоматически; одиночная ссылка задаётся числом-ID.

Пример из практики: токенизация наименований — цепочка `REGEXP_REPLACE`/`REPLACE`
в поле SET, фильтр `!%` берёт только неразмеченные записи
([query-engine-capabilities.md](query-engine-capabilities.md), §2.4).

## 2. Вызов: превью → подтверждение

Изменение выполняется в два шага (`index.php:4134`):

1. **GET** без подтверждения — превью «было ⇒ станет»;
2. **POST** с `confirmed=1` — применение ко всем записям под фильтром
   (блок `Execute UPDATEs`, `index.php:6017-6021`).

Подтверждённый вызов проходит `check()` — проверку XSRF-токена
(`index.php:6020-6021`). Живой пример кнопки: `download/atex/js/orders.js:1472-1482`
— POST на `report/approve_order` с телом `confirmed=1&FR_order_id=…&_xsrf=…`.

## 3. Параметр EXECUTE: автоматический прогон

Реквизит **EXECUTE** (t228, BOOLEAN) у запроса снимает оба шага: запрос выполняется
при вызове любым методом (GET или POST), без подтверждения и без XSRF
(`index.php:4134`, `6018-6020` — ветка `EXECUTE` не зовёт `check()`).

Внедрённый в рабочее место EXECUTE-запрос срабатывает при каждом открытии страницы —
это способ «автоматизации без кнопки». Если реквизита в таблице «Запрос» нет, его
добавляют как обычный булев реквизит. Официальный help — снапшот
`docs/PP Интеграм.mhtml`, раздел «Использование параметра EXECUTE для немедленного
выполнения запросов».

## 4. Права: запрос выполняется с правами владельца

- Роли достаточно **READ-гранта на сам запрос** (таблица «Объекты», t116);
  построчные маски и гранты на колонки роли к SET-обновлениям не применяются —
  меняется только то, что запрос пишет. Формулировка и обоснование:
  [docs/kb/queries.md](kb/queries.md) («SET-запрос меняет записи без проверки прав»),
  [query-engine-capabilities.md](query-engine-capabilities.md) §7.
- **Бизнес-правила закрепляются правами**: поле роли делают read-only, а меняет его
  только кнопка через SET-запрос. Пример: статус «Согласован» и дата согласования
  ставятся исключительно запросами `approve_order` / `approve_position`
  ([query-engine-capabilities.md](query-engine-capabilities.md), §5).
- Рабочие места операторов собирают на запросах `user_*`, выполняемых с правами
  владельца: [integram-app-workflow.md](integram-app-workflow.md) §5.9.4.
- Внешняя система получает право на один запрос, а не на таблицы (пример —
  планировщик с грантом на `report/17021?JSON_KV`).

## 5. Контекст в БД

Условия «по статусам, ролям, датам» формулируются внутри самого запроса:

- **BuiltIn-переменные**, подставляемые при компиляции в любое выражение и фильтр:
  `[TODAY]`, `[NOW]`, `[MONTH_AGO]`, `[USER]`, `[USER_ID]`, `[ROLE]`, `[ROLE_ID]`
  (`index.php:3679-3702`).
- **Подзапрос** `[ИмяЗапроса]` — в формуле, фильтре и даже в маске роли
  ([docs/kb/roles.md](kb/roles.md)).
- **Внешние параметры вызова**: `FR_/TO_`, `_request_.X` (пример — «Меню по роли» с
  `_request_.FR_RoleID`, [integram-app-workflow.md](integram-app-workflow.md) §5.9.3).

## 6. Запрос как HTTP-действие

Колонка-функция `abn_URL` плюс реквизиты запроса **URL** (t97), **URL_POST** (t283),
**URL_HEADER** (t284): при выполнении отчёта на каждую строку делается curl к внешнему
сервису (GET/POST/PUT/PATCH/DELETE); в URL, теле и заголовках подставляются значения
колонок `[ИмяКолонки]`. Ответ читается формулой `CURL.<ключ>` и тем же SET-выражением
пишется в любую запись (`index.php:5660` и далее). Обращение к localhost запрещено.

## 7. Целостность

- Каждая операция атомарна и проходит полную проверку — права, уникальность, ссылки;
  то же верно для пакета `_m_batch` (до 1000 операций): упавшая операция не откатывает
  соседние ([query-engine-capabilities.md](query-engine-capabilities.md), §5).
- Каждый изменяющий SQL попадает в **журнал** `<база>_sql.jsonl` с состоянием до и
  после (`logChangeBefore`/`logChangeAfter`, `index.php:1921, 1971, 2265-2277`).
- **Галка InTransaction** (BOOLEAN-реквизит запроса) делает вызов запроса одной
  транзакцией «всё или ничего»: выборка и все её изменения — SET, создание, удаление —
  фиксируются вместе после блока `Execute UPDATEs`, а отказ посреди вызова (`my_die`,
  фатальная ошибка SQL, обрыв PHP) откатывает уже записанное
  (`Report_tx_begin`/`Report_tx_commit`/`Report_tx_rollback`, `index.php:5578, 6148,
  6296-6336`; откат в `my_die` — `index.php:2956`). Галка действует только на запрос на
  изменение: у запроса есть колонки «Присвоить» (t132) и вызов применяет изменения
  (`confirmed` или EXECUTE). Чистая выборка и превью без подтверждения идут без транзакции. Реквизит распознаётся по имени
  термина `InTransaction`: если термина или реквизита у таблицы «Запрос» нет, запрос
  работает без транзакции. Добавляют его как обычный булев реквизит, так же как EXECUTE.
  Вложенный запрос, вызванный внутри открытой транзакции, свою не открывает.
- Без галки каждая запись фиксируется сразу, и упавший вызов оставляет сделанное до
  ошибки; параллельные вызовы могут дать дубль вставки — фильтр идемпотентности (`!%`)
  снижает риск.
- Транзакция охватывает только базу: вызовы внешних сервисов (`abn_URL`, §6) не
  откатываются, а журнал `<база>_sql.jsonl` сохраняет строки и откатившихся изменений.

## 8. Чем запускается автоматизация

Триггеров «при сохранении записи» в ядре нет: изменение данных всегда происходит при
**вызове запроса**. Способы вызвать:

- кнопка или действие рабочего места: `POST /{база}/report/<имя>?JSON_KV` с
  `confirmed=1`;
- открытие рабочего места со встроенным EXECUTE-запросом;
- внешняя система по расписанию с грантом на один запрос (превью — без `confirmed`,
  применение — с ним);
- ИИ-агент и интеграции через тот же API отчётов.

## Грабли

- **EXECUTE снимает подтверждение и XSRF.** Запрос с EXECUTE пишет данные при каждом
  открытии страницы, куда встроен; для «опасных» присвоений оставляй двухшаговый
  вызов с `confirmed=1`.
- **Пунктуация внутри значения мультиссылки** (кавычки, дефисы, слэши) разрывает
  значение на части. Разделитель — любой символ, кроме букв, цифр и пробела; пробелы
  внутри значения сохраняются (`[ООО Ромашка,ИП Иванов]` — две ссылки).
- **Изменение типа реквизита** — правка одной записи метаданных (`_d_save`), без
  `ALTER TABLE`; старые значения при этом не конвертируются.
- **Без InTransaction серия SET-присвоений не откатывается целиком** — для изменений,
  которые нельзя оставлять наполовину, ставь галку InTransaction (§7); без неё держи
  идемпотентность и журнал.
