# Нагрузочный стенд hlt — методика и результаты (issue #5267)

Стенд нагрузочного тестирования выборок/агрегаций/обновлений в БД hlt (https://ideav.ru/hlt/).
Замеры 24–25.10.2026: 4 справочника + 8 таблиц (`T_{1K,10K,100K,1M}_{W12,W45}`, до 1 млн строк),
56 запросов (sel1/3/5, agg1/3/5, upd на каждую таблицу), сетка **516 ячеек** (потоки 5/10/25/50,
потолок ожидания 30 с, «насыщение» = два подряд отказа соединений).

Итоговые цифры: [results.md](results.md) (сводка) и [results.json](results.json) (сырые).
Сводка выводов и разбор инцидента — в [issue #5267](https://github.com/ideav/crm/issues/5267).

## Повторение на своей базе

1. Нужна база на ядре с REST v2 и пользователь с правами admin. В `api.mjs` укажите свои
   `BASE`, `DB`, `TOKEN`; токен также подставляется в `slice-curl.mjs` и `upd5-curl.mjs`
   (в опубликованных скриптах — placeholder `YOUR_TOKEN`).
2. `node schema.mjs` — создать справочники и таблицы.
3. `node load.mjs dicts`, затем `node load.mjs table T_1K_W12 [workers]` — загрузка чанками
   `_m_batch` с докачкой по текущему числу записей. Для больших таблиц быстрее
   `node import.mjs table T_1M_W12 [workers]` (быстрый BKI-импорт; чанки >4k wide /
   >15k narrow строк молча теряются — не увеличивать).
4. `node queries.mjs` — создать 56 отчётов.
5. `node bench.mjs all` — полная сетка (либо одна ячейка:
   `node bench.mjs cell <scenario> <table> <threads> [limit]`;
   `node bench.mjs cleanup` — удалить `zz_bench%` строки после upd-замеров).
   Результаты дописываются в `results.json`.
6. Ячейки, недотянутые из-за локального node-fetch (деградация TIME_WAIT на длинных
   сессиях), дочитываются curl-ом: `node slice-curl.mjs`, `node upd5-curl.mjs`.
7. `node report.mjs` — `results.json` → markdown.

`state.json` (tid и диапазоны id записей) и `meta0.json` (мета справочников) — состояние
стенда на момент замера; для чистого повторения не нужны, приложены для сверки.

## Замечания по воспроизводимости

- Замер снят на боевом сервере (2 vCPU EPYC, 1.9 ГБ RAM, MySQL 8.0.46, PHP 8.3.6)
  с фоновой нагрузкой ~50–80 % CPU: абсолютные цифры на другом железе будут другими,
  относительные выводы (формулы стоимости выборки/агрегации, точки насыщения) — устойчивы.
- После перезапуска MySQL пул холодный: перемер отдельных ячеек несравним с прогретым
  прогоном.
