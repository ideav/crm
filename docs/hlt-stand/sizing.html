Подбор конфигурации и расчёт параметров системы

По замерам нагрузочного стенда hlt (24–25.10.2026, боевой сервер: 2 vCPU AMD EPYC, 1.9 ГБ RAM, MySQL 8.0.46, PHP 8.3.6; сетка 516 ячеек + перезамер сомнительных на пустом сервере, медианы). Страница отвечает на два вопроса: сколько будет стоить запрос при заданной конфигурации и какую конфигурацию брать под заданную нагрузку. Сырые замеры и графики: load-charts.html, методика и скрипты — README.md.

5. Замеры: ×50 потоков

  • лёгкие sel-запросы ×50 обслуживаются (7–11 rps, p95 ~6–7 с) — «отказы» первого замера были самоиндуцированной очередью: прерванные тяжёлые агрегаты догорают в MySQL и отравляют соседние ячейки сетки;
  • тяжёлые отчёты ×10 не обслуживаются даже на пустом сервере (контрольные пробы: 10/10 таймаутов) — для них насыщение честное;
  • порог потоков определяется ёмкостью воркеров Apache и хвостами тяжёлых запросов, а не числом потоков самого по себе.

6. Подбор конфигурации: правила из замеров

Ключи диапазонных фильтров — фиксированной ширины

Числовой фильтр по коду над longtext не попадает в индекс: читается вся таблица (24.3 с на 500 тыс.). Набивка нулями + строковые границы — 3.2 с (×7.6), читается только срез.
Коды для выборок и отчётов набивать до одной ширины; типизированная числовая колонка значения — отдельное схемное решение (тикет #5278).

Срез отчёта диапазоном почти не экономит

Агрегат по 10 тыс. из миллиона стоит почти как по 100 тыс. — EAV-джойн читает таблицу целиком. Полное чтение — 38–65 с на 1 млн строк (2 vCPU), зависит от числа таблиц в JOIN.
Тяжёлые агрегаты — отдельным контуром (ночь, одиночный поток); в интерактив большие срезы не отдавать.

Ширина строки выборкам безразлична

p95 выборки при 12 и 45 реквизитах отличается в 0.9–1.1× — стоимость определяют колонки запроса, не ширина хранения.
45 реквизитов — не повод дробить таблицу. На агрегатах сравнение ширины не чистое: у T_1M_W45 вдвое меньше строк.

Запись — только батчами

batch100 = ×21 к построчной записи. Точечный one/upd5 — зона насыщения на любых потоках, в интерактив не ставить.
Массовые обновления — upd10–upd500, до ×25 потоков.

Потоки: до ×25 деградация, ×50 — только лёгкие

Выборки: ×10 — ×2.3 латентности, ×25 — ×5.4. ×50 лёгких sel обслуживается (7–11 rps), тяжёлые отчёты уже на ×10 дают 10/10 отказов (очередь воркеров Apache).
Ёмкость потоков определяется воркерами Apache и хвостами тяжёлых запросов, не числом потоков само по себе.

Большие списки не отдавать

Пагинация по 20 строк из 100К/1М — насыщение уже на ×5.
Экраны строить на фильтрах и выборках по ключу; навигатор по данным — через индексные пути.

RAM: данные ×2, swap обязателен

Пул InnoDB 128 МБ на 2.7 ГБ данных = первые прогоны с диска. Self-join по всей EAV-таблице уложил mysqld (OOM при 1.9 ГБ RAM); swap 2 ГБ снял риск.
RAM ≥ 2× объёма данных; пул ≥ горячий набор; тяжёлые self-join отчёты ограничивать (тикет #5276).

Ядра: агрегат масштабируется линейно

Стоимость агрегата — чтение таблицы, она делится по ядрам примерно линейно (проверено до 16 ядер / 700 млн строк, habr 900308).
Выборке ядра отдельного запроса не ускоряют — они разгружают параллельный поток.

7. Границы применимости

  • Все цифры — один сервер класса 2 vCPU / 1.9 ГБ RAM (MySQL 8.0.46, PHP-ядро с REST v2). На другом железе абсолютные значения смещаются, формулы и относительные выводы — устойчивы;
  • на измеренном диапазоне модель укладывается в ±15 % (худшая ячейка перезамера — 8 %); за диапазоном (таблица >1 млн, срез >100 тыс., потоки ≠ опорных) это экстраполяция — допускайте ×1.5–2;
  • не измерено: агрегаты на нескольких потоках по срезам (×1 только), запись при 45 реквизитах, срезы sel больше 5000 строк, ×50 для sel с срезом >10 строк, параллельные клиенты разных типов;
  • фон боевого сервера исключён не полностью: перезамер 25.10 шёл на пустом сервере, сетка 24–25.10 — с фоном; ячейки с ⚠️ в модель не закладывались;
  • потолки замеров: сетка — 30 с, перезамер срезов — 120 с (обе попытки за потолком — время не измерено).
