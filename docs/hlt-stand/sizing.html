Подбор конфигурации и расчёт параметров системы

По замерам нагрузочного стенда hlt (сервер 2 vCPU AMD EPYC, 1.9 ГБ RAM, MySQL 8.0.46, PHP 8.3.6; лесенки потоков и отчёты — 26.10.2026 на тихом сервере, запись и выборки по таблицам — сетка 24–25.10). Порог обслуживания — 60 с: запрос дольше считается необслуженным. Страница отвечает на два вопроса: сколько будет стоить запрос при заданной конфигурации и какую конфигурацию брать под заданную нагрузку. Сырые замеры и графики: load-charts.html, методика и скрипты — README.md.

5. Подбор конфигурации: правила из замеров

Ключи диапазонных фильтров — фиксированной ширины

Числовой фильтр по коду над longtext не попадает в индекс: читается вся таблица (24.3 с на 500 тыс.). Набивка нулями + строковые границы — 3.2 с (×7.6), читается только срез.
Коды для выборок и отчётов набивать до одной ширины; типизированная числовая колонка значения — отдельное схемное решение (тикет #5278).

Срез отчёта диапазоном почти не экономит

Агрегат по 1 тыс. строк из миллиона стоит 25–52 с — EAV-джойн читает таблицу целиком. Полный проход по 1 млн строк — 89–130 с (2 vCPU), за порогом 60 с.
Тяжёлые агрегаты — отдельным контуром (ночь, одиночный поток); в интерактив большие срезы не отдавать.

Ширина строки выборкам безразлична

p95 выборки при 12 и 45 реквизитах отличается в 0.9–1.1× — стоимость определяют колонки запроса, не ширина хранения.
45 реквизитов — не повод дробить таблицу. На агрегатах сравнение ширины не чистое: у T_1M_W45 вдвое меньше строк.

Запись — только батчами

batch100 = ×21 к построчной записи. Точечный one/upd5 — зона насыщения на любых потоках, в интерактив не ставить.
Массовые обновления — upd10–upd500, до ×25 потоков.

Потоки: полка на 8, дальше — очередь

Выборка: до 4 потоков время ответа почти не меняется, к 8 потокам — полка ≈11 запросов/с на 2 vCPU; дальше время растёт с числом потоков (×10 — ×2.1 к ×5, ×25 — ×6.1), но на 50 потоках отказов нет. Отчёт по 100 тыс. строк (5 с в одиночку): одновременные делят ядра, на 25 потоках — 100 % таймаутов.
Тяжёлым отчётам — свой контур или очередь с ограничением параллельности ≤ ядра × 60 с / время отчёта.

Большие списки не отдавать

Пагинация по 20 строк из 100К/1М — насыщение уже на ×5.
Экраны строить на фильтрах и выборках по ключу; навигатор по данным — через индексные пути.

RAM: данные ×2, swap обязателен

Пул InnoDB 128 МБ на 2.7 ГБ данных = первые прогоны с диска. Self-join по всей EAV-таблице уложил mysqld (OOM при 1.9 ГБ RAM); swap 2 ГБ снял риск.
RAM ≥ 2× объёма данных; пул ≥ горячий набор; тяжёлые self-join отчёты ограничивать (тикет #5276).

Ядра: агрегат масштабируется линейно

Стоимость агрегата — чтение таблицы, она делится по ядрам примерно линейно (проверено до 16 ядер / 700 млн строк, habr 900308).
Выборке ядра отдельного запроса не ускоряют — они разгружают параллельный поток.

6. Границы применимости

  • Все цифры — один сервер класса 2 vCPU / 1.9 ГБ RAM (MySQL 8.0.46, PHP-ядро с REST v2). На другом железе абсолютные значения смещаются, формулы и относительные выводы — устойчивы;
  • на измеренном диапазоне модель срезов укладывается в ±30 % от медиан; это предел для этого сервера: прогоны одной ячейки на таблице 1 млн строк сами расходятся до 44 % (пул InnoDB 128 МБ на 2.7 ГБ данных — чтение с диска); за диапазоном (таблица >1 млн, срез >100 тыс.) это экстраполяция — допускайте ×1.5–2;
  • не измерено: агрегаты на потоках по срезам (лесенка — только полный проход 10 и 100 тыс. строк), запись при 45 реквизитах, выборки больше 500 строк на потоках выше ×5, параллельные клиенты разных типов;
  • сервер боевой: кроме стенда на нём ideav.ru и соседние базы; лесенки и отчёты сняты в тихое окно 26.10, ячейки сетки с ⚠️ в модель не закладывались;
  • порог обслуживания — 60 с. Одиночные отчёты дольше порога домерялись до конца (до 150 с), чтобы показать их время; в лесенке после первой ступени с таймаутами — не больше 2 ступеней, зависшие запросы в MySQL добиваются.
