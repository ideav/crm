# Перенос базы со старого Интеграма в новый

Процедура переносит базу `<db>` со старого Интеграма (integram.io, ядро
`experiments/index_integram.io.php`) на новый (ядро `index.php` этого репозитория).
Инструмент — `migrate.js`, зависимостей нет, нужен Node 18+.

## Чем отличаются ядра

| | Старое ядро | Новое ядро |
|---|---|---|
| Длинное значение | первые 127 символов в строке, остаток — кусками по 127 в строках `t=0, up=<id>, ord=0,1,…`; хвостовые пробелы кусков срезаны MySQL | целиком в одной строке, `val longtext utf8mb4` |
| Меню (запрос `MyRoleMenu`) | плоский список, колонки `Name`, `HREF` | дерево, колонки `menu_id`, `menu_up`, `name`, `href`, `icon` (`templates/main.html`, блок `MyRoleMenu`); запросы `myMenus` и `rec`, функция `RECURSIVE` |
| jQuery | подключает `main.html` для всех рабочих мест | подключает само рабочее место |
| Кука токена | `<db>=<токен>` | `idb_<db>=<токен>` |
| Хеш пароля | `sha1(SALT . strtoupper(логин) . db . пароль)` | `sha512(SALT . db . пароль)` |

Запросы (тип 22, колонки 28, связи 44), их плейсхолдеры (`[USER_ID]`, `[TODAY]` …) и адреса
`report/<id>` в обоих ядрах одинаковы — после склейки хвостов запросы базы работают без правки;
меняются только запросы меню (шаг 3).
Файлы лежат в `templates/custom/<db>/` и `download/<db>/` и в обоих ядрах доступны через
`/<db>/dir_admin/`.

## Шаги

### 1. Таблица базы

Таблица `<db>` копируется с сервера MySQL старого Интеграма на сервер нового (например,
`mysqldump <схема> <db> | mysql <схема>`) и переводится на новое ядро SQL-скриптом:

```bash
node tools/old-integram-migration/migrate.js sql --db <db> > merge-tails.sql
mysql <схема> < merge-tails.sql
```

Имя таблицы задаётся в скрипте один раз — первой строкой `SET @tbl = '<db>';`, — так что готовый
скрипт можно взять и поправить руками. Скрипт:
1. приводит структуру к новому ядру: `id`, `t`, `up`, `ord` — `int UNSIGNED`, `val` —
   `longtext utf8mb4_general_ci`, индекс `t_val (t, val(127))`;
2. собирает каждое значение из строки и её хвостов `t=0` и удаляет хвосты. Каждый кусок, кроме
   последнего, дополняется пробелами до 127 символов: старое ядро писало куски ровно по 127, MySQL
   срезал у них хвостовые пробелы, а `Get_tail` возвращал их при чтении. Без добивки слова на стыках
   кусков слипаются;
3. добавляет таблице «Меню» реквизит «Иконка» с id 391 — в него пишет редактор меню нового ядра
   (`js/main-app.js`, `t391`). Занятый id 391 не трогается.

Повторный запуск ничего не меняет. В конце — закомментированный `RENAME TABLE` под новую схему.

### 2. Файлы

```bash
node tools/old-integram-migration/migrate.js files \
  --old https://integram.io/<db> --old-token <токен старой базы> \
  --new https://<сервер>/<db> --new-token <токен новой базы> [--apply]
```

Копирует `templates/custom/<db>/` и `download/<db>/` со всеми подкаталогами байт-в-байт.
Не копируются:
- каталоги `logs` и `backups`;
- шаблоны корня `templates/custom/<db>/`, одноимённые общим шаблонам нового ядра
  (`templates/*.html` репозитория: `main.html`, `info.html`, `dash.html`, `report.html` …):
  такой файл перекрыл бы новую версию. `--keep-overrides` копирует и их.

Старый `main.html` подключал jQuery для всех рабочих мест, новый — нет: рабочее место нового ядра
подключает его само. Шаблону на jQuery (`$(`, `$.`, `jQuery`) без своего подключения инструмент
дописывает в начало `<script src="/js/jquery3.1.1.min.js"></script>`. Файлы `download/` не
меняются. Глобальные переменные старого `main.html` (`db`, `xsrf`, `id`, `token`, `uid`,
`action`) новый `main.html` задаёт так же.

`dir_admin` создаёт каталоги в нижнем регистре — о каталогах с заглавными буквами инструмент
предупреждает, ссылки на них нужно поправить.

### 3. Меню

```bash
node tools/old-integram-migration/migrate.js menu --new https://<сервер>/<db> --new-token <токен> [--apply]
```

Блок `MyRoleMenu` нового `main.html` строит меню-дерево из одноимённого запроса (колонки
`menu_id`, `menu_up`, `name`, `href`, `icon`) и выводит строку, только если заполнены все пять:
без `icon` меню пустое. Эталонный `MyRoleMenu` нового ядра фильтрует пункты через `[rec]` —
рекурсивный обход меню (функция `RECURSIVE`) от пунктов запроса `[myMenus]`. Шаг приводит базу к
эталону (`docs/integram-app-workflow.md` §5.9.3):
- создаёт функцию `RECURSIVE` (таблица «Функция», 63), если её нет; ядро узнаёт её по имени;
- приводит запросы `myMenus`, `rec`, `MyRoleMenu` (в этом порядке) к эталонным колонкам:
  недостающий запрос создаётся, у отличающегося сначала создаются эталонные колонки, затем
  удаляются прежние (их значения печатаются в журнал);
- если у таблицы «Меню» нет реквизита 391 «Иконка», `icon` — пустая вычисляемая колонка: меню
  выводится без иконок, редактор меню иконки не сохранит до шага 1.

Перед записью колонки сверяются с реквизитами типа 28 из `metadata`; при расхождении правка
отменяется. Затем шаг перечисляет пункты меню всех ролей, которые новое меню не покажет как есть: с
`[USER_ID]` в адресе (новое меню его не подставляет) и с апострофом в адресе.

### 4. Пользователи

Хеши паролей старого ядра новое ядро не принимает: пользователям нужно задать пароли заново
(сброс пароля или правка администратором). Токены (реквизит 125) хранятся открыто и продолжают
работать — ими пользуются шаги 2–3.

Без `--apply` команды `files` и `menu` только печатают, что сделают.
